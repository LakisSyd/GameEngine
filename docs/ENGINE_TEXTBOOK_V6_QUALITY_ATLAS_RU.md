# Часть VII. Диагностика, тестирование и качество игрового среза

Почти готовая игра должна объяснять свои сбои. Когда NPC стоит, дверь не открывается или пробоина не закрывается, разработчик должен увидеть место разрыва цепочки данных за минуты, а не менять параметры наугад. Диагностика является частью архитектуры: после релиза на машине игрока Inspector не будет, поэтому основные причины отказа надо уметь записать в лог или показать ограниченным debug overlay.

## 35. От симптома к нарушенному контракту

### 35.1. Найди первую неверную границу

Представь, что инженер не ремонтирует пробоину. Возможные границы: объект не загружен в Registry; нет `RepairableComponent`; coordinator не видит исполнителя; claim занят; utility AI выбрал другое действие; NavMesh не дал путь; дверь не открылась; controller не сдвинул капсулу; WorkZone недоступна; progress не растёт; `RepairSystem` не завершает работу; geometry job не применил результат. Проверяй в этом порядке и записывай первое место, где ожидание расходится с фактом. Если progress уже достиг порога, дальнейшая настройка AI score бесполезна. Если target никогда не назначен, анимация ремонта ни при чём.

Сделай диагностический снимок Entity: живость, компоненты, role, active, faction, state, command source, target, claim, route status, desired velocity, actual displacement, current animation и last error. Снимок одной строки полезен при репродукции; поток лога каждого кадра быстро станет нечитаемым. Пиши сообщение при переходе состояния или изменении причины, при необходимости добавляй ограниченное семплирование раз в секунду.

### 35.2. Различай ошибку данных, порядка и модели

Ошибка данных: у NPC нет оружия или у двери нет collider. Ошибка порядка: питание посчитано после решения двери, а NPC ждёт старого состояния; анимация обновлена после muzzle socket. Ошибка модели: формула ремонта даёт слишком быстрый прогресс или enemy aim использует невидимую текущую позицию игрока. Эти категории требуют разных исправлений. Добавление недостающего компонента не решит неправильную формулу; перестановка систем не поможет, если объект изначально не был создан. В bug report укажи первую неверную границу, owner данных и ожидаемый момент обновления.

### 35.3. Debug рисунок имеет единицы и масштаб

Линии NavMesh, raycast зрения, muzzle ray, capsule, WorkZone и cover points должны иметь легенду и ограничение времени жизни. Цвет не должен быть единственным носителем смысла: подписи `LOS`, `Fire`, `Path`, `Blocked` помогают при разных фонах. Если рисуешь длину 10, подпиши «10 м». Debug line из локального socket в мировую цель выдаёт ложный след; преобразуй оба конца в world. Определи, какие overlay доступны только в Editor, какие в Development build и какие безопасно оставить в Release через выключенный по умолчанию режим диагностики.

## 36. Тестирование без копирования реализации

### 36.1. Проверяй поведение и инварианты

Тест, который буквально повторяет ветвление исходной функции, обнаружит мало ошибок: он согласится с той же ошибочной идеей. Лучше задать независимые инварианты. После завершения ремонта leak прекращается и claim освобождён. Сумма выделенной мощности не превышает доступной. У мёртвого NPC нет активного выстрела. NPC без личной видимости не получает точные координаты скрытого игрока. После scene reload число Bullet тел соответствует живым объектам. Эти утверждения относятся к игровому правилу, поэтому переживают рефакторинг.

Для математики применяй небольшие известные случаи: нормализованный вектор имеет длину 1; поворот без масштаба сохраняет длину; inverse transform возвращает исходную точку; внутренний обмен газом сохраняет общую массу; постоянная скорость за одинаковое время даёт близкий путь при разных FPS. Дробные вычисления сравнивай с допуском в нужной единице, а не с абсолютным `==`. Угол 0,001 рад может быть большим для прицела, но ничтожным для декоративной камеры; epsilon выбирается по смыслу.

### 36.2. Один тестовый уровень лучше сотни случайных состояний

Сделай отдельную диагностическую сцену из двух комнат. Она содержит дверь, генератор, батарею, пробоину, WorkZone, двух инженеров, врага, союзника и укрытие. Каждый эксперимент начинается с известного сохранённого состояния. Варианты создаются параметрами или отдельными минимальными сценами: `door_unpowered`, `cover_low`, `ally_in_fire_lane`, `repair_target_removed`. После каждого изменения запускай связанные сценарии. Это сокращает время поиска причины, потому что у всех участников известные координаты и компоненты.

### 36.3. Производительность измеряется по слоям

Частота кадров сообщает только итог. Для оптимизации нужны CPU времена input/editor, AI, NavMesh, physics, scene systems, render preparation и GPU время основных passes. Если сцена медленна, сначала определи слой и размер нагрузки: число активных NPC, целей, path queries, draw calls, triangles, lights, shadow passes, Bullet objects. Затем меняй один алгоритм. Например, кэш маршрутов с revision двери может снизить дорогие path queries; ранняя фильтрация целей по distance² уменьшит LOS raycasts; batching может снизить draw calls. Но отключение симуляции за пределами камеры может сломать пожар и давление — состояние мира обязано продолжать жить, даже когда его не видно.

## 37. Критерий почти готовой игры

Выбери один эпизод на 15–30 минут. Игрок получает ясную цель, обучается управлению, сталкивается с аварией и врагом, отдаёт приказ экипажу, видит последствия питания и атмосферы, сохраняет прогресс и может выиграть или проиграть. Результат должен запускаться из отдельного каталога без исходников и редактора. Не называй готовностью одно успешное `Build succeeded`: внешний игрок должен пройти путь без объяснений автора. Если он не понимает, почему дверь закрыта или почему NPC стоит, это дефект обратной связи независимо от корректности внутреннего состояния.

Проведи три цикла наблюдения: сам разработчик с debug overlay, другой человек без debug и чистая машина с Release. После первого исправляй нарушение инвариантов; после второго — цели и подсказки; после третьего — паковку, зависимости, пути к ресурсам и сохранения. Для каждого дефекта запиши шаги воспроизведения, ожидаемое и фактическое состояние, а также приоритет. Только после исправления блокирующих ошибок полируй дополнительные эффекты.

# Часть X. Атлас кода как маршрут данных

Атлас — не список названий классов. Он помогает ответить: где создаётся значение, кто его меняет, кто только читает, когда оно сохраняется и что нужно проверить при отказе. Ниже маршруты показывают типичное прохождение данных. Перед изменением кода открой соответствующий путь и сравни его с текущей ревизией проекта: названия методов и порядок вызовов могут меняться.

## 38. Маршрут от файла сцены до Entity

`SceneManager` загружает JSON сцены, создаёт Entity в `ECSRegistry` и добавляет компоненты. Assets layer загружает модель и материалы; physics создаёт collider/body; renderer получает визуальные ресурсы. Компоненты authoring должны пережить round trip через `SaveScene`/`LoadScene`; runtime указатели на Bullet и GPU ресурсы должны пересоздаваться. Если после загрузки объект видим, но не взаимодействует, сравни авторские и runtime компоненты до сохранения и после. Если Entity ID меняются, все ссылки на другую сущность требуют remap. Для новой системы заранее укажи, какие поля являются authoring, какие runtime, какие сохраняются как игровое состояние.

## 39. Маршрут от ввода до движения персонажа

Input layer фиксирует команду, player controller превращает её в намерение, character movement/controller взаимодействует с Bullet, фактический Transform становится доступен камере, анимации и рендеру. Не записывай желаемое положение прямо в Transform после physics, если body является источником правды. При «игрок нажал W, но не двигается» последовательно проверь input event, режим Editor/Play, разрешение контроллера, desired velocity, collision contact и actual displacement. При «скользит без анимации» движение работает, а состояние animation system не получило скорость или использует старый кадр.

## 40. Маршрут от аварии до действия экипажа

Damage/pressure/flooding создают повреждение и `RepairableComponent`. `CrewTaskCoordinator` оценивает цели и ставит claim, `NpcUtilitySystem` выбирает ремонт, `StateSystem` исполняет путь и WorkZone, `CharacterControllerSystem` двигает capsule, `RepairSystem` применяет progress и завершение. Scene/mesh job может перестроить геометрию; HUD и effects показывают результат. Если пропустить один из слоёв, авария может существовать лишь визуально, а NPC её не увидит. Debug трасса должна хранить для каждой стадии один timestamp и Entity, чтобы переходы можно было сопоставить.

## 41. Маршрут от вражеского контакта до урона

`FactionComponent` разрешает отношения; `NpcCombatSystem` вычисляет допустимость, FOV, LOS и память; `NpcCoverSystem` выбирает индивидуальное укрытие; `StateSystem` отвечает за движение; `NpcRangedCombatSystem` после позы проверяет оружие, дуло и союзников; `WeaponSystem` делает реальный выстрел; `DamageSystem` меняет HP и реакцию. Renderer рисует muzzle flash, tracers и damage overlays по событиям. Если враг целится, но не наносит урон, начни с ranged status и hit result, не с PBR материала. Если урон есть без видимого выстрела, проверь связь боевого события и визуального эффекта.

## 42. Маршрут от команды до картинки на экране

Для PBR объекта Renderer выбирает mesh и материал, `PBRShaderClass` загружает matrices и параметры в GPU buffers; vertex shader выполняет skinning и model→world→view→clip; rasterizer создаёт фрагменты; pixel shader использует текстуры и свет. Если объект расположен неверно, остановись на world transform; если форма верна, а пиксели не появляются, проверь culling/depth; если виден, но освещён неверно, проверь normals, tangent basis, texture channels и light space. Сохраняй контрольный одноцветный shader: он позволяет отделить геометрию от материала за один запуск.

## 43. Как использовать атлас при новой системе

Для новой пожарной механики нарисуй свой маршрут до написания C++: damage event → FireComponent → FireSystem tick → room temperature/oxygen → coordinator task → NPC path/WorkZone → suppression progress → extinguisher resource → HUD/audio → save/load. Напротив каждой стрелки запиши владельца, единицу и порядок кадра. Потом пройди маршрут руками на одном Entity и лишь затем добавляй Editor UI и массовые сцены. Этот приём масштабируется: чем больше систем связано, тем важнее явный путь данных.
