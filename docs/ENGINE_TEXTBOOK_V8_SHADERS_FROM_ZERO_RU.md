# Шейдеры с нуля: от одного треугольника до материала DX Framework

Шейдер — небольшая программа, которую GPU выполняет для элементов рисования. Начинающему полезно представить фабрику: CPU подготавливает геометрию, матрицы и ресурсы; vertex shader получает одну вершину и сообщает, где она окажется на экране и какие данные передать дальше; rasterizer определяет покрытые треугольником экранные фрагменты и интерполирует данные; pixel shader рассчитывает выходной цвет. Это не отдельный мир, который сам знает про Entity, здоровье NPC или двери. Он видит только переданные числа, buffers и textures. Официальное описание стадий и семантик есть в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3dgetstarted/work-with-shaders-and-shader-resources) и [справочнике HLSL semantics](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-semantics).

## 1. Один треугольник до первого HLSL слова

Пусть в локальной плоскости есть вершины A=`(-1;-1;0)`, B=`(1;-1;0)`, C=`(0;1;0)`. Vertex buffer содержит их координаты, возможно цвет и UV; index buffer говорит, что треугольник составлен из индексов 0,1,2. Input layout сообщает D3D, в каких байтах каждой вершины находятся `POSITION`, `COLOR`, `TEXCOORD`. Ошибка смещения в layout означает, что HLSL прочтёт цвет как позицию или мусор, даже если текст шейдера безупречен. Для первого опыта используй один треугольник без освещения и текстуры: меньше стадий могут сломаться одновременно.

После vertex shader вершины проходят через world, view, projection. Для принятой в проекте конвенции с вектором-строкой: `clip = local * world * view * projection`. `world` ставит объект в мир, `view` описывает мир относительно камеры, `projection` создаёт перспективу. Результат содержит четыре координаты `(x;y;z;w)`. После деления на w получается нормализованная экранная позиция; если w некорректен или вершина вне видимого объёма, часть геометрии отсечётся. Не путай переменную `SV_POSITION` в pixel shader с мировой позицией: там уже экранная информация. Если нужен свет в мировом пространстве, передай отдельный `worldPos` и нормаль из VS.

## 2. Читаем простейший vertex shader почти по строкам

Файл `src/Render/Shader/Vs/color.vs` объявляет `cbuffer MatrixBuffer : register(b0)` с тремя матрицами. `b0` — слот буфера констант vertex stage, который CPU должен заполнить и привязать. `VertexInputType` получает `position : POSITION` и `color : COLOR`; `PixelInputType` отдаёт `position : SV_POSITION` и цвет. В `ColorVertexShader` сначала `input.position.w=1.0f`: это точка, на которую должен действовать перенос. Затем идут три `mul` в порядке world, view, projection. Последняя строка `output.color=input.color` переносит значение к следующей стадии. Если убрать эту запись, pixel shader, который ожидает COLOR, получит неопределённые для твоего алгоритма данные; если текущий pixel shader их не читает, картинка может случайно остаться прежней.

Минимальная учебная версия того же смысла:

```hlsl
cbuffer MatrixBuffer : register(b0) {
    float4x4 worldMatrix;
    float4x4 viewMatrix;
    float4x4 projectionMatrix;
};
struct VSIn { float4 position : POSITION; float4 color : COLOR; };
struct VSOut { float4 position : SV_POSITION; float4 color : COLOR; };
VSOut MainVS(VSIn input) {
    VSOut output;
    input.position.w = 1.0f;
    output.position = mul(input.position, worldMatrix);
    output.position = mul(output.position, viewMatrix);
    output.position = mul(output.position, projectionMatrix);
    output.color = input.color;
    return output;
}
```

Это учебный фрагмент для объяснения. Реальные entry point и buffer layout бери из файла проекта и соответствующего C++ класса. На CPU `ColorShaderClass::SetShaderParameters` в `src/Render/Shader/colorshaderclass.cpp` получает матрицы, делает `Map` dynamic buffer, записывает значения, `Unmap` и привязывает буфер через `VSSetConstantBuffers`. `InitializeShader` компилирует VS и PS через `D3DCompileFromFile`, создаёт shader objects и input layout. Если текст HLSL правильный, но CPU не привязал `b0`, шейдер не получит нужные матрицы. Если размер/упаковка C++ структуры не совпали с HLSL, одна из матриц или параметров будет считана неверно. Сначала сравни поля и их порядок, затем слоты и стадию привязки.

## 3. Что делает rasterizer между VS и PS

Vertex shader выполняется для вершин, но экран состоит из пикселей. Rasterizer превращает треугольник в покрытые им фрагменты. Для внутренней точки он вычисляет веса относительно трёх вершин. Если веса равны `(0.2;0.3;0.5)` и вершинные цвета красный `(1;0;0)`, зелёный `(0;1;0)`, синий `(0;0;1)`, интерполированный цвет равен `(0.2;0.3;0.5)`. Веса суммируются до 1. Для точек внутри треугольника они неотрицательны; если один вес отрицателен, точка лежит вне него в этой простой геометрической проверке. Для UV применяется схожая идея, но при перспективе GPU учитывает глубину, чтобы текстура не выглядела растянутой неправильно.

Rasterizer также учитывает лицевую сторону треугольника, режим culling, viewport и depth. Если порядок индексов поменять с (0,1,2) на (0,2,1), треугольник может стать обратной стороной и исчезнуть при back-face culling. Если он за другой поверхностью, depth test не позволит ему перекрасить ближний пиксель. Поэтому «pixel shader не работает» сначала проверяют одноцветным материалом, culling и depth, затем текстуру и свет. В документации Microsoft описаны [pipeline stages и rasterization](https://learn.microsoft.com/en-us/windows/win32/direct3dgetstarted/work-with-shaders-and-shader-resources); конкретные states выбирает renderer твоего движка.

## 4. Простейший pixel shader и ловушка текущего файла

`src/Render/Shader/Ps/color.ps` объявляет `ColorBuffer : register(b0)` и `ColorPixelShader(...):SV_TARGET`. `SV_TARGET` означает цвет, записываемый в текущий render target. Хотя структура входа содержит `color : COLOR`, текущая реализация возвращает `uniformColor`, полученный из constant buffer. Следовательно, разноцветные вершины из `color.vs` **не создадут градиент** с этим pixel shader. Это важный урок чтения пары VS/PS: надо проследить, что PS действительно использует из вывода VS. Для учебного эксперимента можно заменить возврат на `input.color`, но тогда потребуется согласовать C++ параметры и ожидаемое назначение `ColorShaderClass`; это изменение поведения проекта, а не описание текущего результата.

`register(b0)` в VS и `register(b0)` в PS не означают один общий буфер: это слоты двух разных стадий. C++ привязывает matrix buffer к VS и color buffer к PS. Если ошибочно привязать оба через `VSSetConstantBuffers`, PS не увидит цвет. Шейдер ничего не «ищет» по имени C++ переменной — совпадают слот, стадия и байтовая форма данных.

## 5. Текстура: UV, sampler и прозрачный вырез

В `src/Render/Shader/Vs/texture.vs` к позиции добавляется `float2 tex : TEXCOORD0`. Vertex shader вычисляет clip position, затем копирует UV в выход. `texture.ps` объявляет `Texture2D shaderTexture : register(t0)` и `SamplerState SampleType : register(s0)`. Выражение `shaderTexture.Sample(SampleType,input.tex)` возвращает цвет текстуры в интерполированной UV точке. Texture resource и sampler — разные вещи: первый хранит данные, второй задаёт способ выборки за границами, фильтрацию и другие правила. `TextureShaderClass::SetShaderParameters` передаёт texture SRV в pixel stage через `PSSetShaderResources`; без этой привязки `t0` не содержит нужную картинку.

Текущий `texture.ps` выполняет `clip(textureColor.a-0.01f)`. Если alpha меньше 0.01, выражение отрицательно и фрагмент отбрасывается. Это пороговый вырез, полезный для решётки или листвы: там нет полупрозрачного смешения у края. Если нужен дым или стекло с alpha 0.5, одного `clip` недостаточно; нужны соответствующие blend и depth правила. Пиксель с RGBA `(0.8;0.2;0.1;0.005)` отбрасывается, с alpha `0.02` остаётся. Не путай alpha cutout с «прозрачностью всего объекта».

Для проверки UV создай квадрат из двух треугольников и текстуру 2×2: красный, зелёный, синий и белый углы. Если цвета переставлены, проверь U/V и ориентацию изображения. Если виден один размазанный цвет, проверь UV в vertex buffer, input layout, передачу TEXCOORD из VS, sampler и привязку t0. Последовательная проверка каждого интерфейса быстрее случайной замены файла изображения.

## 6. Нормаль, Lambert и первая формула освещения

Нормаль N — единичное направление, перпендикулярное поверхности. Направление L от поверхности к источнику тоже нормируем. Простой диффузный свет пропорционален `max(dot(N,L),0)`. Если N и L совпадают, dot=1 и поверхность освещена сильнее. Если угол 60°, dot=cos60°=0.5. Если свет за поверхностью, dot отрицателен, `max` даёт 0. Зачем нормировать? При N длиной 2 и L длиной 3 dot может быть 6, хотя косинус никогда не больше 1. Тогда яркость ошибочно зависит от длины вектора.

Нормаль не является точкой: перенос world matrix не должен на неё влиять. При неравномерном масштабе простое умножение на world 3×3 может испортить перпендикулярность; нужна матрица, обратная транспонированной линейной части, затем нормировка. В проекте есть `normal_transform.hlsli`; сравни его с `pbr.vs` при диагностике растянутого меша. Проверка на кубе с scale `(2;1;1)`: выведи normal как RGB `(N*0.5+0.5)` и вращай камеру. Если цвет меняется от камеры, нормаль, вероятно, оказалась в другом пространстве, чем ожидалось. Если нормаль верна, переходи к light direction и shadow map.

## 7. От обычного света к PBR без заклинаний

`pbr.vs` и `pbr.ps` уже сложнее учебной пары. Вершинный этап может учитывать кости персонажа, преобразует позицию world/view/projection и передаёт сведения для освещения. Пиксельный этап читает material textures и вычисляет цвет на основе normal, направления света и камеры, roughness и metallic. Сначала покажи на debug material каждую входную величину отдельно: albedo; normal; roughness; metallic; shadow factor. Затем объединяй их. Если итоговая картинка чёрная, один из входов может быть неверным; общая формула не объяснит, какой.

Albedo обычно представляет цвет и проходит через sRGB преобразование при чтении/выводе; normal, roughness и metallic — числовые данные, которые нельзя бездумно декодировать как цвет. Roughness влияет на ширину блика, metallic меняет баланс отражения и диффузной составляющей. PBR микрофасеточная модель использует распределение микронормалей, маскирование и Fresnel. Для новичка сначала достаточно понять энергетический вопрос: сколько света приходит, в какую сторону отражается и почему отражение меняется с углом взгляда. Параметры материала — входы модели, не независимые «эффекты красоты».

Тень обычно начинается отдельным проходом. `ShadowMap` хранит глубину от источника; основной pixel shader сравнивает текущую глубину с записанной и ослабляет прямой свет, если на пути была другая поверхность. Если тень оторвана от объекта, проверь bias, матрицу света и единицы глубины. Если поверхность исчезает лишь в теневом проходе, проверь culling и skinning обоих проходов. Световое PBR и теневая карта должны смотреть на одну и ту же геометрию текущего кадра.

## 8. Как добавить свой маленький шейдерный эффект в движок

Поставь конкретную задачу: аварийная панель плавно мигает, когда уровень опасности комнаты больше нуля. Gameplay система вычисляет `severity` в [0,1]. C++ передаёт её и время визуального эффекта в pixel constant buffer; PS рассчитывает `pulse=0.5+0.5*sin(time*frequency)` и смешивает базовый цвет с красным по `severity*pulse`. При `severity=0` панель остаётся исходной; при `severity=1` и `pulse=1` становится красной. Время можно брать из render clock, если мигание декоративное. Причина тревоги живёт в ECS, чтобы AI, сохранение и HUD видели то же состояние без GPU.

Сделай этот эффект по шагам. Сначала верни постоянный красный `float4(1,0,0,1)` и убедись, что нужный объект получает новый PS. Потом передай один `severity` через buffer, проверь значения 0, 0.5, 1. Затем добавь time и синус. После этого проверь обновление constant buffer (`Map`, запись, `Unmap`, `PSSetConstantBuffers`) и отсутствие конфликта слотов с другим материалом. Наконец проверь, что renderer сбрасывает ресурсы между draw calls: иначе следующая обычная панель может наследовать аварийный buffer.

Выполни четыре диагностические сцены: один треугольник с uniformColor; треугольник с vertex colors после явного изменения PS; квадрат с текстурой 2×2; куб с normal visualizer и одним источником Lambert. Каждый шаг добавляет только одну неизвестную. Когда они работают, читай `PBRShaderClass.cpp` как перечень CPU→GPU договоров: какие constant buffers созданы, в какие слоты привязаны, какие SRV поступают в PS, какой input layout ожидается и когда вызывается DrawIndexed. Эта цепь делает сложный шейдер проверяемым.

## 9. Буфер констант — точное соглашение о байтах

HLSL `cbuffer` не является C++ объектом, который GPU «находит» по имени. Это область байтов с правилами упаковки и привязкой к стадии и номеру регистра. Если в HLSL есть `float4 color; float severity;`, на стороне CPU нельзя без проверки положить подряд только 20 байт и предположить, что следующий buffer начнётся сразу после `severity`. Для D3D11 размер constant buffer должен соответствовать требованиям выравнивания, а поля внутри упаковываются по правилам HLSL. Проще начинать с группы из `float4` и матриц, сверять `sizeof` C++ структуры и отладочным шейдером выводить каждое поле как цвет. Официальное объяснение constant buffers и их привязки есть в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/direct3dgetstarted/work-with-shaders-and-shader-resources).

Путь обновления выглядит так: `Map(buffer,WRITE_DISCARD)` даёт CPU доступ к новой памяти, код копирует структуру, `Unmap` завершает запись, `VSSetConstantBuffers` или `PSSetConstantBuffers` привязывает buffer к нужному stage. Для карты, которая меняется каждый кадр, такой путь должен соответствовать флагам её создания. Если `Map` не удался, не вызывай Draw со случайным старым содержимым, если игра ожидает новую матрицу. Если изменился HLSL layout, но C++ структура осталась прежней, ошибка может выглядеть как «всё тёмное» или «свет прыгает», хотя компиляция обеих сторон успешна: C++ компилятор не проверяет контракт с HLSL автоматически.

Матрицы требуют ещё одной осторожности. Транспонирование перед записью в shader buffer связано с соглашением размещения и выбранной формой `mul`, а не с желанием поменять геометрический порядок. В конкретном `PBRShaderClass.cpp` CPU использует `XMMatrixTranspose`; в `pbr.vs` HLSL умножает позицию слева на world, затем view, projection. При отладке запиши одну тестовую точку на бумаге: локальная `(1;0;0;1)`, перенос по X на 5, камера без поворота. После world ожидается X=6. Если шейдер выдаёт другое число, сначала проверь upload и соглашение вектора/матрицы, а не подбирай camera FOV.

## 10. Какие ещё бывают шейдеры и нужны ли они здесь

В этом курсе подробно рассматриваются vertex и pixel shader, потому что они составляют основной путь видимого mesh в текущем DirectX 11 рендере. В графическом pipeline могут быть и другие стадии: geometry shader работает с примитивами, hull/domain используются для tessellation, compute shader запускает общее параллельное вычисление вне обычного draw треугольника. Наличие этих стадий в API не означает, что проект уже применяет их в главном рендере. Добавляй стадию только под конкретную задачу с измерением стоимости и данных. Для обычной подсветки аварийной панели новый compute pass не нужен: достаточно параметра pixel shader.

Один и тот же pixel shader может запускаться для очень многих фрагментов. Если экран 1920×1080, это около 2.07 млн пикселей до учёта перекрытия объектов и нескольких render passes. Дополнительная операция на каждом пикселе может стоить гораздо больше одной операции на каждом из нескольких тысяч объектов CPU. Но нельзя оценивать производительность только числом строк HLSL: выборки текстур, ветвления, память, overdraw и кэш GPU имеют разные цены. Измеряй GPU время конкретного прохода, а при диагностике сначала сделай одноцветную версию, затем по одному возвращай normal map, shadow, IBL и эффекты повреждения.

## 11. Цвет, яркость и тональная коррекция

Цвет текстуры, число света и цвет монитора относятся к разным пространствам значений. Большинство привычных цветных изображений предназначены для просмотра в sRGB; расчёт освещения удобнее делать в линейном пространстве, где удвоение числа примерно соответствует удвоению светового вклада. Если просто сложить два закодированных sRGB цвета и ограничить каждый канал единицей, результат может быть неверно ярким или тёмным. Карты roughness, normal и metallic хранят данные; применять к ним такое же цветовое преобразование нельзя. В отладке отдельно показывай сырое значение sample и значение после необходимого декодирования.

HDR позволяет временно хранить значения яркости больше 1.0. Затем tone mapping переводит диапазон сцены к диапазону экрана, а output conversion готовит цвет для отображения. Если светильник в HDR buffer даёт `(4;2;1)`, простой clamp сделал бы `(1;1;1)` и потерял цвет яркого источника; tone mapping может сохранить различие каналов. Но выбранная кривая — художественное и техническое решение, а не физический закон для всей игры. Не пытайся исправить отсутствующую normal map увеличением exposure: сначала отладь входы материала.

## 12. Задачи для самостоятельной проверки шейдеров

**Задача A.** VS получил локальную точку `(2;0;0;1)`, world переносит по X на 3, view и projection условно единичные. Какой X уйдёт из VS? Ответ: 5. Если `w=0`, перенос не должен подействовать; это уже направление, а не точка. Найди в `color.vs` строку, которая принудительно ставит `w=1`.

**Задача B.** В вершинах треугольника цвета `(1;0;0)`, `(0;1;0)`, `(0;0;1)` и веса внутренней точки `(0.25;0.25;0.5)`. Интерполированный цвет `(0.25;0.25;0.5)`. Почему текущая пара `color.vs` + `color.ps` не покажет этот цвет? Pixel shader возвращает `uniformColor`, а не `input.color`.

**Задача C.** Normal N=`(0;1;0)`, направление света L=`(0.6;0.8;0)`, оба единичные. `dot=0.8`, Lambert diffuse factor 0.8. Если L=`(0;-1;0)`, фактор `max(-1,0)=0`. Проверь, что N и L находятся в одном пространстве: world normal и view light direction нельзя складывать без преобразования.

**Задача D.** Texture sample вернул alpha 0.009. `texture.ps` считает `clip(0.009-0.01)=clip(-0.001)`, поэтому фрагмент отбрасывается. При 0.011 выражение положительно, фрагмент остаётся. Почему это не равнозначно полупрозрачности 1%? Потому что `clip` принимает двоичное решение оставить/отбросить, а смешение с фоном выполняется другой стадией при подходящем blend state.

**Задача E.** Добавь свой параметр `severity` в учебный pixel shader. Сначала выведи `float4(severity,severity,severity,1)` для значений 0, 0.5, 1. Если экран остаётся одинаковым, проверь C++ buffer, `PSSetConstantBuffers`, номер `register(b#)` и то, что Draw действительно использует этот PS. Только после прохода такого простого теста добавляй цветовое смешение и синусоидальный pulse.
