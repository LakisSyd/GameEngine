# C++ для разработчика игрового движка

Эта глава не пытается пересказать весь язык. Она объясняет ту часть C++, от которой напрямую зависит надёжность DX Framework: где живут данные, кто их уничтожает, почему указатель может стать недействительным и каким образом шаблонный ECS превращает тип компонента в набор сущностей.

## 1 От исходного файла до работающей программы

Файл `.cpp` сам по себе не является программой. Компилятор обрабатывает каждую единицу трансляции отдельно. Упрощённо единица трансляции — это `.cpp` после текстовой подстановки всех `#include`.

Процесс состоит из четырёх стадий.

1. Препроцессор раскрывает include, условную компиляцию и макросы.
2. Компилятор проверяет типы и превращает одну единицу трансляции в объектный файл.
3. Линкер соединяет объектные файлы и библиотеки, находя определения функций и глобальных данных.
4. Загрузчик операционной системы размещает готовый модуль и его зависимости в памяти.

Отсюда происходят типичные ошибки.

- `identifier not found` обычно означает, что объявление не видно компилятору.
- `unresolved external symbol` означает, что объявление было видно, но линкер не нашёл определение.
- `already defined` означает, что одно внешнее определение попало в несколько единиц трансляции.
- Неполный тип допустим для указателя или ссылки, но недостаточен, когда компилятору нужен размер объекта или его поля.

### 1.1 Объявление и определение

Объявление сообщает форму сущности:

```cpp
class NpcPlanner;
void UpdateNpc(float deltaTime);
```

Определение создаёт функцию или полностью описывает класс:

```cpp
void UpdateNpc(float deltaTime)
{
    // Здесь существует тело функции.
}
```

Header-only системы проекта, например `InventorySystem`, помещают определения методов в `.h`. Это удобно, когда не хочется добавлять новую единицу трансляции в проект Visual Studio. Цена — увеличение времени компиляции и более сильная связанность include. Большие устойчивые реализации лучше переносить в `.cpp`, оставляя в заголовке публичный контракт.

### 1.2 `#pragma once` и include

`#pragma once` не даёт одному заголовку раскрыться дважды внутри одной единицы трансляции. Он не лечит циклический дизайн. Если `A.h` включает `B.h`, а `B.h` включает `A.h`, стоит спросить, нужны ли им полные определения или достаточно предварительного объявления.

Практическое правило движка: заголовок включает то, что необходимо его публичным полям и сигнатурам; `.cpp` включает детали реализации. Чем меньше случайных транзитивных include, тем легче понять зависимости.

## 2 Память и время жизни

У каждого объекта есть время жизни. Ошибка чаще возникает не потому, что адрес неправильный, а потому, что объект по этому адресу уже перестал существовать.

Основные области хранения:

- автоматическая память локальных переменных до выхода из блока;
- динамическая память объектов, которыми владеет контейнер или умный указатель;
- статическая память глобальных и `inline static` данных до завершения программы;
- память внешней системы, например COM-ресурса Direct3D или объекта Bullet.

### 2.1 Значение ссылка и указатель

```cpp
NpcTacticalComponent value;
NpcTacticalComponent& reference = value;
NpcTacticalComponent* pointer = &value;
```

`value` является самим объектом. `reference` — обязательное второе имя существующего объекта, которое нельзя переназначить на другой объект. `pointer` — число-адрес, которое может быть `nullptr` и может начать указывать на другой объект.

В ECS проекта `GetComponent<T>(entity)` возвращает указатель, потому что компонента у сущности может не быть:

```cpp
auto* tactical = registry.GetComponent<NpcTacticalComponent>(entity);
if (!tactical)
    return;
```

Проверка не является лишним шумом. Она формализует вариант «данных нет». После проверки `tactical->status` обращается к реальному компоненту.

### 2.2 Когда указатель из ECS опасен

Даже ненулевой указатель не вечен. Контейнер компонента может перераспределить память после добавления новых элементов. Сущность может быть уничтожена. Поэтому не стоит хранить сырой `T*` между кадрами. Надёжнее хранить `Entity`, а в момент использования снова запрашивать компонент.

Опасный шаблон:

```cpp
class SomeSystem
{
    NpcBrainComponent* cachedBrain = nullptr;
};
```

Более устойчивый шаблон:

```cpp
class SomeSystem
{
    Entity npc = INVALID_ENTITY;

    void Update(ECSRegistry& registry)
    {
        auto* brain = registry.GetComponent<NpcBrainComponent>(npc);
        if (!brain)
            return;
    }
};
```

### 2.3 `const` как контракт

`const` сообщает не только компилятору, но и читателю: функция не должна менять объект через этот доступ.

```cpp
const auto* weapon = registry.GetComponent<WeaponComponent>(weaponEntity);
```

Такой указатель позволяет читать боезапас, но не менять его. Если система только оценивает решение, это полезная граница. Решающий модуль может получить `const WorldState&`, вернуть намерение и не иметь физической возможности телепортировать NPC.

Сравни:

```cpp
NpcCoverRequestDecision EvaluateCoverRequest(
    const NpcTacticalComponent& tactical,
    const NPCComponent& npc);
```

Функция текущего `NpcTacticalDecisionSystem` читает тактическую память и здоровье, а наружу возвращает маленький результат. По сигнатуре видно, что она не меняет состояние мира.

## 3 Владение и RAII

Владение отвечает на вопрос: кто обязан освободить ресурс. RAII связывает освобождение со временем жизни C++ объекта.

`std::vector`, `std::string` и `std::unique_ptr` освобождают свои ресурсы автоматически. Поэтому контейнеры компонентов и `ShaderManager` с `std::unique_ptr<ShaderBaseClass>` безопаснее ручного `new/delete`.

### 3.1 `unique_ptr` и единственный владелец

```cpp
std::unordered_map<std::string,
    std::unique_ptr<ShaderBaseClass>> shaders;
```

У каждого шейдера один владелец — карта менеджера. При удалении элемента вызывается деструктор. Копирование запрещено, зато владение можно переместить.

```cpp
auto shader = std::make_unique<PBRShaderClass>();
shaders.emplace("PBR", std::move(shader));
```

После `std::move` переменная `shader` больше не владеет объектом. Сам объект не копируется: передаётся право его уничтожить.

### 3.2 COM ресурсы Direct3D

Текущий `ShaderBaseClass` хранит сырые COM-указатели и освобождает их в `Shutdown`. Это рабочий старый стиль DirectX 11. Он требует дисциплины: каждый успешно созданный ресурс должен быть освобождён один раз, а указатель после `Release()` надо обнулить.

Современный вариант — `Microsoft::WRL::ComPtr<T>`:

```cpp
Microsoft::WRL::ComPtr<ID3D11Buffer> matrixBuffer;
```

`ComPtr` автоматически вызывает `Release`, корректно переживает ранний `return` и упрощает обработку частично успешной инициализации. Миграцию лучше выполнять по одному классу, сохраняя поведение.

### 3.3 Внешнее владение Assimp

`AssimpModelClass` хранит `Assimp::Importer`. Возвращённый `aiScene*` принадлежит importer и действителен, пока жив importer или пока не загружена новая сцена. Нельзя освободить узлы Assimp вручную или сохранить указатель на них после `Shutdown`.

Это общий принцип адаптеров: C++ класс движка владеет внешним контекстом, а наружу копирует только стабильные данные — вершины, индексы, имена костей, ключи и текстуры.

## 4 Классы структуры и инварианты

`struct` и `class` отличаются только доступом по умолчанию. В проекте компоненты естественно оформлены как `struct`: они являются наборами данных. Системы оформлены как `class` со статическими методами: они являются поведением над данными.

Инвариант — условие, которое должно оставаться истинным после любой публичной операции. У `InventoryComponent` это, например, ограниченный индекс активного слота и отсутствие одной сущности оружия сразу в двух слотах. `InventorySystem::SanitizeSlots` восстанавливает эти условия после удаления сущностей или загрузки старых сцен.

Хороший публичный метод либо сохраняет инвариант, либо явно сообщает ошибку:

```cpp
InventoryOperation result = InventorySystem::PickupWeapon(
    registry, npc, weapon);

if (!result)
{
    // status объясняет причину отказа.
}
```

Возвращаемая структура лучше одного `bool`, потому что для AI важна причина: инвентарь полон, предмет занят другим владельцем или сущность уже уничтожена.

## 5 Шаблоны и ECS

Шаблон создаёт семейство функций или классов. Вызов `GetComponent<NpcBrainComponent>` сообщает тип во время компиляции. Registry может использовать `std::type_index` как ключ к правильному пулу компонентов.

Упрощённая идея:

```cpp
template<class T>
T* GetComponent(Entity entity)
{
    auto* pool = FindPool<T>();
    return pool ? pool->Get(entity) : nullptr;
}
```

При первом использовании `T = NpcBrainComponent` компилятор создаёт соответствующую версию функции. Ошибка типа обнаруживается до запуска.

### 5.1 `ForEach` и лямбда

```cpp
registry.ForEach<NPCCombatComponent>(
    [&](Entity npc, NPCCombatComponent& combat)
    {
        // Один вызов для каждой подходящей сущности.
    });
```

`[&]` захватывает используемые внешние переменные по ссылке. Это удобно, но широко. Для учебного и критичного кода полезно иногда перечислить захват явно:

```cpp
[&registry, deltaTime](Entity npc, NPCCombatComponent& combat)
```

Так читатель видит входы лямбды. Нельзя сохранять такую лямбду дольше объектов, захваченных по ссылке.

### 5.2 Вложенный `ForEach`

Во внешнем цикле `npcEntity` — наблюдатель. Во внутреннем цикле `candidateEntity` — проверяемая цель. Ошибка в именах быстро превращает условие самопроверки в бессмыслицу.

```cpp
registry.ForEach<NPCCombatComponent>(
    [&](Entity observerEntity, NPCCombatComponent& combat)
    {
        registry.ForEach<FactionComponent, TransformComponent>(
            [&](Entity candidateEntity,
                FactionComponent& candidateFaction,
                TransformComponent& candidateTransform)
            {
                if (candidateEntity == observerEntity)
                    return;
            });
    });
```

Здесь `return` выходит только из текущего вызова внутренней лямбды, то есть пропускает кандидата. Он не завершает всю систему.

## 6 Контейнеры и сложность

`std::vector` хранит элементы подряд. Это хорошо для обхода каждого кадра: процессор заранее подгружает соседние данные. Добавление в конец иногда вызывает перераспределение и делает старые указатели недействительными.

`std::unordered_map` даёт ожидаемый поиск за постоянное время, но элементы разбросаны по памяти и обход дороже. Она удобна для поиска по имени шейдера, кости или снимка NPC.

`std::deque` подходит журналу `NpcSimulationStudio`: добавление события в конец и удаление старого спереди не требует сдвигать весь массив.

### 6.1 Big O без мистики

- `O(1)` — число операций примерно не зависит от размера данных.
- `O(n)` — просмотр всех элементов.
- `O(n log n)` — типичная сортировка.
- `O(n²)` — каждый объект сравнивается с каждым.

Поиск целей «каждый NPC против каждого кандидата» имеет квадратичную природу. Для десятка NPC это нормально. Для сотен понадобится пространственное разбиение: uniform grid, quadtree, BVH или запрос широкофазной структуры Bullet.

Оптимизировать стоит после измерения. Сначала правильная модель знания цели, затем профилирование.

## 7 Значения перемещение и копирование

Копирование создаёт независимый объект. Перемещение передаёт внутренние ресурсы, оставляя источник в корректном, но неопределённом содержательном состоянии.

```cpp
std::string reason = BuildReason();
event.details = std::move(reason);
```

После перемещения `reason` можно уничтожить или присвоить новое значение, но нельзя рассчитывать на прежний текст.

Для маленьких `Entity`, `float` и `XMFLOAT3` копирование дёшево. Для больших `std::vector` и строк перемещение полезно. Не следует механически ставить `std::move` везде: он может запретить оптимизацию возврата значения и ухудшить читаемость.

## 8 Ошибки и способы сообщить о них

В игровом кадре исключение редко является лучшим способом обычного отказа. «У NPC нет оружия» — не авария, а состояние мира. Его лучше выразить enum или `std::optional`.

Исключение уместно на границе загрузки инструмента, если верхний слой гарантированно ловит его и сообщает путь файла. Текущий `SaveAnimationStudio` использует `try`, потому что JSON и файловая система могут выбросить исключение.

Три уровня реакции:

1. Ожидаемый отказ возвращается как статус.
2. Нарушение внутреннего предположения проверяется `assert` в debug-сборке.
3. Ошибка внешних данных записывается в лог и показывает понятный fallback.

Не стоит молча продолжать с частично корректными данными. Например, constant buffer обязан иметь размер, кратный 16 байтам. Создающая его функция должна округлить размер и проверить HRESULT.

## 9 Числа время и устойчивость

`float` не представляет большинство дробей точно. Сравнение таймера с точным нулём после серии вычитаний ненадёжно. В проекте используется насыщение:

```cpp
timer = (std::max)(0.0f, timer - (std::max)(0.0f, deltaTime));
```

После этого `timer <= 0.0f` имеет понятный смысл.

Не все величины должны использовать игровой `deltaTime`. UI может продолжать работать на паузе, а физика — выполнять фиксированный шаг. NPC Logic Studio отдельно управляет паузой, одиночным тиком и масштабом симуляционного времени. Это пример правильного разделения часов.

### 9.1 `std::isfinite`

Перед использованием внешних или накопленных данных полезно проверять `std::isfinite`. `NaN` заражает дальнейшие вычисления: любое сравнение с ним ложно, а матрица может исчезнуть с экрана без очевидной ошибки.

## 10 Матрицы и типы DirectXMath в C++

`XMFLOAT3` — удобное хранилище трёх чисел. `XMVECTOR` и `XMMATRIX` предназначены для SIMD-вычислений. Обычный путь:

```cpp
using namespace DirectX;

XMVECTOR position = XMLoadFloat3(&transform.position);
XMMATRIX world = XMMatrixRotationRollPitchYaw(
    transform.rotation.x,
    transform.rotation.y,
    transform.rotation.z) *
    XMMatrixTranslationFromVector(position);

XMFLOAT4X4 stored{};
XMStoreFloat4x4(&stored, world);
```

Важно определить соглашение умножения. Текущие HLSL-шейдеры используют строковый вектор через `mul(position, matrix)`, поэтому порядок преобразований читается слева направо: local → world → view → projection. Смешивание этого соглашения с примерами, где пишут `matrix * columnVector`, даёт визуально правдоподобные, но неправильные результаты.

## 11 Многопоточность и границы данных

Нельзя просто отправить любую систему в `JobSystem`. Параллельный код безопасен, если известны наборы чтения и записи.

Пример независимой задачи: декодировать файл текстуры во временный CPU-буфер. Пример опасной задачи: одновременно добавлять компоненты в Registry, пока основной поток его обходит.

Удобная модель:

- фоновые потоки читают неизменяемый снимок и создают результат, которым владеют сами;
- очередь главного потока принимает результат и создаёт GPU-ресурсы или компоненты;
- runtime-системы одного кадра исполняются в известном порядке, пока нет явного графа зависимостей.

Direct3D 11 immediate context и ImGui обычно принадлежат главному потоку. Физический мир Bullet тоже не следует менять параллельно без отдельного контракта синхронизации.

## 12 Производительность через данные

Главная цена кадра часто не в арифметике, а в промахах кэша, выделениях памяти и повторной работе.

Практические правила:

- не строить диагностическую строку каждый кадр, если статус не менялся;
- не искать компонент несколько раз в одной ветке, если указатель уже получен и контейнер не менялся;
- резервировать `vector`, когда примерное число элементов известно;
- сравнивать квадрат расстояния, если само расстояние не нужно;
- отделять частое обновление от редкого решения таймером;
- не выполнять полный поиск пути, если цель и навигационная ревизия не изменились.

Текущий AI уже использует часть этих идей: `decisionTimer`, `repositionCooldown`, `tacticCommitTimer`, `rejectedCoverTimer`. Таймер не просто оптимизация. Он также создаёт устойчивое поведение вместо дрожания между почти равными вариантами.

## 13 Как читать сложную функцию построчно

Не начинай с деталей. Разметь функцию пятью вопросами.

1. Какие guard clauses прекращают работу?
2. Какие данные только читаются?
3. Какие поля изменяются?
4. Где вызывается внешний мир: физика, файл, GPU, Registry?
5. Что функция обещает вызывающему коду?

Например, `InventorySystem::PickupWeapon` читается фазами:

- проверяет владельца и сущность предмета;
- убеждается, что предмет является оружием и не занят другим;
- создаёт или санирует инвентарь;
- ищет свободный слот;
- записывает отношение владения;
- синхронизирует `EquippedWeaponComponent`;
- возвращает подробный статус.

После такого скелета отдельные `if` перестают быть стеной текста.

## 15 Критерий понимания C++ в этом проекте

Знание языка проявляется не в количестве запомненных ключевых слов. Ты понимаешь код, если можешь до запуска предсказать:

- сколько живёт объект;
- кто имеет право его менять;
- что станет недействительным после добавления или удаления компонента;
- где произойдёт копирование или передача владения;
- какую ошибку увидит вызывающая сторона;
- в какой стадии кадра изменение станет видимым.

С этими вопросами даже большой класс раскладывается на проверяемые части.
