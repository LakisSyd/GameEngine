# Учебный roadmap на 7 дней: автономная космическая игра

## Итог недели

За эту неделю мы не пытаемся добавить как можно больше несвязанных механик. Цель — собрать один небольшой, но системный игровой цикл:

1. На корабле независимо от игрока возникает авария.
2. Авария изменяет реальное состояние комнаты и оборудования.
3. NPC не узнают о ней магически: они должны увидеть, услышать или получить сообщение.
4. Экипаж публикует и распределяет работы, не дублируя действия друг друга.
5. NPC самостоятельно выбирают между ремонтом, спасением, тушением и собственной безопасностью.
6. Игрок может помочь, но не способен в одиночку игнорировать вакуум, дым, травмы и нехватку ресурсов.
7. Сценарий сохраняется, воспроизводится и проверяется через debug-инструменты.

Это соответствует главному принципу игры: **игрок является участником мира, а не центром, ради которого мир притворяется живым**.

План рассчитан примерно на 3–5 часов в день. Если обязательная часть заняла больше времени, дополнительную часть переносим. Качество одной законченной системы важнее пяти недоделанных.

---

Каждый день состоит из шести частей:

- **теория** — сначала понять модель, затем писать код;
- **проектирование данных** — определить компоненты и связи;
- **теоретический код** — пример направления, а не готовая вставка;

- **проверка** — наблюдаемые условия готовности;

# День 1. Время симуляции, события и наблюдаемость мира

## Цель дня

Создать фундамент, на котором аварии и AI смогут работать независимо от FPS, камеры и присутствия игрока.

## Теория: существует три разных времени

В игровом движке нельзя использовать одно `deltaTime` для всех смыслов.

### 1. Реальное время

Это время компьютера и интерфейса. Оно подходит для:

- двойного клика;
- мигания курсора;
- измерения производительности;
- editor-анимаций, которые должны работать на паузе.

Реальное время не подходит для пожара или голода. Иначе пауза остановит интерфейс либо, наоборот, авария продолжится на паузе.

### 2. Игровое время

Это время мира после применения паузы и `timeScale`:

```text
simulationDelta = frameDelta * timeScale
```

Им пользуются:

- пожары;
- кислород;
- здоровье;
- таймеры AI;
- производство энергии;
- развитие аварий.

### 3. Фиксированное физическое время

Bullet должен обновляться одинаковыми шагами, например `1/60` секунды. Переменный шаг делает результат столкновений зависимым от FPS. Поэтому кадр на 33 мс может породить два физических шага, а кадр на 8 мс — ни одного.

```text
render frames:   |----|----|----|----|----|
physics ticks:   |------|------|------|----
simulation time: непрерывно накапливается
```

Важно: fixed update решает стабильность симуляции, но не плавность картинки. Плавность даёт визуальная интерполяция между двумя физическими состояниями.

## Теория: события не заменяют состояние

Событие сообщает: «что-то произошло». Компонент хранит: «что сейчас существует».

Пример:

- `FireStarted` — событие;
- `FireComponent{ intensity = 0.7 }` — состояние.

Если хранить пожар только событием, поздно подключившаяся система не узнает, что огонь всё ещё существует. Если хранить только компонентом, UI и AI придётся каждый кадр заново искать изменения. Поэтому нужны оба уровня.

## Проектирование данных

Создай минимальные типы в `src/Gameplay/World/`:

```cpp
struct SimulationClock
{
    double elapsedSeconds = 0.0;
    float timeScale = 1.0f;
    bool paused = false;

    float Advance(float frameDelta)
    {
        if (paused)
            return 0.0f;

        const float dt = std::clamp(frameDelta, 0.0f, 0.1f) * timeScale;
        elapsedSeconds += dt;
        return dt;
    }
};
```

Теоретическая модель события:

```cpp
enum class WorldEventType
{
    BreachCreated,
    FireStarted,
    EquipmentFailed,
    AlarmRaised,
    CharacterInjured
};

struct WorldEvent
{
    WorldEventType type{};
    Entity source = INVALID_ENTITY;
    Entity room = INVALID_ENTITY;
    DirectX::XMFLOAT3 position{};
    float strength = 0.0f;
    double simulationTime = 0.0;
};
```

Очередь событий должна иметь понятное время жизни. Простой вариант — две очереди:

```cpp
class WorldEventQueue
{
public:
    void Publish(const WorldEvent& event)
    {
        m_next.push_back(event);
    }

    std::span<const WorldEvent> Current() const
    {
        return m_current;
    }

    void EndFrame()
    {
        m_current = std::move(m_next);
        m_next.clear();
    }

private:
    std::vector<WorldEvent> m_current;
    std::vector<WorldEvent> m_next;
};
```

Две очереди защищают от зависимости порядка: событие, опубликованное одной системой, не вызывает бесконечную цепочку обработчиков в том же проходе.

## Обязательная практика

1. Создай `SimulationClock` и передавай `simulationDelta` минимум в AI и одну корабельную систему.
2. Добавь debug-панель:
   - elapsed simulation time;
   - pause;
   - time scale `0.25 / 1 / 2 / 4`;
   - кнопки `+10 sec` и `+60 sec` только для тестового режима.
3. Создай очередь `WorldEventQueue`.
4. При создании пробоины опубликуй `BreachCreated`.
5. Покажи последние 20 событий в debug UI.

## Проверка

- При паузе физика и мир не развиваются, но editor UI отвечает.
- При `timeScale = 2` игровой таймер за 10 реальных секунд проходит примерно 20 секунд.
- Одно создание пробоины даёт ровно одно событие.
- События не растут в памяти бесконечно.
- При 30 и 144 FPS результат десяти игровых секунд совпадает с разумной погрешностью.

## Что прислать мне

- файлы часов и очереди;
- место вызова систем в `ApplicationClass.cpp`;
- скриншот панели времени и событий;
- результат теста при двух FPS.

## Дополнительная задача

Добавь `simulationTick` — целочисленный номер шага. Он удобнее секунд для детерминированных тестов и сортировки событий с одинаковым временем.

# День 2. Восприятие и память NPC без всеведения

## Цель дня

NPC должен реагировать не на все компоненты мира, а только на известные ему факты.

## Теория: истина мира и знания агента — разные данные

Пожар может существовать в машинном отделении, но NPC за закрытой дверью не обязан знать об этом. Есть два слоя:

- **world state** — объективная истина симуляции;
- **agent knowledge** — неполное, устаревающее представление NPC.

Если Utility AI напрямую перебирает все `FireComponent`, NPC становится телепатом. Мир кажется построенным вокруг игрока, потому что все персонажи синхронно реагируют на события, которые физически не могли заметить.

Источники информации:

1. **Зрение** — линия видимости, угол обзора, расстояние, освещение.
2. **Слух** — событие имеет громкость, комнаты и двери ослабляют сигнал.
3. **Приборы** — датчик дыма сообщает в корабельную сеть, если есть питание.
4. **Общение** — один NPC передаёт факт другому.
5. **Память** — факт остаётся после исчезновения объекта, но его уверенность падает.

## Теория: факт должен уметь устаревать

NPC увидел огонь в точке A. Через минуту огонь мог переместиться или погаснуть. Поэтому память содержит не только Entity:

```cpp
enum class NpcFactType
{
    Fire,
    Breach,
    InjuredCharacter,
    BrokenEquipment,
    DangerousRoom
};

struct NpcFact
{
    NpcFactType type{};
    Entity subject = INVALID_ENTITY;
    Entity room = INVALID_ENTITY;
    DirectX::XMFLOAT3 lastKnownPosition{};
    double observedAt = 0.0;
    float confidence = 1.0f;
    bool confirmedBySensor = false;
};
```

Уверенность можно уменьшать экспоненциально:

```text
confidence(t) = initialConfidence * exp(-decayRate * age)
```

Экспонента удобна тем, что значение плавно приближается к нулю и не становится отрицательным.

Пример функции:

```cpp
float DecayedConfidence(const NpcFact& fact, double now)
{
    const float age = static_cast<float>(now - fact.observedAt);
    constexpr float decayRate = 0.08f;
    return fact.confidence * std::exp(-decayRate * std::max(age, 0.0f));
}
```

Факт удаляется не сразу после потери видимости, а когда уверенность стала ниже порога или Entity окончательно признана уничтоженной.

## Теория: комнаты позволяют дешёвое восприятие

Не начинай с сотни raycast на каждого NPC. В корабельной игре уже есть естественное пространственное разбиение — комнаты.

Сначала выполняется дешёвый broad phase:

- объект в той же комнате;
- объект в соседней комнате через открытую дверь;
- событие достаточно громкое.

Только затем при необходимости выполняется точный Bullet raycast. Это тот же принцип, что broad phase и narrow phase в физике.

## Обязательная практика

1. Добавь `NpcPerceptionComponent` с вектором фактов.
2. Создай `NpcPerceptionSystem`.
3. На первом этапе NPC воспринимает:
   - пробоину в своей комнате;
   - громкую аварию в соседней комнате через открытую дверь;
   - корабельную тревогу при работающей сети/питании.
4. Удали прямой доступ Utility AI хотя бы к одному глобальному типу цели. Пусть он читает эту цель только из памяти.
5. Добавь debug-панель памяти выбранного NPC:
   - тип;
   - Entity;
   - комната;
   - возраст;
   - confidence;
   - источник.

## Теоретический код обновления памяти

```cpp
void RememberFact(
    NpcPerceptionComponent& perception,
    const NpcFact& observation)
{
    auto sameSubject = [&](const NpcFact& existing)
    {
        return existing.type == observation.type &&
               existing.subject == observation.subject;
    };

    auto it = std::find_if(
        perception.facts.begin(), perception.facts.end(), sameSubject);

    if (it == perception.facts.end())
        perception.facts.push_back(observation);
    else
        *it = observation;
}
```

Для уничтоженной Entity нельзя слепо разыменовывать `subject`. Память может законно пережить объект. Сначала проверяй существование компонента, затем понижуй уверенность или помечай факт проверенным как ложный.

## Проверка

- NPC в дальней закрытой комнате не реагирует мгновенно.
- NPC рядом с пробоиной создаёт факт.
- После ухода факт остаётся, но стареет.
- После сообщения по работающей сети другой NPC тоже узнаёт об аварии.
- При отключённом питании корабельный датчик не сообщает магическую информацию.

## Что прислать мне

- компоненты восприятия;
- систему обновления;
- изменённый участок Utility AI;
- два скриншота: NPC знает / NPC не знает об одной аварии.

## Дополнительная задача

Добавь ложноположительный или устаревший факт: NPC приходит к старой позиции, проверяет её и только тогда удаляет знание. Это создаёт правдоподобное поведение без сложного машинного обучения.

# День 3. Доска работ, резервации и кооперация экипажа

## Цель дня

Отделить существование проблемы от назначения исполнителя. Несколько NPC не должны без причины бежать к одной маленькой пробоине.

## Теория: цель мира, задача и действие — не одно и то же

- Пожар — состояние мира.
- «Потушить пожар №42» — задача.
- «Подойти к шкафу за огнетушителем» — действие плана.

Если Utility AI выбирает непосредственно Entity пожара, трудно добавить резервации, количество работников, требования к инструментам и приоритет команды.

Доска работ превращает проблемы мира в явные контракты:

```cpp
enum class ShipTaskType
{
    SealBreach,
    ExtinguishFire,
    RepairEquipment,
    RescueCharacter,
    CarryResource
};

enum class ShipTaskState
{
    Open,
    Reserved,
    InProgress,
    Completed,
    Cancelled
};

struct ShipTask
{
    std::uint64_t id = 0;
    ShipTaskType type{};
    ShipTaskState state = ShipTaskState::Open;
    Entity target = INVALID_ENTITY;
    Entity room = INVALID_ENTITY;
    Entity reservedBy = INVALID_ENTITY;
    float urgency = 0.0f;
    int workerSlots = 1;
    double createdAt = 0.0;
    double reservationExpiresAt = 0.0;
};
```

## Теория: резервация — временное обещание

Резервация не должна жить вечно. NPC может умереть, застрять или получить более важный приказ. Поэтому у неё есть lease/срок:

```text
Open -> Reserved -> InProgress -> Completed
          |              |
          +---- timeout --+-> Open
```

Каждый работающий NPC продлевает lease. Если подтверждение перестало приходить, задача автоматически освобождается.

Нельзя хранить только `reservedBy` без проверки жизни Entity. Иначе удалённый NPC навсегда заблокирует работу.

## Теория: генератор задач должен быть идемпотентным

Система каждый кадр может увидеть один и тот же пожар. Она не должна создавать новую задачу каждый кадр.

Идемпотентность означает: повторный вызов с тем же смыслом не изменяет результат после первого успешного вызова.

```cpp
ShipTask* FindOrCreateTask(ShipTaskBoard& board,
                           ShipTaskType type,
                           Entity target)
{
    for (ShipTask& task : board.tasks)
    {
        if (task.type == type && task.target == target &&
            task.state != ShipTaskState::Completed &&
            task.state != ShipTaskState::Cancelled)
        {
            return &task;
        }
    }

    // Создание только если активного эквивалента нет.
    return &board.tasks.emplace_back(/* ... */);
}
```

## Обязательная практика

1. Добавь `ShipTaskBoard` и `ShipTaskSystem`.
2. Пробоина публикует или поддерживает одну задачу `SealBreach`.
3. Реализуй атомарную по логике одного игрового тика операцию `TryReserve(taskId, npc)`.
4. Utility AI выбирает только открытые задачи, о которых NPC знает.
5. Завершение ремонта переводит задачу в `Completed`.
6. Смерть, отмена команды или timeout освобождают резервацию.
7. Добавь debug-таблицу всех задач.

## Пример безопасной резервации

```cpp
bool TryReserve(ShipTask& task, Entity npc, double now)
{
    const bool leaseExpired =
        task.state == ShipTaskState::Reserved &&
        now >= task.reservationExpiresAt;

    if (leaseExpired)
    {
        task.state = ShipTaskState::Open;
        task.reservedBy = INVALID_ENTITY;
    }

    if (task.state != ShipTaskState::Open)
        return false;

    task.state = ShipTaskState::Reserved;
    task.reservedBy = npc;
    task.reservationExpiresAt = now + 3.0;
    return true;
}
```

В текущем однопоточном gameplay update это логически атомарно. Если позже выбор задач будет распараллелен, работники должны только вычислять предложения, а окончательные резервации нужно применять последовательно в главном потоке.

## Проверка

- Два NPC видят одну пробоину, но работу получает один.
- После удаления назначенного NPC задача через timeout снова открывается.
- После ремонта новая идентичная задача не появляется.
- Debug-команда имеет приоритет и корректно освобождает автоматическую работу.

## Что прислать мне

- структуру задачи;
- код создания и резервации;
- место интеграции с `NpcUtilitySystem`;
- скриншот двух NPC и одной зарезервированной задачи.

## Дополнительная задача

Добавь `workerSlots > 1` для тяжёлых задач. Не превращай это сразу в сложную командную систему: достаточно списка работников и проверки свободных слотов.

# День 4. Utility AI: выбор между пользой, риском и собственными потребностями

## Цель дня

NPC выбирает не первую найденную задачу, а наиболее разумную для конкретного персонажа в текущей ситуации.

## Теория: Utility AI не строит маршрут и не выполняет действие

Utility AI отвечает только на вопрос: **что сейчас выгоднее делать?**

Он не должен:

- двигать Transform;
- открывать двери;
- проигрывать анимацию;
- выполнять ремонт;
- самостоятельно менять физику.

После выбора он передаёт цель исполнительному уровню `StateSystem`.

## Теория: нормализация параметров

Разные величины имеют разные единицы:

- расстояние — метры;
- здоровье — проценты;
- огонь — интенсивность;
- возраст задачи — секунды.

Перед объединением их переводят в диапазон `[0, 1]`.

Примеры response curve:

```cpp
float Saturate(float value)
{
    return std::clamp(value, 0.0f, 1.0f);
}

float DistanceUtility(float distance, float usefulRange)
{
    return 1.0f - Saturate(distance / usefulRange);
}

float DangerUtility(float danger)
{
    // Квадрат делает высокий риск существенно важнее среднего.
    const float x = Saturate(danger);
    return x * x;
}
```

Теоретическая оценка задачи:

```text
score = urgency
      * knowledgeConfidence
      * distancePreference
      * skillSuitability
      * equipmentAvailability
      * personalCourage
      * survivalPermission
```

Умножение полезно для обязательных условий: если нет знания или задача смертельно опасна, итог стремится к нулю. Сложение удобно для независимых бонусов. Часто используется комбинация.

## Теория: гистерезис запрещает метание между задачами

Если задача A имеет score `0.61`, а B — `0.62`, NPC не должен каждый кадр менять решение. Нужен штраф переключения или порог улучшения:

```cpp
bool ShouldSwitch(float currentScore, float candidateScore)
{
    constexpr float requiredImprovement = 0.15f;
    return candidateScore > currentScore + requiredImprovement;
}
```

Исключение — немедленная угроза жизни. Она имеет отдельное прерывание, а не огромный случайный вес во всех формулах.

## Обязательная практика

1. Добавь минимум три consideration:
   - срочность задачи;
   - расстояние/стоимость пути;
   - опасность комнаты для конкретного NPC.
2. Добавь вторую задачу или потребность: например, `SeekSafety` при опасной атмосфере.
3. Реализуй гистерезис переключения.
4. Сохраняй breakdown оценки для debug UI.
5. Раздели выбор и применение:
   - сначала собрать кандидатов и scores;
   - затем выбрать;
   - затем зарезервировать;
   - только после успешной резервации менять state.

## Пример диагностируемого результата

```cpp
struct UtilityBreakdown
{
    float urgency = 0.0f;
    float distance = 0.0f;
    float knowledge = 0.0f;
    float safety = 0.0f;
    float finalScore = 0.0f;
};
```

Не храни только итоговый score. Когда NPC выберет странное действие, без breakdown будет невозможно понять причину.

## Проверка

- Близкий NPC предпочитает близкую работу при равной срочности.
- Тяжело раненый NPC не идёт в смертельную комнату без особой причины.
- Score в debug UI объясняет выбор.
- Значения около границы не заставляют NPC менять задачу каждый кадр.
- Ручная debug-команда по-прежнему сильнее автоматического выбора.

## Что прислать мне

- формулу и response curves;
- два разных набора score для одной ситуации;
- видео или лог, где NPC сохраняет решение при малом изменении scores.

## Дополнительная задача

Добавь индивидуальность через параметры, а не отдельные `if`:

```cpp
struct NpcPersonalityComponent
{
    float courage = 0.5f;
    float selfPreservation = 0.5f;
    float discipline = 0.5f;
};
```

Одинаковая авария тогда создаёт разные решения без случайных сценариев.

# День 5. Системная авария: пожар, атмосфера, питание и каскадные последствия

## Цель дня

Добавить одну опасность, которая связана с существующими системами и может развиваться без игрока.

## Теория: хорошая механика изменяет несколько других систем

Отдельная красивая частица огня — эффект, но ещё не gameplay-система. Системный пожар:

- расходует кислород;
- выделяет дым и тепло;
- повреждает оборудование;
- создаёт события восприятия;
- повышает срочность задач;
- может погаснуть сам без кислорода;
- меняет доступность маршрута;
- вынуждает игрока и NPC принимать решения.

## Проектирование состояния

```cpp
struct FireComponent
{
    Entity room = INVALID_ENTITY;
    float intensity = 0.15f;
    float fuel = 1.0f;
    float heat = 0.0f;
    float spreadTimer = 0.0f;
};
```

Простейшая модель изменения:

```text
oxygenFactor = saturate((oxygen - minimumOxygen) / oxygenRange)
growth       = growthRate * fuel * oxygenFactor
suppression  = naturalDecay + extinguisherEffect
intensity   += (growth - suppression) * dt
fuel        -= burnRate * intensity * dt
oxygen      -= oxygenUse * intensity * dt
```

Нужно ограничивать значения и явно обрабатывать конец жизни:

```cpp
fire.intensity = std::clamp(fire.intensity, 0.0f, 1.0f);
fire.fuel = std::max(0.0f, fire.fuel);

if (fire.intensity <= 0.001f || fire.fuel <= 0.0f)
    QueueDestroyFire(entity);
```

Не удаляй Entity во время обхода пула, если ECS этого явно не поддерживает. Сначала собери список удаления, затем примени изменения.

## Теория: каскад не должен быть мгновенным

Если огонь за один кадр отключает генератор, убивает NPC и сжигает комнату, игрок не получает решений. Системной игре нужны времена реакции:

- заметить;
- оценить;
- подготовиться;
- вмешаться;
- увидеть последствия.

Балансируй не только силу, но и скорость процессов. Хорошая авария сначала создаёт предупреждающие сигналы, затем ухудшается.

## Обязательная практика

1. Создай `FireComponent` и `FireSystem`.
2. Добавь debug-кнопку создания пожара в выбранной комнате.
3. Свяжи интенсивность с кислородом комнаты.
4. Наноси постепенный урон хотя бы одному ближайшему оборудованию.
5. Публикуй события `FireStarted`, `FireGrowing`, `FireExtinguished` без спама каждый кадр.
6. Создавай задачу `ExtinguishFire`.
7. Подключи существующие частицы как визуальное отражение intensity.

## Проверка

- В нормальной атмосфере огонь растёт медленно.
- Без кислорода он затухает.
- Огонь существует и развивается, даже когда игрок в другой комнате.
- Отключённое огнём оборудование влияет на корабль обычным компонентом повреждения.
- После тушения задача закрывается и частицы исчезают.

## Что прислать мне

- формулу пожара и выбранные коэффициенты;
- граф или таблицу intensity за 60 секунд;
- видео развития без участия игрока;
- список систем, которые читают или изменяют пожар.

## Дополнительная задача

Добавь распространение только через понятные связи: соседняя воспламеняемая Entity или открытая дверь. Не используй случайный глобальный поиск точки — игрок должен иметь возможность предсказать риск.

# День 6. Игрок не супергерой: физиология, экипировка и цена решения

## Цель дня

Сделать опасности значимыми для игрока теми же правилами, которые действуют на NPC.

## Теория: урон — это последний этап воздействия

Если любая опасность просто уменьшает HP, разные ситуации ощущаются одинаково. Лучше разделить:

1. **экспозицию** — персонаж находится в дыме, вакууме, жаре;
2. **накопление** — растёт доза дыма, кислородный долг, температура;
3. **симптомы** — падает выносливость, ухудшается управление;
4. **травма** — возникает устойчивое состояние;
5. **урон/смерть** — крайнее последствие.

## Проектирование данных

```cpp
struct CharacterVitalsComponent
{
    float health = 100.0f;
    float bloodOxygen = 1.0f;
    float smokeDose = 0.0f;
    float bodyTemperature = 37.0f;
    float pain = 0.0f;
};

struct ProtectiveEquipmentComponent
{
    bool sealedSuit = false;
    float suitOxygen = 0.0f;
    float smokeProtection = 0.0f;
    float heatProtection = 0.0f;
};
```

Защита не должна быть бинарным бессмертием. Скафандр:

- имеет запас кислорода;
- может быть повреждён;
- ограничивает подвижность;
- требует времени на надевание;
- защищает от одного класса угроз, но не обязательно от всех.

## Теория: единые правила для Player и NPC

Если `PlayerVitalsSystem` работает только с `PlayerGameTag`, NPC живут в другом мире. Лучше создать общий `CharacterVitalsSystem`, а UI игрока лишь отображает его компонент.

```cpp
registry.ForEach<CharacterVitalsComponent, TransformComponent>(
    [&](Entity entity, CharacterVitalsComponent& vitals,
        TransformComponent& transform)
    {
        const RoomEnvironment environment =
            QueryEnvironmentAt(transform.position);
        ApplyBreathing(vitals, environment, dt);
        ApplyHeat(vitals, environment, dt);
    });
```

NPC Utility AI читает те же vitals и выбирает безопасность. Игрок получает управление и HUD, но не особые физические законы.

## Обязательная практика

1. Создай общий `CharacterVitalsComponent` для игрока и NPC.
2. Свяжи дыхание с атмосферой текущей комнаты.
3. Добавь минимум два промежуточных последствия до прямого урона:
   - восстановление stamina медленнее;
   - снижение скорости или точности;
   - кашель/визуальный эффект;
   - рост риска потери сознания.
4. Добавь один ограниченный защитный ресурс: фильтр, баллон или medkit.
5. Покажи состояние в HUD и debug UI.
6. Научи Utility AI учитывать собственную безопасность.

## Проверка

- Игрок не может бесконечно находиться в вакууме.
- NPC получает те же последствия.
- Выход в безопасную комнату постепенно восстанавливает обратимые показатели.
- Тяжёлая травма не исчезает мгновенно.
- Защитный ресурс заканчивается и имеет понятный расход.

## Что прислать мне

- компоненты vitals/equipment;
- формулы изменения;
- сценарий «без защиты / с защитой»;
- скриншот HUD в опасной комнате.

## Дополнительная задача

Добавь потерю сознания как состояние, а не мгновенную смерть. Это создаёт задачу спасения для экипажа и новые истории без искусственного квестового скрипта.

# День 7. Вертикальный срез, сохранение, тестирование и баланс

## Цель дня

Соединить системы в воспроизводимый десятиминутный сценарий и убрать архитектурные долги недели.

## Теория: вертикальный срез проверяет связи, а не количество контента

Вертикальный срез — маленький фрагмент игры, проходящий через все важные уровни:

```text
авария -> среда -> восприятие -> задача -> решение AI
       -> навигация -> действие -> последствия -> UI/save
```

Если один уровень отсутствует, механика выглядит постановочной. Например, красивый пожар без восприятия NPC не проверяет обещание живого мира.

## Теория: сохранение — часть архитектуры компонента

Для каждого нового компонента ответь:

- нужно ли сохранять его между запусками;
- какие поля являются постоянным состоянием;
- какие поля являются runtime-кешем;
- содержит ли он `Entity`-ссылки;
- как ссылки remap после загрузки;
- что делать, если целевая Entity отсутствует.

Обычно не сохраняются:

- указатели Bullet;
- указатели ресурсов;
- кеш NavMesh-пути;
- временные debug-значения;
- вычислимые response scores.

Обычно сохраняются:

- фактическое состояние пожара;
- vitals;
- постоянные черты NPC;
- задачи, если они отражают незавершённую работу;
- память NPC, если мир должен продолжаться после загрузки.

## Теория: тестируй инварианты

Инвариант — условие, которое должно быть истинным всегда.

Примеры:

- завершённая задача не имеет активной резервации;
- удалённая Entity не разыменовывается из памяти NPC;
- intensity пожара находится в `[0, 1]`;
- здоровье не выше максимального и не ниже нуля;
- одна пробоина создаёт не более одной активной задачи ремонта;
- пауза не изменяет игровое состояние;
- FPS не меняет скорость симуляции.

Debug assertion полезнее случайного симптома через десять минут:

```cpp
assert(task.state != ShipTaskState::Completed ||
       task.reservedBy == INVALID_ENTITY);
```

## Обязательная практика

1. Создай тестовую сцену `AutonomousShipLab`:
   - 3 комнаты;
   - 2 двери;
   - генератор и один потребитель;
   - датчик тревоги;
   - 2 NPC с разными параметрами;
   - шкаф с ограниченным средством защиты/тушения.
2. Создай debug-сценарий:
   - пожар или пробоина появляется в комнате без игрока;
   - ближайший NPC узнаёт первым;
   - второй узнаёт через сообщение;
   - работа резервируется;
   - опасность меняет среду;
   - игрок может помочь либо ничего не делать.
3. Добавь save/load новых постоянных компонентов и remap Entity.
4. Проверь сценарий при 30, 60 и 120+ FPS.
5. Проверь паузу и ускорение времени.
6. Оставь debug overlay, который показывает всю причинную цепочку.

## Матрица обязательных тестов

| Тест | Начальные условия | Ожидаемый результат |
|---|---|---|
| Игрок отсутствует | Игрок в дальней комнате | Авария и NPC продолжают работать |
| Нет информации | Дверь закрыта, сеть выключена | Дальний NPC ничего не знает |
| Есть сообщение | Сеть получает питание | Дальний NPC создаёт факт |
| Конкуренция | Два NPC, одна работа | Только один резервирует задачу |
| Исполнитель потерян | Назначенный NPC удалён | Lease истекает, задача открывается |
| Нет кислорода | Пожар в пустой атмосфере | Огонь затухает |
| Игрок без защиты | Опасная атмосфера | Появляются симптомы и урон |
| Save/load | Авария в середине развития | После загрузки состояние продолжается |
| Разный FPS | Одинаковый seed и игровое время | Результат близок |

## Баланс через время принятия решений

Не начинай баланс с точного урона оружия. Сначала измерь:

- сколько секунд есть до обнаружения;
- сколько занимает путь NPC;
- сколько длится подготовка инструмента;
- через сколько авария становится необратимой;
- какое решение игрок успевает принять;
- что произойдёт без участия игрока.

Хорошая начальная авария имеет несколько фаз:

1. **сигнал** — звук, датчик, сообщение;
2. **локальная проблема** — её можно решить одним работником;
3. **распространение** — появляются конкурирующие задачи;
4. **кризис** — приходится чем-то пожертвовать;
5. **последствия** — мир помнит результат.

## Проверка

- Сценарий работает от начала до конца без ручного переставления Entity в редакторе.
- NPC могут закончить его без игрока, но исход зависит от ресурсов и условий.
- Игрок полезен, однако не является обязательным триггером мира.
- Debug-инструменты объясняют каждое решение.
- Сохранение не оставляет битых ссылок.
- Debug x64 собирается без ошибок.

## Что прислать мне

- сцену и изменённые файлы;
- видео полного сценария;
- матрицу тестов с фактическими результатами;
- один save-файл в середине аварии;
- список технического долга на следующую неделю.

## Дополнительная задача

Добавь seed для генератора аварий. С одинаковым seed и одинаковыми действиями последовательность событий должна быть воспроизводимой. Это сильно упрощает поиск редких ошибок системного gameplay.

# Архитектурная памятка на всю неделю

## Правильное направление зависимостей

```text
World state
   ↓ создаёт события
Perception
   ↓ создаёт знания
Task Board
   ↓ предоставляет кандидатов
Utility AI
   ↓ выбирает намерение
StateSystem
   ↓ строит последовательность действий
Navigation / CharacterMovement
   ↓ передаёт физическое намерение
Bullet controller
   ↓ выдаёт фактическую позицию
Animation / UI / Debug
```

Нижний слой не должен принимать решения верхнего. Например, Bullet-контроллер не должен решать, стоит ли NPC тушить пожар, а частица огня не должна напрямую назначать работника.

## Компонент или система?

Используй компонент, если это данные конкретной Entity:

- здоровье;
- интенсивность огня;
- память NPC;
- запас кислорода.

Используй систему, если это правило обработки набора Entity:

- уменьшение кислорода;
- выбор задачи;
- старение памяти;
- применение урона.

Используй сервис/ресурс мира, если данные глобальны и не принадлежат одной Entity:

- часы симуляции;
- очередь событий;
- доска задач корабля;
- seed генератора сценария.

## Запрещённые короткие пути

- Не проверяй `PlayerGameTag` внутри закона атмосферы.
- Не двигай NPC изменением `Transform.position` в AI.
- Не ищи все опасности мира напрямую из Utility AI.
- Не создавай одну и ту же задачу каждый кадр.
- Не храни необработанные указатели на ECS-компоненты между кадрами.
- Не удаляй Entity во время небезопасного обхода component pool.
- Не используй реальное время для gameplay timeout.
- Не исправляй визуальное дрожание отключением всей физики или гравитации.
- Не скрывай причины решений: debug breakdown является частью AI-системы.

## Definition of Done для любой новой системы

Система считается законченной только когда:

1. её данные имеют понятного владельца;
2. определён порядок update;
3. значения ограничены и проверены на NaN;
4. обработано удаление связанных Entity;
5. нет зависимости от FPS;
6. есть debug-представление;
7. есть минимальная тестовая сцена;
8. сохранение обновлено либо явно объяснено, почему оно не требуется;
9. Debug x64 собирается;
10. результат можно воспроизвести по короткой инструкции.

# Формат нашей совместной проверки

После каждого дня напиши в следующем сообщении:

```text
День N завершён.

Изменённые файлы:
- ...

Как запустить проверку:
1. ...
2. ...

Ожидаемое поведение:
- ...

Известные проблемы:
- ...
```

Я проверю код и сначала дам:

1. ошибки, способные сломать игру или данные;
2. архитектурные проблемы;
3. проблемы поведения и баланса;
4. понятные исправления;
5. только после этого — следующую задачу.

Не нужно ждать идеального кода, чтобы показать результат. Но код должен собираться, а известные проблемы должны быть записаны честно. Такая итерация намного быстрее ведёт к сильной игре, чем неделя скрытой разработки большой системы без промежуточной проверки.
