# Графический конвейер и HLSL от данных до пикселя

Шейдер не рисует модель в одиночку. Он является одной программируемой стадией большого контракта между CPU, Direct3D, видеодрайвером и GPU. Чтобы уверенно писать HLSL, надо одновременно понимать форму вершины в C++, input layout, регистры ресурсов, пространства координат и математический смысл результата.

## 1 Что происходит при отрисовке одного меша

Упрощённая последовательность Direct3D 11:

1. CPU выбирает меш, материал, шейдер и состояние конвейера.
2. В Input Assembler привязываются vertex buffer, index buffer и input layout.
3. Vertex Shader вызывается для каждой используемой вершины.
4. Rasterizer собирает треугольники, отсекает невидимые стороны и определяет покрытые пиксели.
5. Значения между вершинами интерполируются.
6. Pixel Shader вычисляет цвет каждого фрагмента.
7. Output Merger применяет depth test, stencil и blending и пишет итог в render target.

На GPU одновременно обрабатывается множество вершин и пикселей. У шейдера нет привычного доступа к Registry, файлам или соседнему пикселю. Входные данные должны быть заранее привязаны CPU-кодом.

## 2 Input Assembler и соглашение о вершине

Текущий `AssimpModelClass::VertexType` хранит:

- позицию;
- UV;
- нормаль;
- tangent и binormal;
- четыре индекса костей;
- четыре веса.

HLSL-структура должна описывать тот же поток семантиками:

```hlsl
struct VertexInputType
{
    float3 position  : POSITION;
    float2 tex       : TEXCOORD0;
    float3 normal    : NORMAL;
    float3 tangent   : TANGENT;
    float3 binormal  : BINORMAL;
    int4   boneIDs   : BLENDINDICES;
    float4 weights   : BLENDWEIGHT;
};
```

Семантика — имя канала, а не имя C++ поля. Input layout говорит Direct3D, в каком формате, смещении и слоте лежит каждая семантика. Если C++ добавил поле, но layout и HLSL не обновлены согласованно, GPU будет читать соседние байты под неверным смыслом.

Полезная проверка перед запуском:

- число компонентов совпадает;
- формат совпадает со знаком и разрядностью;
- byte offset соответствует реальной структуре;
- семантический индекс совпадает;
- stride равен размеру вершины;
- целочисленные bone ID не объявлены как нормализованный цвет.

## 3 Vertex Shader и пространства координат

Позиция модели проходит несколько пространств.

- Model space: координаты, экспортированные из редактора модели.
- World space: положение объекта в сцене.
- View space: мир относительно камеры.
- Clip space: координаты после projection, необходимые rasterizer.

В текущем соглашении используется строковый вектор:

```hlsl
float4 worldPosition = mul(float4(input.position, 1.0f), worldMatrix);
float4 viewPosition = mul(worldPosition, viewMatrix);
output.position = mul(viewPosition, projectionMatrix);
```

Читать надо слева направо. Сначала локальная точка становится мировой, затем камерной, затем clip-space.

### 3.1 Почему `w` равен 1 для точки и 0 для направления

Однородная координата позволяет матрице содержать перенос. У точки `w = 1`, поэтому строка переноса участвует. У направления `w = 0`, поэтому перенос не меняет нормаль или скорость.

```hlsl
float3 worldNormal = mul(float4(input.normal, 0.0f), worldMatrix).xyz;
```

Но эта упрощённая формула корректна только без неравномерного масштаба. В общем случае нормаль преобразуется обратной транспонированной матрицей верхнего блока world matrix. Если проект разрешит разный scale по осям у освещаемых моделей, стоит передавать normal matrix отдельно или запрещать такой scale контрактом.

### 3.2 Clip space и деление на W

Vertex Shader возвращает `SV_POSITION`. После него GPU делит x, y и z на w и получает normalized device coordinates. Perspective projection делает дальние предметы меньше именно благодаря зависимости w от глубины.

Не надо выполнять perspective divide вручную в обычном VS. Rasterizer должен получить clip-space позицию, чтобы правильно отсекать треугольники у границ камеры.

## 4 Интерполяция между вершинами

Pixel Shader не вызывается только в трёх вершинах. Rasterizer создаёт фрагменты внутри треугольника и интерполирует выходы VS.

Если в вершинах UV равны `(0,0)`, `(1,0)` и `(0,1)`, каждый фрагмент получит промежуточное значение. То же происходит с мировой позицией, нормалью и fog factor.

Целочисленные или дискретные данные нельзя интерполировать как обычный `float`. Для них применяется модификатор `nointerpolation` или иной способ передачи.

## 5 Pixel Shader и текстура

Минимальный пиксельный шейдер:

```hlsl
Texture2D albedoTexture : register(t0);
SamplerState linearSampler : register(s0);

float4 main(PixelInputType input) : SV_TARGET
{
    return albedoTexture.Sample(linearSampler, input.tex);
}
```

`Texture2D` хранит данные. `SamplerState` описывает, как вычислять значение между texel, что делать за границей UV и какие mip levels использовать. Один sampler может применяться к нескольким текстурам.

`register(t0)` — не выделение памяти. Это соглашение о слоте. CPU обязан вызвать `PSSetShaderResources` с тем же номером.

## 6 Constant buffer и правило 16 байт

Constant buffer обновляется CPU и читается многими shader invocation. Его поля упаковываются по 16-байтовым регистрам. Ошибка выравнивания часто даёт не crash, а бессмысленные числа.

```hlsl
cbuffer PbrParameters : register(b6)
{
    float metallic;
    float roughness;
    float2 padding;
};
```

Соответствующая C++ структура должна повторять порядок и размер:

```cpp
struct PbrParametersBuffer
{
    float metallic;
    float roughness;
    DirectX::XMFLOAT2 padding;
};

static_assert(sizeof(PbrParametersBuffer) % 16 == 0);
```

Текущий `ShaderBaseClass::CreateConstantBuffer` округляет `ByteWidth` до кратного 16. Это защищает размер ресурса, но не исправляет неправильное расположение полей внутри структуры. Поэтому `static_assert`, явные padding-поля и единый заголовок контрактов всё равно нужны.

### 6.1 Обновление буфера

CPU обычно:

1. формирует C++ структуру;
2. отображает dynamic buffer через `Map`;
3. копирует данные;
4. вызывает `Unmap`;
5. привязывает буфер к VS или PS слоту.

Нельзя менять один общий dynamic buffer для сотен объектов заранее, а потом ожидать, что каждый draw запомнит свою версию. Данные должны обновляться перед соответствующим draw либо находиться в отдельном ресурсе.

## 7 Регистры текущего PBR шейдера

В текущем `pbr.ps` текстуры распределены так:

- `t0` albedo;
- `t1` normal map;
- `t2` metalness;
- `t3` roughness;
- `t6` cracks или damage mask;
- `t7` shadow map;
- `t8` environment map.

Используются обычный sampler `s0` и comparison sampler `s7` для теней. Буферы занимают, среди прочего, `b0`, `b1`, `b3`, `b4`, `b5`, `b6`, `b7`, `b9`; fog включается отдельным общим контрактом.

Такое ручное распределение работает, но с ростом числа эффектов становится источником коллизий. Следующий инженерный шаг — единая таблица shader bindings:

```cpp
namespace ShaderSlots
{
    constexpr unsigned Albedo = 0;
    constexpr unsigned Normal = 1;
    constexpr unsigned Shadow = 7;
    constexpr unsigned BonePalette = 8;
}
```

HLSL не умеет напрямую включить C++ namespace, но номера можно генерировать из одного описания или хотя бы проверять shader reflection при загрузке.

## 8 Нормали tangent space и normal map

Normal map хранит направление поверхности в касательном пространстве. Обычно RGB из диапазона `[0,1]` преобразуется в `[-1,1]`:

```hlsl
float3 sampled = normalTexture.Sample(sampler0, uv).xyz;
float3 tangentNormal = normalize(sampled * 2.0f - 1.0f);
```

Чтобы вернуть его в world space, нужен базис TBN:

- T — tangent, направление роста U;
- B — bitangent или binormal, направление роста V;
- N — геометрическая нормаль.

```hlsl
float3x3 tbn = float3x3(T, B, N);
float3 worldNormal = normalize(mul(tangentNormal, tbn));
```

Знак и порядок зависят от соглашения матриц и от того, как Assimp преобразовал систему координат. Если normal map выглядит вывернутой, надо проверить не только текстуру, но и handedness, направление green channel и построение binormal.

## 9 Освещение от Lambert до PBR

Диффузный Lambert использует косинус угла между нормалью N и направлением к свету L:

```text
diffuse = albedo * max(dot(N, L), 0)
```

PBR не означает «реальная физика полностью». Это набор приближений, которые устойчиво связывают свойства материала, свет и камеру.

Текущий шейдер использует Cook–Torrance microfacet BRDF. Зеркальная часть имеет форму:

```text
specular = D * F * G / max(4 * dot(N,V) * dot(N,L), epsilon)
```

Здесь:

- D описывает распределение микрограней, в текущем коде GGX;
- F — Fresnel, приближение Schlick;
- G — геометрическое затенение Smith;
- V — направление к камере;
- L — направление к свету;
- H — нормализованная полусумма V и L.

### 9.1 Roughness

Малый roughness создаёт узкий яркий блик. Большой roughness распределяет отражение по широкой области. Roughness нельзя бездумно доводить до нуля: формулы содержат деления и степени. Шейдер должен clamp значение до малого положительного порога.

### 9.2 Metalness

У диэлектрика базовый Fresnel около 0.04, а основная энергия находится в diffuse. У металла отражение окрашивается albedo, а diffuse почти исчезает. Metalness обычно смешивает два случая, а не является произвольным коэффициентом блеска.

### 9.3 Сохранение энергии

Если отражённая зеркальная доля велика, диффузная должна уменьшиться. Иначе материал создаёт дополнительный свет. Упрощённо:

```text
kS = Fresnel
kD = (1 - kS) * (1 - metallic)
```

## 10 Безопасная математика шейдера

GPU легко производит `NaN` и бесконечность. Визуально это может проявляться чёрными вспышками, цветными точками или исчезающим объектом.

Нужны защитные операции:

- нормализовать только вектор ненулевой длины;
- ограничивать знаменатель `max(value, epsilon)`;
- clamp аргумент `pow` и результат выборки;
- не доверять альфе и normal map без диапазона;
- очищать нечисловой цвет перед записью.

Текущий `pbr.ps` уже содержит `SafeNormalize`, `SafePow` и очистку цвета. Это не косметика, а часть контракта стабильного renderer.

## 11 Скиннинг на GPU

Скиннинг деформирует вершину взвешенной суммой bone transforms.

```text
skinnedPosition = Σ weight[i] * transform[boneID[i]] * position
```

Текущий `pbr.vs` поддерживает до четырёх влияний и палитру до 128 костей в `b8`. Для каждого влияния он проверяет диапазон индекса и положительный вес, затем нормализует сумму весов.

Очень важен static fallback. Если вершина не имеет валидных костей, она должна использовать исходную позицию и нормаль. Нельзя читать старое содержимое `b8`: предыдущий анимированный draw мог оставить там любые матрицы.

### 11.1 Почему нормаль тоже скинится

Если меняется положение вершины, направление поверхности должно следовать за костью. Нормаль скинится матрицами без переноса. Tangent и binormal тоже должны следовать деформации, иначе normal map «отлипнет» от анимации.

## 12 Тени

Shadow mapping рендерит сцену из позиции света в текстуру глубины. При основном проходе мировая позиция проецируется в light clip space, и текущая глубина сравнивается с сохранённой.

Основные проблемы:

- shadow acne из-за ограниченной точности и самосравнения;
- peter panning из-за слишком большого bias;
- ступенчатые края;
- неправильная проекция координат за границами карты.

Текущий PBR шейдер использует небольшую 2×2 PCF-фильтрацию. Несколько сравнений вокруг UV усредняют жёсткую границу. Bias должен зависеть от масштаба сцены и угла поверхности, а не быть случайно большим числом.

## 13 Прозрачность и порядок отрисовки

Alpha blending не решается только строкой в pixel shader. Нужно:

- включить соответствующий blend state;
- решить, пишет ли объект глубину;
- обычно отсортировать прозрачные объекты от дальних к ближним;
- различать alpha test и полупрозрачность.

Alpha test отбрасывает пиксель полностью и хорошо подходит листьям или решёткам. Полупрозрачное стекло смешивает цвет и требует порядка. `AssimpModelClass::MeshPart` уже хранит признаки прозрачности, стекла и opacity, поэтому renderer должен выбирать проход на основании материала.

## 14 Fog как отдельный общий контракт

Fog factor можно вычислять по глубине в VS и интерполировать либо вычислять в PS по мировой/камерной позиции. Текущий `ShaderBaseClass` поддерживает fog buffer в `b2`.

Преимущество общего слота — разные материалы получают одинаковую атмосферу. Риск — новый шейдер случайно займёт `b2` другим буфером. Поэтому общие слоты должны быть документированы централизованно.

## 15 Что делает текущий ShaderBaseClass

`ShaderBaseClass` является инфраструктурным базовым классом. Его обязанности:

- скомпилировать VS или PS из файла через `D3DCompileFromFile`;
- вывести ошибки компиляции в `shader-error.txt`;
- создать input layout;
- создать sampler;
- создать выровненный constant buffer;
- привязать shader objects и layout к context;
- обновить общий fog buffer;
- освободить COM-ресурсы в `Shutdown`.

Логический путь `CompileShader`:

1. получает путь, entry point и shader model;
2. включает строгую компиляцию и debug-флаги в отладочной сборке;
3. вызывает compiler с обычным include handler;
4. если есть error blob, записывает его текст;
5. возвращает bytecode вызывающему классу;
6. вызывающий создаёт `ID3D11VertexShader` или `ID3D11PixelShader`.

Bytecode VS нужен также для создания input layout: драйвер проверяет, что layout согласован с входной сигнатурой.

## 16 ShaderManager

Текущий `ShaderManager` — singleton с картой `name → unique_ptr<ShaderBaseClass>`. Он умеет загружать конкретный тип шаблонным `Load<T>`, возвращать базовый или типизированный указатель, перечислять имена и освобождать набор.

Плюсы:

- один экземпляр каждого именованного шейдера;
- явное владение;
- редактор может перечислять доступные имена;
- материал хранит лёгкую ссылку по имени или типу.

Ограничения:

- singleton скрывает зависимость от глобального состояния;
- строковое имя допускает опечатку только во время запуска;
- загрузка и hot reload требуют аккуратно сохранить старый рабочий shader при ошибке новой компиляции;
- часть комментариев исходника сейчас имеет повреждённую кодировку. Исходники стоит сохранить в UTF-8, потому что нечитаемые комментарии разрушают документацию, даже если бинарное поведение не меняется.

## 17 Как добавить новый шейдер в этот движок

Рассмотрим эффект подсветки выбранного объекта.

### Шаг 1 Сформулировать входы

Нужно решить, использует ли эффект существующую геометрию, требует ли normal, какие текстуры читает и какие параметры меняются на объект или на кадр.

Пример параметров:

```cpp
struct SelectionBuffer
{
    DirectX::XMFLOAT4 color;
    float intensity;
    DirectX::XMFLOAT3 padding;
};
```

### Шаг 2 Зарезервировать слоты

Проверить все include и текущие PBR bindings. Выбрать свободный `b` слот либо добавить поле в существующий буфер, если жизненный цикл совпадает. Нельзя занимать номер только потому, что он свободен в одном файле.

### Шаг 3 Написать HLSL

Сначала сделать минимальный shader, возвращающий постоянный цвет. Затем добавить world position, маску и освещение. Один новый фактор за раз облегчает диагностику.

### Шаг 4 Создать C++ класс

Наследник `ShaderBaseClass` создаёт shader objects, input layout и собственные buffers. `Render` или метод параметров обновляет ресурсы перед draw.

### Шаг 5 Зарегистрировать

Добавить загрузку в `ShaderManager` при инициализации renderer. Не забыть понятное имя, обработку ошибки и `Shutdown`.

### Шаг 6 Подключить материал или проход

Renderer должен реально выбрать новый класс и вызвать обновление параметров. Наличие HLSL на диске ничего не меняет.

### Шаг 7 Добавить диагностику

В редакторе показать активное имя шейдера, доступные слоты и последнюю ошибку компиляции. Для hot reload сначала компилировать во временный объект; заменять рабочий shader только после полного успеха.

### Шаг 8 Проверить эталонную сцену

Проверки: объект перед камерой, сзади, в тени, с отрицательным scale, со skinned mesh, без текстуры и с несколькими источниками света.

## 18 Shader reflection как следующий шаг

Direct3D shader reflection может прочитать из bytecode:

- имена и слоты constant buffers;
- размеры и поля;
- texture и sampler bindings;
- входную сигнатуру;
- число инструкций и параметры shader model.

Это позволяет валидировать контракт CPU/GPU при загрузке и вывести понятную ошибку вроде «PbrParameters ожидает 32 байта, C++ передаёт 28». Reflection не заменяет архитектуру, но превращает молчаливое искажение в диагностируемый отказ.

## 19 Compute shader и когда он нужен

Compute Shader исполняет общие группы потоков без rasterizer. Он полезен для частиц, постобработки, culling, генерации данных и некоторых симуляций.

Он не является автоматически быстрее CPU. Нужно учитывать передачу данных, синхронизацию ресурсов и характер задачи. Для небольшого числа NPC utility AI на CPU проще и дешевле. Для миллионов независимых частиц GPU естественнее.

## 20 Отладка шейдера

Надёжная последовательность:

1. Убедиться, что shader скомпилирован и действительно привязан.
2. Вернуть постоянный яркий цвет.
3. Показать UV как `float4(uv, 0, 1)`.
4. Показать normal как `normal * 0.5 + 0.5`.
5. По одному включать texture, light и shadow.
6. Проверить CPU buffer и слот.
7. Захватить кадр RenderDoc или Graphics Diagnostics.

Цветовые диагностические режимы полезнее случайного изменения формулы. Они превращают скрытые векторы в видимые данные.

## 21 Практические задания

### Задание 1 Контракт вершины

Найди `VertexType`, input layout PBR-класса и `VertexInputType` в HLSL. Составь таблицу смещений и форматов. Объясни, какое поле сломается первым, если забыть bone IDs.

### Задание 2 Пространства

## 22 Критерий понимания шейдера

Ты готов уверенно менять HLSL, если можешь для любого поля ответить:

- кто создал это значение;
- в каком пространстве оно находится;
- какой C++ код привязал ресурс;
- какой регистр используется;
- интерполируется ли значение;
- что увидит экран при неверном значении;
- каким одноцветным debug-режимом проверить гипотезу.

Тогда шейдер перестаёт быть магией и становится обычной программой с очень строгим вводом и массовым параллельным исполнением.
