# Частицы, взрывы и декомпрессия: технический срез

Этот документ описывает добавленные системы так, чтобы их можно было дальше
развивать самостоятельно. Здесь разобраны обязанности классов, поток данных,
главные формулы и примеры расширения.

## 1. Карта файлов

### Частицы

- `src/Gameplay/Effects/ParticleSystem.h` - публичный API и структуры данных.
- `src/Gameplay/Effects/ParticleSystem.cpp` - CPU-симуляция и готовые пресеты.
- `src/Gameplay/Effects/ParticleRenderer.h` - интерфейс DirectX-рендера.
- `src/Gameplay/Effects/ParticleRenderer.cpp` - billboard-геометрия и GPU-состояния.

## 2. Общая схема

```text
Игровое событие
    |
    +--> ParticleSystem --------> ParticleRenderItem[]
    |         |                         |
    |         | CPU Update              | Renderer
    |         v                         v
    |    позиция/скорость         ParticleRenderer --> DirectX 11
    |
    +--> ExplosionSystem --> Bullet RigidBody impulses
    |
    +--> HullBreachComponent
              |
              v
       RoomEnvironmentSystem
          |       |       |
       oxygen  pressure  temperature
                          |
                          v
             CharacterExternalVelocitySystem
                          |
                          v
               CharacterControllerSystem
```

Главная идея: игровая логика не должна знать детали DirectX. `ParticleSystem`
симулирует частицы, а `ParticleRenderer` только рисует готовый список.

## 3. Универсальный ParticleSystem

### 3.1. Типы эффекта

`ParticleEffectType` содержит готовые крупные пресеты:

- `Fire` - постоянное пламя;
- `Smoke` - постоянный дым;
- `Explosion` - одноразовый многослойный эффект.

Это удобные точки входа. Внутри все они всё равно используют один
`ParticleEmitterDesc`.

### 3.2. Форма частицы

`ParticleShape` выбирает математическую форму в pixel shader:

- `SoftDisc` - мягкое светящееся пятно;
- `Flame` - вытянутое пламя;
- `Smoke` - шумовое облако;
- `Spark` - тонкая искра;
- `Shockwave` - кольцо ударной волны;
- `Texture` - нарисованная частица или кадр sprite sheet.

Форма не требует отдельной картинки. Pixel shader рассчитывает прозрачность по
UV-координатам квадрата. Это удобно для прототипа: эффект работает без набора
текстур и атласов.

### 3.3. Смешивание

`ParticleBlendMode` имеет два режима:

- `Alpha` - обычная прозрачность. Нужна для дыма.
- `Additive` - цвет добавляется к кадру. Нужен для огня, вспышек и искр.

Обычные прозрачные частицы сортируются от дальних к ближним. Аддитивные можно не
сортировать: порядок сложения почти не влияет на результат.

### 3.4. ParticleEmitterDesc

Основные поля:

| Поле | Значение |
|---|---|
| `position` | мировая позиция эмиттера |
| `direction` | главное направление вылета |
| `acceleration` | постоянное ускорение, например подъём дыма или гравитация |
| `startColor/endColor` | цвет и прозрачность в начале/конце жизни |
| `particlesPerSecond` | частота постоянного эмиттера |
| `positionRadius` | случайный разброс точки рождения |
| `directionSpread` | отклонение от главного направления |
| `speedMin/speedMax` | случайная начальная скорость |
| `lifetimeMin/lifetimeMax` | время жизни |
| `startSizeMin/Max` | размер при появлении |
| `endSizeMin/Max` | размер перед исчезновением |
| `rotationSpeedMin/Max` | вращение billboard-квадрата |
| `drag` | сопротивление движению |
| `aspectRatio` | отношение ширины к высоте |
| `shape` | процедурная форма или `Texture` |
| `blendMode` | тип прозрачности |
| `emitImmediately` | родить первую частицу сразу |
| `texturePath` | путь к PNG/JPG/TGA для формы `Texture` |
| `atlasColumns/atlasRows` | сетка кадров sprite sheet |
| `atlasFrameCount` | сколько первых ячеек реально используется |
| `atlasFramesPerSecond` | скорость анимации; `0` растягивает кадры на lifetime |
| `atlasLoop` | зацикливать анимацию |
| `randomStartFrame` | начинать частицы с разных кадров |

Диапазоны `Min/Max` убирают механическую одинаковость: для каждой частицы
значение выбирается случайно.

### 3.5. Постоянный эмиттер

```cpp
ParticleEmitterId fire = particleSystem.CreateEmitter(
    ParticleEffectType::Fire,
    worldPosition,
    1.0f);

// Если объект двигается, обновляем позицию каждый кадр.
particleSystem.SetEmitterPosition(fire, newWorldPosition);

// Можно временно выключить источник, не удаляя уже созданные частицы.
particleSystem.SetEmitterActive(fire, false);

// При удалении объекта обязательно удалить его эмиттер.
particleSystem.DestroyEmitter(fire);
```

`ParticleEmitterId` лучше хранить в компоненте устройства или в отдельном
компоненте визуального эффекта. Сам ID не является Entity.

### 3.6. Одноразовый выброс

```cpp
ParticleEmitterDesc steam;
steam.position = worldPosition;
steam.direction = { 0.0f, 1.0f, 0.0f };
steam.acceleration = { 0.0f, 0.4f, 0.0f };
steam.startColor = { 0.85f, 0.90f, 0.92f, 0.65f };
steam.endColor = { 0.45f, 0.50f, 0.52f, 0.0f };
steam.speedMin = 1.0f;
steam.speedMax = 2.5f;
steam.lifetimeMin = 0.8f;
steam.lifetimeMax = 1.6f;
steam.startSizeMin = 0.15f;
steam.startSizeMax = 0.30f;
steam.endSizeMin = 0.6f;
steam.endSizeMax = 1.0f;
steam.shape = ParticleShape::Smoke;
steam.blendMode = ParticleBlendMode::Alpha;

particleSystem.EmitBurst(steam, 24);
```

`particlesPerSecond` в этом случае не используется: количество передаётся
напрямую в `EmitBurst`.

### 3.7. Частица из рисунка

Лучший исходник — квадратный PNG с прозрачным фоном. Сам рисунок должен доходить
почти до краёв, но не обрезаться. Чёрный фон в PNG не считается прозрачностью:
его нужно удалить и сохранить настоящий alpha-канал.

```cpp
ParticleEmitterDesc fire;
fire.position = worldPosition;
fire.direction = { 0.0f, 1.0f, 0.0f };
fire.acceleration = { 0.0f, 0.35f, 0.0f };
fire.particlesPerSecond = 24.0f;
fire.speedMin = 0.25f;
fire.speedMax = 0.8f;
fire.lifetimeMin = 0.45f;
fire.lifetimeMax = 0.9f;
fire.startSizeMin = 0.20f;
fire.startSizeMax = 0.35f;
fire.endSizeMin = 0.45f;
fire.endSizeMax = 0.75f;
fire.startColor = { 1.0f, 0.75f, 0.35f, 1.0f };
fire.endColor = { 1.0f, 0.12f, 0.01f, 0.0f };
fire.shape = ParticleShape::Texture;
fire.texturePath = "assets/texture/particles/fire.png";
fire.blendMode = ParticleBlendMode::Additive;

ParticleEmitterId fireId = particleSystem.CreateEmitter(fire);
```

Для анимированного атласа 4 столбца на 4 строки:

```cpp
fire.texturePath = "assets/texture/particles/fire_4x4.png";
fire.atlasColumns = 4;
fire.atlasRows = 4;
fire.atlasFrameCount = 16;
fire.atlasFramesPerSecond = 20.0f;
fire.atlasLoop = true;
fire.randomStartFrame = true;
```

Кадры читаются слева направо, затем сверху вниз. Все ячейки должны иметь
одинаковый размер. Для одной картинки оставь `Columns = Rows = Frames = 1`.

### 3.8. Редактор эффекта

Открой вкладку `Spawn` и блок `Image Particle Emitter`:

1. Вставь относительный путь к текстуре, например
   `assets/texture/particles/smoke.png`.
2. Для одиночного рисунка оставь atlas `1 x 1`, `Frames used = 1`.
3. Выбери `Alpha` для дыма/пыли или `Additive` для огня/свечения.
4. Нажми `Create live emitter`.
5. Меняй параметры и нажимай `Apply to live emitter`. Старые частицы спокойно
   доживут со старыми параметрами, новые родятся с новыми.
6. После изменения самого PNG нажми `Reload texture from disk`: renderer очистит
   кэш и прочитает свежий файл при следующем кадре.
7. `Emit one burst` удобен для взрыва, искр и короткой утечки.
8. `Delete live emitter` останавливает рождение, не обрывая уже видимые частицы.

Снизу показаны `Alive` и `Emitters`. Это быстрый контроль бюджета: постоянное
значение около `4096` означает, что частота или lifetime слишком велики.

### 3.9. Чем рисовать

Для быстрого результата рекомендуются две бесплатные программы:

- **Krita** — рисовать одиночные PNG с прозрачностью и покадровую 2D-анимацию.
  Хороший выбор для дыма, искр, иконок и масок вручную.
- **Effekseer** — собирать сложный эффект визуально и записывать его в готовый
  sprite sheet. В Recorder выбери экспорт одной картинки: кадры укладываются от
  верхнего левого угла вправо, затем на следующую строку — именно такой порядок
  читает движок.

Практический конвейер: нарисовать базовые маски в Krita, собрать движение и
слои в Effekseer, экспортировать PNG-atlas, положить его в
`assets/texture/particles/`, затем настроить тот же размер сетки в Spawn-панели.

В проект уже добавлен готовый реалистичный пример:
`assets/texture/particles/fire_realistic_4x4.png`. Это 16 кадров, сетка `4 x 4`,
рекомендуемая скорость `20 FPS`, режим `Additive`. Он выставлен в редакторе по
умолчанию, поэтому для первого теста достаточно нажать `Create live emitter`.

### 3.10. Как работает Update

1. Эмиттер накапливает `particlesPerSecond * deltaTime`.
2. Целая часть накопителя превращается в новые частицы.
3. Для частицы обновляются ускорение, сопротивление, позиция и вращение.
4. Увеличивается `age`.
5. Частицы с `age >= lifetime` удаляются.
6. Для живых частиц создаётся компактный `ParticleRenderItem`.

Цвет и размер интерполируются по формуле:

```text
age01 = age / lifetime
current = start + (end - start) * age01
```

Шаг времени ограничен `0.10` секунды. После остановки в отладчике это не даёт
частицам за один кадр улететь на десятки метров.

Лимиты сейчас:

- `MAX_PARTICLES = 4096`;
- `MAX_EMITTERS = 128`.

Это предохранители от случайного бесконечного рождения частиц.

## 4. ParticleRenderer

### 4.1. Почему billboard

Каждая частица визуально является квадратом из двух треугольников. Его оси
берутся из обратной матрицы камеры, поэтому квадрат всегда развёрнут к игроку.
Так одна частица стоит всего 6 вершин и выглядит объёмной в группе.

### 4.2. Один динамический буфер

Рендерер не создаёт DirectX-буфер для каждой частицы. Все вершины кадра сначала
складываются в `m_cpuVertices`, затем одним `Map/Unmap` копируются в общий
динамический vertex buffer.

Процедурные частицы всё ещё собираются в два основных batch. Рисованные частицы
добавляют один draw call на уникальную пару `текстура + blend mode`. Сто частиц
с одним PNG — это один draw call, а не сто. Загруженные текстуры кэшируются и не
читаются с диска каждый кадр.

### 4.3. Глубина

Для частиц включён Z-test, но выключена запись в Z-buffer:

- частица скрывается за стеной;
- одна прозрачная частица не вырезает другую прямоугольной глубиной.

### 4.4. Pixel shader и текстуры

`particle.ps` использует UV квадрата и простую функцию шума. Для каждой формы
рассчитывается своя маска alpha. Для `ParticleShape::Texture` shader читает
цвет и alpha из изображения, умножает их на цвет частицы и применяет общий
fade-in/fade-out. UV одного кадра атласа заранее рассчитываются на CPU.

### 4.5. Текущее подключение

`ParticleSystem` регистрирует единственный активный экземпляр через
`GetActiveSystem()`, а общий `Renderer` забирает у него очередь. Для текущего
движка с одним игровым миром это работает нормально.

Если появятся одновременно несколько миров или preview-сцен, лучше удалить
статический активный указатель и передавать `ParticleSystem*` в `Renderer`
явно через конструктор или setter.

## 5. Готовые эффекты

### Огонь

- вытянутая форма `Flame`;
- additive blending;
- частицы поднимаются;
- размер уменьшается к концу жизни;
- цвет идёт от жёлтого к красному и прозрачному.

### Дым

- форма `Smoke` с двумя слоями шума;
- alpha blending;
- медленное движение вверх;
- облако увеличивается и растворяется;
- жизнь заметно длиннее огня.

### Взрыв

`EmitExplosion` состоит из слоёв:

1. бело-жёлтая короткая вспышка;
2. расширяющийся огненный объём;
3. долгоживущий дым;
4. быстрые искры с отрицательным ускорением Y;
5. кольцо ударной волны.

Сложный эффект почти всегда лучше собирать слоями, а не пытаться заставить один
тип частицы выглядеть одновременно как огонь, дым и осколки.

## 6. Физический ExplosionSystem

`ExplosionSettings`:

- `radius` - радиус воздействия;
- `impulse` - сила центрального импульса;
- `upwardBias` - небольшая добавка вверх;
- `particleScale` - масштаб визуального взрыва.

Система перебирает `RigidBodyComponent` и пропускает:

- тела без Bullet `body`;
- статические объекты;
- кинематические объекты;
- тела с нулевой обратной массой.

Ослабление силы квадратичное:

```text
distance01 = distance / radius
falloff = 1 - distance01
finalImpulse = impulse * falloff * falloff
```

Рядом с центром предмет получает сильный толчок, у края радиуса сила плавно
приближается к нулю. Дополнительный `applyTorqueImpulse` слегка вращает предмет.

Пример ручного вызова:

```cpp
ExplosionSettings settings;
settings.radius = 8.0f;
settings.impulse = 30.0f;
settings.particleScale = 1.5f;

ExplosionSystem::Emit(
    registry,
    particleSystem,
    explosionPosition,
    settings);
```

`DamageSystem` вызывает тот же метод, когда здоровье `DamageableComponent`
впервые переходит из живого состояния в уничтоженное.

## 7. Тестовые клавиши

Обработка находится в `Renderer.cpp`:

- `F7` - создать/удалить постоянный огонь перед камерой;
- `F8` - создать/удалить постоянный дым перед камерой;
- `F9` - физический взрыв перед камерой.

Огонь и дым остаются в точке создания. Это намеренно: клавиши проверяют мировой
эмиттер. Если нужен эффект, приклеенный к движущемуся объекту, каждый кадр нужно
вызывать `SetEmitterPosition`.

Для релизной игры этот тестовый блок стоит обернуть в `#ifdef _DEBUG` или вынести
в отдельную debug-команду редактора.

## 8. Декомпрессия

### 8.1. Компоненты

`HullBreachComponent` хранит факт пробоины:

- комнату;
- мировую позицию;
- радиус отверстия;
- leak rate;
- sealed.

`DecompressionSourceComponent` хранит настраиваемое поведение:

- `suctionStrength` - скорость тяги игрока при полном давлении;
- `suctionRadius` - радиус действия;
- `maxSuctionSpeed` - ограничитель суммы тяг;
- `coolingRate` - скорость охлаждения;
- `outsideTemperature` - температура внешней среды.

Разделение полезно: ремонт и геометрия пробоины не зависят от настроек физики
атмосферы.

### 8.2. Потеря атмосферы

Размер отверстия влияет на эффективную утечку:

```text
radiusScale = clamp(radius / 0.25, 0.25, 4.0)
effectiveLeak = leakRate * radiusScale
lostFraction = clamp(effectiveLeak * deltaTime, 0, 0.95)
```

Давление и кислород умножаются на оставшуюся долю:

```text
pressure *= 1 - lostFraction
oxygen   *= 1 - lostFraction
```

Так утечка естественно замедляется при приближении к вакууму и значение не
уходит ниже нуля.

### 8.3. Температура

Температура движется к `outsideTemperature`. Чем больше потеря воздуха, тем
сильнее шаг охлаждения. Есть и небольшой постоянный теплообмен, пока пробоина
остаётся открытой.

Это игровая модель, не точная термодинамическая симуляция. Для геймплея она
даёт понятный результат и легко настраивается.

### 8.4. Тяга игрока

Тяга применяется только если:

- объект имеет `PlayerGameTag`;
- игрок находится в комнате пробоины;
- игрок внутри `suctionRadius`;
- давление ещё выше нуля.

Формула:

```text
distanceFalloff = 1 - distance / suctionRadius
speed = suctionStrength * roomPressure * distanceFalloff^2
```

Поэтому тяга сильная возле отверстия, слабая у края радиуса и исчезает вместе с
давлением.

### 8.5. Почему нельзя просто applyCentralForce игроку

Игрок использует `btKinematicCharacterController`, а не динамический
`btRigidBody`. Обычная Bullet-сила на него не действует.

`CharacterExternalVelocitySystem` временно сохраняет рассчитанную атмосферой
скорость. На следующем кадре `CharacterControllerSystem` забирает её и
прибавляет к скорости WASD. После чтения значение удаляется.

Порядок важен:

1. `CharacterControllerSystem` применяет тягу прошлого атмосферного кадра;
2. `RoomEnvironmentSystem` рассчитывает тягу для следующего кадра.

Задержка в один кадр незаметна, зато атмосферная система не затирает управление.

### 8.6. Потоки между комнатами

Через открытые двери теперь выравниваются:

- кислород;
- давление;
- температура.

Закрытая исправная дверь возвращает нулевой flow. Открытая или сломанная дверь
использует `DoorComponent::GetEffectiveFlowRate()`.

Изменения сначала собираются в `RoomTransfer`, а затем применяются. Это важно:
результат не должен зависеть от порядка комнат в ECS-контейнере.

## 9. Настройка во время игры

1. Выбрать сущность пробоины.
2. Нажать `F1`.
3. Открыть `Hull Breach`.
4. Найти секцию `Decompression tuning`.
5. Менять `Suction strength`, `Suction radius`, `Max suction speed`,
   `Cooling rate` и `Outside temperature`.

Изменения действуют сразу. Сейчас новые значения не сериализуются. После выбора
подходящего баланса можно:

- закрепить defaults в `DecompressionSourceComponent.h`;
- либо добавить поля `decompression_*` в сохранение/загрузку `SceneManager.cpp`.

## 10. Телеметрия F3

`GameHud::FindPlayerRoom` ищет комнату, в `objectsInRoom` которой находится
Entity игрока. В debug-панели выводятся:

- `PLAYER O2`;
- `ROOM PRESSURE` в процентах;
- `ROOM TEMP` в градусах C.

Если игрок не найден ни в одной комнате, HUD пишет
`ROOM ATMOSPHERE OUTSIDE / UNKNOWN`.

`RoomSystem` обновляет membership отдельно, поэтому сразу после телепорта или
загрузки комнаты телеметрия может отставать на один кадр.

## 11. Куда развивать дальше

### Постоянный пожар повреждённого генератора

Добавить компонент с `ParticleEmitterId`. При переходе здоровья ниже порога
создать Fire emitter. Каждый кадр брать `TransformComponent::position` и двигать
эмиттер. После ремонта выключать его, после удаления Entity уничтожать.

### Огонь должен расходовать кислород

Для каждого активного источника огня найти его комнату и уменьшать
`RoomComponent::oxygen`. При низком кислороде уменьшать `particlesPerSecond` или
выключать emitter. Тогда пожар станет частью атмосферы, а не только картинкой.

### Дым должен влиять на видимость

Добавить в комнату `smokeDensity`. Пожар её повышает, вентиляция и открытые двери
выравнивают. Значение можно передавать в fog shader и снижать дальность обзора.

### Взрыв должен наносить урон

Сейчас `ExplosionSystem` отвечает за частицы и физику. Следующим отдельным шагом
можно собрать сущности в радиусе и отправить `DamageEvent` с тем же falloff.
Не следует напрямую уменьшать здоровье внутри ExplosionSystem: очередь событий
сохранит единый путь брони, пробоин, ремонта и смерти.

### Тяга предметов при декомпрессии

В `ApplyPlayerSuction` сейчас намеренно проверяется только `PlayerGameTag`.
Для предметов можно перебрать динамические `RigidBodyComponent`, рассчитать ту же
скорость и применить `applyCentralForce`. Для производительности сначала стоит
ограничить перебор объектами `room.objectsInRoom`.

### Как рисовать текстуры

- Одиночная частица: `256x256` или `512x512`, прозрачный фон.
- Атлас: обычно `4x4` ячейки; все кадры выровнены и имеют одинаковый размер.
- У дыма края должны плавно уходить в alpha `0`, иначе будет виден квадрат.
- Для огня обычно используется `Additive`, для дыма — `Alpha`.
- Не делай каждый эффект отдельной огромной текстурой: уникальная текстура
  создаёт отдельный batch. Один атлас для родственных эффектов выгоднее.

## 12. Частые ошибки

- Не хранить emitter ID - источник потом нельзя корректно удалить.
- Создавать новый emitter каждый кадр - быстро закончится лимит 128.
- Не обновлять позицию эффекта движущегося объекта - эффект останется в мире.
- Использовать alpha blending для яркой вспышки - цвет станет тусклым.
- Использовать additive blending для дыма - дым начнёт светиться.
- Сохранить PNG с чёрным фоном вместо alpha - будет виден чёрный квадрат.
- Указать неверное число колонок/строк - shader покажет части соседних кадров.
- Делать десятки уникальных текстур в одном кадре - увеличится draw call count.
- Включить запись глубины для прозрачных частиц - появятся квадратные вырезы.
- Применять Bullet force к кинематическому игроку - эффекта не будет.
- Удалять пробоину без удаления связанных компонентов/ремонтного состояния.
- Менять комнаты прямо во время расчёта парных потоков - результат зависит от
  порядка итерации.

Перед текущим состоянием проекта выполнено:

- сборка Debug x64;
- отдельная компиляция `particle.vs` и `particle.ps` через D3DCompiler;
- проверка совпадения записей `.vcxproj` и `.vcxproj.filters`;

## 14. Повреждение и восстановление пластин

### 14.1. Зачем нужна история вырезов

У корпуса два разных представления:

- видимые панели одного материала собраны в общий `ShipPanelVisualBatchComponent`;
- Bullet-коллизия остаётся отдельной у каждой сущности `HullPanelComponent`.

Поэтому простое возвращение исходного меша панели неверно: физика восстановится,
а дыра в общем render-батче останется. Возвращать весь render-батч тоже нельзя,
потому что это одновременно залечит повреждения других панелей.

`RuntimeMeshDamageComponent` решает это через историю операций. Для каждого
затронутого render/collision-меша он хранит:

- общий неизменяемый снимок `RuntimeMeshGeometrySnapshot` с вершинами и индексами
  до первого выреза;
- указатель на конкретный `AssimpModelClass`;
- список активных `RuntimeMeshCutOperation`;
- `revision` для будущей сериализации и диагностики.

Снимок создаётся лениво: неповреждённые модели дополнительную память не занимают.

### 14.2. Один ID для одной пробоины

`MeshCuttingTest::CutByRayAsync` создаёт единый `operationId`. Один и тот же ID
используется для выреза в визуальном батче и в collision-меше панели.

Путь данных выглядит так:

1. `WeaponSystem` вызывает `CutByRayAsync` и получает ID операции.
2. Рабочий поток строит новую геометрию без вызовов DirectX, Bullet и ECS.
3. Главный поток применяет результат через `ApplyCpuMeshForTest`.
4. Только после успешного применения операция записывается в историю меша.
5. `DamageSystem` создаёт `HullBreachComponent` и добавляет к нему
   `HullBreachRepairLinkComponent` с тем же ID.

Это связывает игровую утечку, видимую дыру и физический проход одной командой
ремонта. Неудачный клиппинг не записывается как успешно применённая геометрия.

### 14.3. Удаление висящих фрагментов

После клиппинга `RemoveDetachedTriangleIslands` сваривает близкие позиции вершин
с точностью `0.0001`, строит компоненты связности треугольников и считает их
площадь и расстояние до нового выреза.

Удаляется островок, если одновременно выполнено следующее:

- он не является самым крупным фрагментом;
- для отдельной collision-панели он отделился возле только что созданной пробоины;
- для общего render-батча он целиком находится возле пробоины и имеет малую
  площадь относительно её диаметра.

Проверка расстояния особенно важна для общего render-батча: соседние панели в
нём тоже геометрически не связаны, но они далеко от нового выреза и сохраняются.
После удаления индексы и вершины уплотняются, поэтому невидимые вершины не
остаются в CPU/GPU-буферах.

### 14.4. Что происходит при ремонте

Когда удержание `L` заполнило `RepairableComponent::progress`, `RepairSystem`
запускает двухфазное восстановление:

1. читает `HullBreachRepairLinkComponent`;
2. вызывает `MeshCuttingTest::RepairCutAsync` и помечает связанные модели занятыми;
3. рабочий поток копирует исходный snapshot, пропускает ремонтируемую операцию и
   повторно применяет все остальные вырезы;
4. главный поток проверяет `revision`, применяет уже готовую CPU-геометрию к
   DirectX-буферам и вызывает `PhysicsSystem::RefreshRigidBody`;
5. закрывает утечку и пересчитывает `breachCount`/`isDestroyed`;
6. удаляет ближайшую к пробоине запись `DamageDecalComponent`;
7. удаляет служебную entity пробоины из ECS.

Самая тяжёлая часть — копирование и повторный клиппинг треугольников — больше не
выполняется в кадре, где шкала дошла до 100%. DirectX device, ECS и Bullet world
намеренно остаются на главном потоке: параллельная запись в них небезопасна.
Игрок и NPC используют одну и ту же очередь `JobSystem`; NPC в это время остаётся
в состоянии ремонта с полной шкалой, а игрок может отпустить клавишу `L` —
`PumpCompletedRepairs` всё равно завершит операцию после возврата worker-результата.

Если на панели остались другие дыры, они сохраняются и визуально, и физически.
После ремонта последней пробоины здоровье панели становится максимальным,
`accumulatedDamage` обнуляется, а состояние разрушения снимается.

Если в момент ремонта меш ещё обрабатывает вырезание или другой ремонт, операция
откладывается до следующего кадра. Общий pending-набор и проверка `revision` не
дают двум конкурирующим результатам перезаписать один DirectX-буфер.

### 14.5. Как проверить

1. Взять корабельное оружие и пробить пластину клавишей `H`.
2. Убедиться, что сквозь отверстие можно пройти и начинается декомпрессия.
3. Прицелиться в отверстие и удерживать `L` до завершения ремонта.
4. Проверить, что видимая геометрия вернулась и Bullet больше не пропускает игрока.
5. Сделать две пробоины, починить одну и убедиться, что вторая осталась активной.
6. Починить последнюю: декали должны исчезнуть, давление перестать падать, а
   прочность панели вернуться к максимуму.

### 14.6. Ограничения и следующий шаг

`RuntimeMeshDamageComponent` сейчас является runtime-состоянием и отдельно не
сериализуется. Старую сцену с пробоинами можно загрузить и герметизировать, но
восстановление вырезанной геометрии после перезапуска требует сохранения baseline
или воспроизводимого списка операций. Практичный следующий шаг: сохранять
`RuntimeMeshCutOperation` вместе с пробоинами, а baseline повторно брать из
исходного GLB при загрузке корабля.

### 14.7. Восстановление атмосферы после ремонта

Герметизация пластины останавливает потерю атмосферы, но не создаёт воздух из
ничего. Это делает работающий кислородный генератор в `OxygenGeneratorSystem`.
Теперь он для каждой активной комнаты постепенно возвращает:

- `oxygen` до `1.0`;
- `pressure` до `1.0`;
- `temperature` к `targetTemperature`.

Параметры находятся в `OxygenGeneratorComponent` и сохраняются в сцене:

- `oxygenPerSecond = 0.05`;
- `pressurePerSecond = 0.035`;
- `temperatureRecoveryPerSecond = 1.5` градусов C в секунду;
- `targetTemperature = 20.0` градусов C.

Генератор делит свою производительность между всеми активными комнатами,
нуждающимися в восстановлении. Пока есть открытая пробоина, утечка продолжает
вычитаться до работы генератора, поэтому одной мощности может не хватать для
полного восстановления. Это делает ремонт корпуса осмысленной частью цикла.
