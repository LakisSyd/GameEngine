# Как читать и менять DX Framework с нуля

Этот раздел рассчитан на человека, который умеет открыть проект, но хочет заново понять собственный C++ код. Здесь не требуется предварительно помнить названия паттернов. Мы будем идти от одного значения в памяти к компоненту, от компонента к системе, затем к целому кадру. Если встретилось незнакомое слово, сначала выясни, какие данные оно обозначает и кто ими владеет. Только после этого переходи к следующему методу. Файлы и имена ниже описывают состояние проекта на 29 октября 2026 года; строки могут сдвинуться после изменения исходников, поэтому ищи указанное имя метода.

## 1. Как разобрать строку C++ и не потерять смысл

### 1.1. Тип, имя, значение и время жизни

Возьми простую строку `float deltaTime = 0.016f;`. `float` задаёт тип числа с плавающей точкой, `deltaTime` — имя, `0.016f` — начальное значение. Суффикс `f` означает литерал типа float, иначе дробный литерал в C++ обычно имеет тип double. Но тип не сообщает единицы измерения. В игровом кадре `deltaTime` — секунды, а `position` обычно измеряется в метрах. Если прибавить `deltaTime` к позиции без скорости, объект будет двигаться на численно похожее расстояние, но игровое правило окажется неявным. При чтении каждой арифметической строки подпиши единицы аргументов и результата.

Локальная переменная создаётся при входе в область видимости и уничтожается при выходе из неё. Поле объекта живёт столько же, сколько объект. Динамически созданный ресурс живёт до освобождения владельцем. Это различие важно в `ApplicationClass::Frame`: локальный `registry` как ссылка на `m_sceneManager.GetECSRegistry()` не создаёт второй мир. Когда функция заканчивается, сама ссылка исчезает, но Registry остаётся полем SceneManager. Нельзя вернуть указатель на локальную временную переменную из функции и продолжать пользоваться им в следующем кадре.

### 1.2. Значение, ссылка и указатель

`Entity e` передаёт числовой идентификатор по значению: изменение локальной копии не меняет ID у вызывающего кода. `ECSRegistry& registry` означает ссылку на существующий Registry: система работает с тем же объектом, а не копирует все компоненты. `const RepairableComponent* repairable` — указатель, который может быть `nullptr`, и через который нельзя менять компонент, пока действует `const`. Звёздочка в объявлении указывает тип указателя; `*repairable` в выражении разыменовывает его. `repairable->progress` — доступ к полю через указатель. Разыменовать `nullptr` нельзя.

Если `GetComponent<T>(entity)` возвращает `T*`, следующий безопасный шаг — проверить результат. Сам `Entity` может быть живым, но компонента T у него нет. Для примера, у декоративного ящика есть Transform, но нет Repairable. Правильное условие `if (auto* repairable = registry.GetComponent<RepairableComponent>(e))` связывает проверку и использование. Однако даже ненулевой указатель не обещает вечной жизни: после `DestroyEntity`, `RemoveComponent` или структурной операции с pool проверь его заново. Особо опасно хранить `T&` между вызовами систем, которые могут удалить цель.

### 1.3. `const`, `auto` и `enum`

`const` не означает, что весь игровой мир заморожен; оно ограничивает изменение через конкретный доступ. `const auto* brain = registry.GetComponent<NpcBrainComponent>(e)` позволяет читать brain, но не записывать state через этот указатель. `auto` выводит тип выражения, а не превращает язык в динамический: если справа `T*`, тип остаётся указателем. При чтении сложного кода при необходимости выпиши настоящий тип `auto`, иначе легко перепутать копию с ссылкой. `auto&` создаёт ссылку, `auto` в range loop может копировать элемент.

`enum class` задаёт именованные варианты состояния: `NpcState::Idle`, `NpcState::Attacking` и так далее. Он помогает компилятору отличать состояние NPC от произвольного числа. Но enum сам не определяет переходы: их задают условия систем. Если персонаж одновременно хранит `state=Attacking` и `target=INVALID_ENTITY`, это логически противоречивое состояние, даже если оба поля по отдельности имеют допустимые типы. Составь инварианты: при Attacking цель жива и враждебна; при Repairing есть действительная цель и достижимая рабочая точка. Claim нужен для автоматического назначения; для оборудования может использоваться WorkZone, а пробоина в текущем коде обрабатывается без него.

### 1.4. `std::vector`, `unordered_map` и итерация

`std::vector<T>` хранит последовательность. Добавление элемента иногда перераспределяет память, поэтому старые указатели и ссылки на элементы могут стать недействительными. `std::unordered_map<Key,Value>` хранит значения по ключу; изменение структуры контейнера влияет на итераторы по правилам конкретной операции. В ECS Registry каждый тип компонента имеет pool, а `ForEach` итерирует его. Поэтому не удаляй текущий компонент из того же pool прямо во время `ForEach`, если контракт `ComponentManager` этого явно не гарантирует. Безопасный подход: во время обхода складывай Entity ID в `pendingDestroy`, после обхода применяй удаления. Это не просто стиль — так сохраняется корректность итератора и ссылок.

### 1.5. Лямбда и захват

`[&](Entity e, auto& component) { ... }` — функция без имени, которую можно передать `ForEach`. `[&]` разрешает использовать внешние локальные переменные по ссылке. Это удобно для накопления результатов, но опасно для фоновой задачи: после выхода из вызывающей функции захваченная ссылка может стать висячей. В синхронном `ForEach`, который вызывает лямбду до возврата, захват по ссылке обычно соответствует времени жизни. При `JobSystem::SubmitJob` код может выполниться позже; копируй нужные входные данные и применяй итог в главном потоке после проверки живости Entity и версии сцены.

### 1.6. RAII и владение ресурсом

RAII означает, что освобождение ресурса связано с уничтожением объекта-владельца. `std::unique_ptr<IComponentPool>` внутри `ECSRegistry` ясно выражает единоличное владение pool. Если Registry уничтожается, unique_ptr освободит pool. Bullet body, GPU buffer и job queue живут по другим правилам: удалить C++ объект недостаточно, если он всё ещё зарегистрирован в physics world или привязан к GPU command. Для каждого такого ресурса составь пару «создание — удаление» и момент отписки от внешнего мира. Если scene reload оставил collider без Entity, это нарушение жизненного цикла, а не визуальный баг.

Проверочное упражнение. Прочитай сигнатуру `void StateSystem::Update(ECSRegistry& registry, float deltaTime, JobSystem& jobs)`. Назови, какие аргументы копируются, какие ссылаются на существующий объект, где ожидаются единицы, какие изменения возможны. Затем найди один вызов функции из `ApplicationClass::Frame`. Проверь, передан ли `simulationDeltaTime`, когда Play поставлен на паузу. Не переходи к телу метода, пока сигнатура не понятна.

## 2. Разбираем `ECSRegistry.h` буквально по шагам

### 2.1. `CreateEntity`: от ID до живой сущности

Файл `src/ECS/ECSRegistry.h`, метод `CreateEntity` (в текущем файле около строк 15–22). Строка с `if (nextEntity == INVALID_ENTITY)` защищает от выдачи зарезервированного значения. `throw std::overflow_error` останавливает операцию явной ошибкой; без этой проверки переполнение ID могло бы дать новое значение, совпадающее с «нет сущности». `const Entity entity = nextEntity++;` сначала берёт прежний номер, затем увеличивает счётчик. `m_liveEntities.insert(entity)` фиксирует, что ID существует. Возврат отдаёт номер вызывающему коду. В этот момент у сущности ещё нет Transform, RenderComponent или NPCBrain: CreateEntity создаёт идентичность, а не готовый игровой объект.

Проверь на бумаге: если `nextEntity=10`, первый вызов возвращает 10 и оставляет 11; второй возвращает 11. `IsAlive(10)` после первого вызова истинно, но `HasComponent<TransformComponent>(10)` может быть ложно. Это объясняет, почему одно лишь создание Entity не рисует объект. Если игра удалит 10, текущая реализация не переиспользует этот номер немедленно; generation handle здесь не реализован. При добавлении повторного использования в будущем понадобятся поколения, чтобы старый сохранённый ID не указывал на новую сущность.

### 2.2. `DestroyEntity`: удаление из набора и pools

Около строк 24–28 `DestroyEntity` сначала делает `m_liveEntities.erase(e)`, затем проходит `for (auto& [ti, pool] : m_pools)` и вызывает `pool->Remove(e)` у каждого типа компонента. Это универсальная очистка ECS данных: Registry не обязан знать заранее, какие компоненты были у Entity. Но у внешних систем есть дополнительные ресурсы. Если компонент содержал `btRigidBody*`, перед уничтожением нужно убедиться, что тело исключено из Bullet world и освобождено по договору владельца. Если async job хранит ссылку на компонент, удаление до завершения job опасно. Поэтому в gameplay коде зачастую нужен более высокий `DespawnEntity` путь, который согласует ECS, physics, renderer, jobs и временные reservations.

На проверочной сцене создай Entity с двумя компонентами, вызови Destroy, затем проверь `IsAlive=false`, `GetComponent<T>=nullptr` для обоих. Потом проверь физический мир: число тел тоже должно уменьшиться, если Entity владело телом. Если не уменьшилось, Registry выполнил свой контракт, а вызывающий lifecycle путь — нет. Важно различать эти уровни ответственности.

### 2.3. `AddComponent` и две перегрузки

Около строк 33–43 есть две формы. `AddComponent(Entity e, const T& comp)` копирует объект и разрешена только для copy-constructible T. `AddComponent(Entity e, T&& comp)` пересылает временное значение или объект, который можно переместить; это нужно для некопируемых компонентов, например тех, что владеют физическим ресурсом. `GetOrCreatePool<T>()` находит pool этого типа либо создаёт его. Обрати внимание: в этих строках не видно проверки `IsAlive(e)`. Следовательно, вызывающий код должен соблюдать контракт живой Entity или нужно усилить Registry; не предполагай невидимую защиту. Если компонент добавлен на несуществующий ID, pool может хранить мусорную запись, которая не соответствует `m_liveEntities`.

Для новичка полезна аналогия: Entity ID — номер папки, component pool — отдельная таблица одного вида данных. `AddComponent` добавляет строку в таблицу по номеру папки. Если номер папки неверен, таблица не обязательно сама поймёт это. Поэтому фабрика объекта должна создавать Entity один раз, затем последовательно добавлять обязательные компоненты и валидировать готовую конфигурацию.

### 2.4. `GetComponent`, `HasComponent`, `RemoveComponent`

`GetComponent<T>` находит pool типа T. Если pool отсутствует, возвращает `nullptr`; иначе вызывает `pool->Get(e)`. `HasComponent<T>` проверяет наличие pool и Entity в нём. `RemoveComponent<T>` удаляет только этот тип у выбранной Entity. Ни один из этих методов не меняет `m_liveEntities`. Следовательно, NPC может оставаться живым, но временно потерять оружие, и системы должны обрабатывать это как допустимое или ошибочное состояние по своему правилу. Нельзя писать `*registry.GetComponent<T>(e)` без проверки, если отсутствие T возможно.

`GetComponents<T>()` в отличие от `GetComponent` создаёт pool, если его ещё не было. Это полезно для системного обхода, но имеет побочный эффект создания пустого pool. При диагностике «почему появился pool» учитывай это. Для read-only запроса к одному объекту предпочитай `GetComponent`/`HasComponent`, чтобы чтение не изменяло структуру Registry без необходимости.

### 2.5. `ForEach<T1,T2>` построчно

Около строк 45–59 берутся два указателя на pools: `FindPool<T1>()` и `FindPool<T2>()`. Если один отсутствует, `return` заканчивает обход без вызова callback. Затем цикл проходит каждый элемент первого pool. Для текущего Entity проверяется `pool2->Has(entity)`. Если второй компонент найден, берётся ссылка `comp2` и вызывается `fn(entity, comp1, comp2)`. Это значит, что порядок типов влияет на количество итераций: `ForEach<Редкий,Частый>` обычно делает меньше проверок, чем `ForEach<Частый,Редкий>`. Но менять порядок нужно только если callback аргументы и логика соответственно переставлены.

Ключевое ограничение: callback получает ссылки на элементы pools. Если внутри callback удалить текущий компонент или Entity, цикл может потерять валидность итератора. Даже если конкретный контейнер иногда переживает удаление другого элемента, не строй на этом неявную гарантию. Собирай команды на структурные изменения отдельно. Вопрос для самопроверки: `ForEach<NpcBrainComponent,TransformComponent>` найдёт ли Entity только с Transform? Нет: она отсутствует в первом pool и не участвует в цикле. Найдёт ли Entity только с Brain? Цикл её увидит, но проверка второго pool не пропустит callback.

### 2.6. `type_index` и закрытая часть класса

В `private` находятся `nextEntity`, набор живых ID и `unordered_map<std::type_index,std::unique_ptr<IComponentPool>>`. `typeid(T)` превращается в ключ вида компонента. `FindPool<T>` ищет ключ и приводит базовый `IComponentPool*` к конкретному `ComponentManager<T>*`; корректность зависит от того, что под данным ключом всегда лежит pool именно T. `GetOrCreatePool<T>` создаёт его при первом обращении. Это простая реализация ECS, которую можно понять без магии: каждый тип имеет собственную таблицу, а Registry связывает таблицы общим Entity ID.

Упражнение: вручную нарисуй три pools — Transform у Entity 1 и 2, Repairable у Entity 2 и 3, NPCBrain у Entity 1. Что вызовет `ForEach<TransformComponent,RepairableComponent>`? Только Entity 2. Что произойдёт после `DestroyEntity(2)`? ID 2 удалён из набора живых и обоих pools. После этого попытка `GetComponent<RepairableComponent>(2)` должна вернуть null. Проверь тем же набором в маленьком тестовом запуске.

## 3. Главный кадр: читаем порядок, а не названия систем

### 3.1. Вход `Frame(float dt)` и режимы времени

`ApplicationClass::Frame` начинается около строки 1023 `src/Core/ApplicationClass.cpp`. Параметр `dt` — длительность кадра. В отдельном режиме проверки оружия код принудительно ставит `dt=1/60`, поэтому измерение FPS в этой ветке не отражает реальное время. Затем обновляется DebugHud, input manager и очищаются события текущего кадра. Уже здесь читатель должен спросить: `m_events.Clear()` удаляет события прошлого кадра до или после того, как их потребители обработали? Ответ ищи в местах публикации и чтения событий, а не предполагай. Для нового события выбери конкретную фазу кадра, чтобы оно не исчезало сразу после создания.

Переключение F5 проверяет не только `IsKeyDown`, но и `!m_wasF5Down`: так одно долгое удержание клавиши не переключает режим каждый кадр. При входе в Play `EnterPlayMode` проверяет сцену, затем сбрасываются timer, event log, trigger state, открытый UI и режим камеры. В AI-only сцене без игрока код отдельно не создаёт фиктивный инвентарь для `INVALID_ENTITY`. Это пример защитной проверки на границе режимов. При выходе в Editor нужно очистить накопленное намерение движения character controller; иначе физика продолжает шагать, используя последнюю команду Play. Этот комментарий в коде показывает, что режим Editor не является полной остановкой всех подсистем.

### 3.2. От ввода игрока до намерения движения

В Play при работающей симуляции `m_gameplayController.Update` получает Registry, `simulationDeltaTime`, input, режим захвата UI и yaw камеры. Он не обязан непосредственно перемещать mesh. Его задача — превратить действие игрока и направление камеры в намерение. Далее системы движения и Bullet определят фактическое положение. Если игрок нажал W, а персонаж стоит, проверь по цепи: получен ли GameAction; заблокировал ли его UI; записана ли желаемая скорость; вызван ли character controller; есть ли контакт с collider; изменился ли Transform после physics. Если первый разрыв на входе, физику менять рано.

### 3.3. Почему NPC pipeline стоит именно так

В текущем кадре перед выбором и выстрелами уменьшаются таймеры оружия (`WeaponSystem::UpdateTimers`). Затем `NpcUtilitySystem` рассчитывает автоматическое действие; `CrewTaskCoordinator` закрепляет работу за конкретным членом экипажа; `NpcCombatSystem` обновляет боевую видимость и память; `NpcCoverSystem` выбирает индивидуальное укрытие; `StateSystem` исполняет итоговое состояние, строит путь и заполняет движение; `CharacterFacingSystem` поворачивает персонажа. Групповой `NpcSquadCombatSystem::Update` в этой ревизии закомментирован. Позднее, после обновления позы и оружейных данных, `NpcRangedCombatSystem` может фактически стрелять. Не говори «NpcCombatSystem стреляет» только потому, что он выбирает Attacking; выстрел имеет отдельные условия и место кадра.

На бумаге проследи одного инженера. До кадра у него Idle и нет цели. Utility видит пробоину и рассчитывает полезность; Coordinator ставит claim; StateSystem в этом же кадре может увидеть назначение и запросить путь; Facing поворачивает модель. Фактическая капсула может сдвинуться позже на physics step. Если поменять местами Coordinator и StateSystem, первое движение задержится до следующего кадра. Это не обязательно катастрофа, но меняет наблюдаемое поведение. Любая перестановка вызовов должна сопровождаться таблицей «кто пишет поле → кто читает».

### 3.4. Кто владеет состоянием и что значит «на один кадр старое»

В одном кадре разные поля могут отражать разные моменты. У NPC `brain.state` уже новый, `desiredVelocity` вычислена по новому маршруту, а `Transform` ещё хранит позицию до physics step. Renderer после physics может увидеть обновлённое положение, а HUD, если был заполнен раньше, покажет старую дистанцию. Это обычный вопрос фаз, пока задержка определена и мала. Для диагностики показывай timestamp/fixed tick рядом с данными. Если поле используется через несколько кадров без инвалидации, это уже ошибка контракта, особенно для raycast muzzle и lastKnownPosition.

## 4. Как добавлять систему так, чтобы она заработала во всей игре

### 4.1. Сперва сформулируй правило без C++

Выберем пожар. Правило для игрока: повреждённый прибор может загореться; огонь расходует ресурс и нагревает комнату; инженер с огнетушителем может потушить его; закрытая дверь влияет на доступность; HUD сообщает причину, если работа невозможна. Запиши, как игрок видит начало, развитие и конец события. Затем выпиши состояния `Igniting`, `Burning`, `Dying`, `Extinguished`; для каждого — кто меняет его, что видно, можно ли сохранять. Если эту схему нельзя изложить словами, реализация тоже будет противоречивой.

Данные огня принадлежат `FireComponent` на Entity очага: интенсивность, топливо, room ID, рабочая зона и временной параметр. Температура комнаты принадлежит комнате, заряд огнетушителя — инвентарю NPC. Не дублируй одно и то же число в нескольких местах без явного правила синхронизации. Например, если и FireComponent, и RoomComponent хранит «текущую температуру пожара», один из них неизбежно станет устаревшим. Выбери источник правды и производные показатели.

### 4.2. Реализация минимального тика

Создай систему, которая работает с одним очагом без NPC и рендера. Пример ниже — учебный псевдокод, потому что конкретных `FireComponent` и `RoomTemperatureComponent` в текущем проекте ещё может не быть. Он показывает контракт обновления, а не готовую вставку:

```cpp
void FireSystem::Update(ECSRegistry& ecs, float dt) {
    ecs.ForEach<FireComponent>([&](Entity fireEntity, FireComponent& fire) {
        if (fire.state != FireState::Burning) return;
        const float burn = std::min(fire.fuel, fire.burnRate * dt);
        fire.fuel -= burn;
        fire.intensity = std::clamp(fire.intensity + fire.growthRate * dt,
                                    0.0f, fire.maxIntensity);
        if (fire.fuel <= 0.0f) fire.state = FireState::Dying;
    });
}
```

Разбор. Проверка state предотвращает рост потушенного очага. `burnRate*dt` переводит расход «в секунду» в расход за шаг. `std::min` не позволяет забрать больше топлива, чем есть. Clamp удерживает интенсивность в допустимых границах. Переход в Dying выполняется при исчерпании топлива. Но этот код ещё не нагревает комнату, не наносит урон и не создаёт задачу NPC. Добавляй по одному звену и каждый раз проверяй инвариант, чтобы при сбое знать, на каком этапе он появился.

### 4.3. Место в кадре и зависимости

Если Coordinator должен выбирать пожар по текущей интенсивности, `FireSystem::Update` должен выполняться до него либо решение сознательно использует предыдущий tick. Если тушение снижает интенсивность после работы NPC, порядок должен не удваивать изменение за один кадр. Отдельно реши, когда атмосфера реагирует на кислородный расход: до или после FireSystem, и нужна ли задержка. Напиши таблицу входов и выходов каждой функции. Не вставляй новую систему «куда удобно» между случайными вызовами `ApplicationClass::Frame`.

### 4.4. Сцена, Inspector, сохранение, UI

После работающего тика нужно дать автору игры создать очаг в Editor. Добавь сериализацию только authoring полей, например начальная интенсивность, запас топлива и room ID. Runtime указатель на комнату, временные claim, path cache, Bullet pointer и GPU handle не записывай как числа в JSON. Для продолжаемой игры отдельно реши, какие runtime поля нужно сохранять: оставшееся топливо и текущий state обычно важны. После LoadScene восстанови Entity references и runtime ресурсы. В Inspector показывай и редактируемые authoring поля, и read-only live данные, чтобы пользователь не путал сохранённый параметр со значением текущего кадра.

### 4.5. Связь с NPC и контроль отказов

Новая работа требует обнаружения очага, оценки полезности, claim, доступной WorkZone, маршрута, расхода огнетушителя, прогресса тушения и события завершения. Каждое из этих звеньев имеет отдельную причину отказа: нет очага, он уже занят, путь закрыт, нет ресурса, комната опасна, WorkZone внутри collider. Покажи причину в debug UI. Начни с одного NPC и одного очага, затем два NPC и две цели. Смерть исполнителя должна освободить claim. Ручная команда должна вытеснить automatic работу по ясному правилу. После тушения удалённый Entity не должен оставаться в чужом `repairTarget`.

### 4.6. Проверка результата в игре

Построй маленькую сцену с двумя комнатами, дверью и одним очагом. Запиши прогноз на 10 секунд: сколько топлива сгорит, до какой интенсивности вырастет пожар, когда инженер войдёт в WorkZone, сколько заряда потратит и когда огонь перейдёт в Extinguished. Выполни прогон при 30, 60 и 120 FPS на одинаковое simulation time. Если числа кратно различаются, проверь `dt`. Сохрани игру посередине, загрузи и убедись, что огонь не создался второй раз, ресурс не вернулся, claim не дублировался. Это минимальный стандарт новой системы до включения её в большую миссию.
