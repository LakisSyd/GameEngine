# Практикум по слабым местам DX_FrameWork

Источник: `DX_FRAMEWORK_ENGINE_TEXTBOOK_RU.docx`, прежде всего §5–8, §10–15, §17–18, §20–27, §32–37 и сводка §39. Это **второй файл заданий**, после [недельного практикума по прицелу и врагу](WEEK_1_AIM_AND_ENEMY_RU.md). Здесь нет изменений кода: задачи даны тебе как разработчику движка. Двигайся по порядку внутри раздела; для каждой темы сначала воспроизведи симптом, потом меняй код, затем проверяй результат.

**Граница текущего проекта.** Учебник описывает также старый формат игры с подлодкой, затоплением, атмосферой, энергетикой, пробоинами и ремонтом. Эти подсистемы всё ещё встречаются в исходниках, но сейчас они тебе не нужны. Практикум не предлагает их исправлять или расширять. Если они мешают боевой игре, отдельной задачей станет безопасное отключение/изоляция старого gameplay-кода после проверки зависимостей. В графике оставлены общие задачи про материалы, прозрачность, свет и тени; водный рендер не является целью.

## Как работать с этим списком

1. Сохрани исходное состояние проекта в Git. Одна тема = небольшой отдельный коммит, чтобы видеть причинно-следственную связь. Не начинай сразу с HDR или полного NavMesh.
2. Для каждой темы запиши четыре вещи: **инвариант** («что всегда должно быть верно»), минимальную сцену воспроизведения, код изменения, проверку до/после. Пример: «закрытая стена всегда перекрывает пулю»; сцена — NPC, стена, игрок на одной линии.
3. `Debug x64` нужен для итерации, `Release x64` — для реальной поставки. Отдельно проверяй запуск из другого рабочего каталога. FPS-зависимые ошибки проверяй хотя бы на двух частотах.
4. Примеры C++/HLSL ниже — **схемы**, а не готовые патчи. Подставляй существующие типы, порядок матриц и ownership проекта. Сначала прочитай указанные файлы: учебник описывает состояние на момент написания, часть уже изменилась.
5. После выполнения помечай `[x]` в копии этого файла или в своём журнале. Не меняй исходный учебник до проверки: он остаётся историческим объяснением причин.

## Блок A. Сборка, жизненный цикл, данные — фундамент

### A1. Воспроизводимый Release и запуск не из каталога проекта — P0, аудит (§6.2–6.4)

**Теория.** Компиляция `.exe` не гарантирует запуск: нужны DLL, шейдеры, модели, настройки и правильный путь к ресурсам. Рабочая директория процесса может быть другой, чем каталог `.exe`. Путь `assets/model/a.glb` считается относительно working directory, поэтому при запуске из другой папки исчезнет модель.

**Пример.** Если исполняемый файл находится в `build/Game.exe`, а ассеты в `build/assets`, корнем ресурсов можно считать каталог `.exe`, полученный через `GetModuleFileNameW` и `std::filesystem::path(...).parent_path()`. Собирай полный путь как `assetRoot / "assets/model/a.glb"`; не полагайся на случайный `SetCurrentDirectory` из IDE.

**Шаги.** (1) Собери `Debug|x64` и `Release|x64` через `.vcxproj`. (2) Для каждого запусти из каталога проекта и из пустой папки через PowerShell с `-WorkingDirectory`; запиши ошибку первого отсутствующего ресурса. (3) Создай единый resolver путей и используй его у загрузчиков модели/текстуры/шейдера/JSON. (4) Собери runtime package с DLL и ассетами; проверь запуск с машинной конфигурацией без IDE. (5) Задокументируй команду сборки и расположение результата.

**Готово, когда:** Release показывает сцену и Play, а запуск из другой рабочей директории даёт тот же результат. Если Release уже работал, задача — только оформить проверку и package.

### A2. Безопасная смена сцены и транзакционная загрузка — P0, частично аудит (§5.2, §26.6, §36.3)

**Теория.** Bullet хранит указатели на свои объекты. Нельзя уничтожить C++-компонент, пока мир ещё ссылается на его `btCollisionObject`, action или constraint. Загрузка должна вести себя как транзакция: невалидный файл не уничтожает действующую сцену.

**Пример.** Порядок выгрузки: остановить новые задания → дождаться/отменить операции сцены → удалить из Bullet constraints/actions/bodies → освободить shapes/motion states → очистить ECS. Порядок загрузки: `read → parse → validate → build temporary state → commit`, а не `Clear() → parse later`.

**Шаги.** (1) Прочитай `SceneManager::Clear`, `ReleasePhysicsRuntime`, `LoadScene` и `PhysicsSystem.cpp`; выпиши владельцев каждого Bullet pointer. (2) Сделай тестовую боевую сцену с игроком, двумя NPC, оружием и коллайдерами; загрузи её подряд 20 раз, сравни число объектов Bullet и ECS. (3) Попробуй открыть обрезанный JSON, неверную версию, отсутствующую модель: старая сцена должна остаться. (4) Если не остаётся, сначала валидируй полный JSON и ссылки, затем строй временное состояние и меняй сцены только после успеха. (5) Повтори с незавершённой async-операцией.

**Готово, когда:** невалидная загрузка не меняет текущую сцену; многократная загрузка не накапливает физические объекты. Существующий вызов `ReleasePhysicsRuntime()` сохрани, если тест проходит.

### A3. Атомарная запись и полноценный round trip сцены — P0/P1 (§36.1–36.5)

**Теория.** `ofstream(target)` сразу обнуляет файл; сбой в середине оставит повреждённый save. Round trip означает: `Save → Load → Save` сохраняет существенные значения и ссылки, даже если порядок объектов в JSON изменился. Сохранение редакторской сцены и состояния запущенной игры — разные форматы.

**Пример.** `write scene.json.tmp → flush/close → validate temp → replace scene.json`. Для ссылок Entity нужна таблица `oldId → newId` после создания всех сущностей. В сравнении JSON сортируй сущности по устойчивому имени/ID и сравни поля семантически; простое сравнение строк шумит из-за порядка.

**Шаги.** (1) В `SceneManager.cpp` сравни, что `SaveScene` пишет, а `LoadScene` читает: материал и модель игровой локации, оружие, `DamageableComponent`, боевые настройки NPC, спрайты HUD, Entity references. (2) Напиши тест на сохранение/загрузку маленькой тестовой сцены с каждым **нужным** типом. (3) Исправь действительно отсутствующие поля, расширь schema version и миграцию старых версий. (4) Добавь временный файл и замену основного только после успешной записи; не удаляй рабочий save раньше. (5) Отдельно реши, нужен ли runtime save: HP, патроны, экипированный слот, память AI, скорости Bullet, игровое время и random seed.

**Готово, когда:** прерванная запись сохраняет старый файл; старая боевая сцена открывается; round trip не теряет параметры и ссылки. Старые компоненты, которых нет в новой игре, в этот тест не входят.

### A4. Entity generation и безопасное изменение ECS при обходе — P1 (§10.6)

**Теория.** `Entity` как простой номер легко становится «висячей» ссылкой после удаления/повторного использования. `std::unordered_map`/pool может инвалидировать итератор, когда callback `ForEach` удаляет текущий компонент или добавляет много новых. Наличие `IsAlive` помогает, но не решает повторное использование ID после сброса registry.

**Пример.** Handle `{index, generation}` считается живым, только если `generation[index] == handle.generation`. Для удаления во время обхода собери намерения в `std::vector<Entity> toDestroy`, затем примени после цикла.

**Шаги.** (1) Выведи, что происходит со ссылкой на Entity после `DestroyEntity` и после загрузки новой сцены. (2) Добавь тест: сохрани старый handle, удали объект, создай новый, убедись, что старый handle не указывает на новый. (3) Определи, нужен ли generation в самом типе Entity или scene epoch в долгоживущих ссылках. (4) Запрети/отложи структурные изменения pool во время `ForEach` командным буфером. (5) Проверь ссылки NPC, оружия, подбираемых предметов и async results.

**Готово, когда:** старые ссылки отвергаются и удаление во время обхода не вызывает UB. `Get/Has` уже не создают pool — этот подпункт учебника закрыт.

### A5. Async-задания не должны переживать свою сцену — P0 (§17.3, §35.8)

**Теория.** Worker может рассчитать результат для старой сцены; затем main-thread callback применит его к новым Entity с теми же числами. `JobSystem::Wait()` ждёт рабочую очередь, но не обязательно очередь обратных вызовов главного потока.

**Пример.** `SceneEpoch epoch = currentSceneEpoch;` захватывается при постановке задачи. Перед применением: `if (epoch != currentSceneEpoch) return;`. Для NPC route дополнительно сравни `command.revision` и цель. GPU-ресурсы создавай на потоке, где это допускает выбранный контракт рендера, а применение к ECS — на главном.

**Шаги.** (1) Найди всех вызывающих `SubmitJob` и `SubmitMainThread`; для нынешней игры выдели NavMesh, culling и загрузку assets, а старые вызовы mesh cutting только учти при выгрузке сцены. (2) Для каждого нужного пути выпиши: что worker читает, чем владеет, какой callback выполняется при успешной/проваленной загрузке сцены. (3) Введи scene epoch или слабый токен жизни и проверку перед commit. (4) Определи shutdown: запретить новые задачи, закончить/отменить worker, обработать или отбросить main-thread completion, затем выгрузить сцену. (5) Стресс-тест: запусти pathfinding/загрузку модели и сразу перезагрузи тестовую сцену десять раз.

**Готово, когда:** результат старой сцены никогда не меняет новую; `Wait` не считается окончанием операции, пока не решена main-thread очередь.

### A6. Исключения и остановка JobSystem — P0 (§35.8)

**Теория.** Необработанное исключение из `std::thread` вызывает `std::terminate`; если при этом `activeJobs` не уменьшается, `Wait()` может висеть. Сейчас в `src/Core/JobSystem.h` worker вызывает `job()` без защиты, и main-thread callback тоже вызывается без защиты.

**Пример.** Схема: `try { job(); } catch (...) { recordError(std::current_exception()); }` → уменьшить `activeJobs` в scope guard → `finishedCondition.notify_all()`. Ошибку передавай в журнал/главный поток. `SubmitMainThread` после Shutdown должен явно отклонять работу или принимать её только при документированном lifecycle.

**Шаги.** (1) Создай тестовую задачу, выбрасывающую исключение. (2) Убедись, что процесс не падает, `Wait()` завершается, последующая задача исполняется. (3) Повтори для main-thread callback. (4) Проверь Submit до Initialize и после Shutdown. (5) Затем добавь диагностику числа queued/active/failed jobs.

**Готово, когда:** исключение одной задачи не убивает процесс и не зависает очередь; ошибки видны, а shutdown детерминирован.

### A7. Очередь задач: отмена, приоритет и лимиты — P3 (§35.8)

**Теория.** Фиксированное число worker threads само по себе допустимо, но для asset loading, NavMesh и подготовки рендера нужны разные ожидания. Сотни тяжёлых задач могут задержать видимый пользователю результат. Отмена обычно кооперативная: работа периодически читает токен, а main-thread commit всё равно проверяет scene epoch.

**Пример.** Запрос маршрута около игрока получает высокий приоритет, фоновая подготовка дальнего объекта — низкий. При отмене: `if (cancelToken.stop_requested()) return;`, а перед применением: `if (epoch != currentEpoch) return;`. Приоритет не должен заставлять низкоприоритетную очередь голодать бесконечно.

**Шаги.** (1) Измерь длины очередей и время ожидания разных задач. (2) Если задержка заметна, добавь дескриптор задачи и кооперативную отмену; затем максимум очереди и два-три уровня приоритета. (3) Протестируй отмену до старта, во время работы и перед main-thread commit. (4) Проверь graceful shutdown и отсутствие starvation. (5) Оставь прежнюю простую реализацию, если измерения не показывают проблемы.

**Готово, когда:** важная задача не ждёт бесконтрольно фоновые работы, отменённый результат не применяется и лишние threads/queue рост не съедают кадр.

### A8. Изоляция старого gameplay-кода — P2, по необходимости

**Теория.** Ненужную систему лучше сначала исключить из игрового цикла, а затем удалить отдельным изменением. Простое удаление файлов может сломать загрузку старых сцен, порядок освобождения Bullet-объектов или сборку проекта. Код, который больше не запускается, всё равно может оставаться зависимостью сериализации и редактора.

**Пример.** У старой системы симуляции условие вызова должно определяться режимом/типом сцены, а не случайным отсутствием компонентов. После отключения её счётчик вызовов в боевом Play равен нулю, а `ReleasePhysicsRuntime()` продолжает корректно чистить уже созданные объекты.

**Шаги.** (1) Для каждой старой подсистемы выпиши места создания компонентов, вызов `Update`, сохранение/загрузку и shutdown. (2) Сначала отключи её выполнение в новом игровом режиме и проверь FPS/логи. (3) Проверь, что загрузка старых сцен либо поддерживается явно, либо даёт понятное сообщение о несовместимости. (4) Удаляй файлы/компоненты только отдельным коммитом после проверки сцены, сборки и тестов. (5) Зафиксируй перечень оставшихся legacy-зависимостей в документации.

**Готово, когда:** боевой режим не тратит кадр на старые симуляции, а смена сцены и закрытие игры остаются устойчивыми.

## Блок B. Время, единицы и физика персонажа

### B1. Единицы измерения и единая модель вращения — P1 (§12, §14–15)

**Теория.** Число `90` может означать градусы или радианы; матрицы Euler зависят от порядка осей. Если визуальный `Rx*Ry*Rz`, а Bullet строит quaternion в другом порядке, модель и collider расходятся. Для нормалей при неравномерном масштабе нужна `transpose(inverse(world3x3))`; `world3x3` подходит только без проблемного scale/shear.

**Пример.** Именуй входы `yawRadians` или `yawDegrees`, конвертируй на границе UI: `radians = XMConvertToRadians(degrees)`. Выбери один контракт ориентации, например quaternion как canonical pose; UI Euler — лишь способ ввода. Для локального центра collider: `worldCenter = TransformCoord(localCenter, worldMatrix)`.

**Шаги.** (1) Нарисуй три цветные оси у объекта и его Bullet shape. (2) Дай ему поворот по X/Y/Z одновременно и неравномерный scale; сравни mesh/shape/normal. (3) Найди места умножения матриц и создания Bullet orientation; документируй порядок. (4) Приведи к одному контракту через небольшие функции преобразования. (5) Проверь углы 0°, 90°, 179° и повторное сохранение/загрузку.

**Готово, когда:** collider совпадает с mesh, normal shading не меняется неверно от масштаба, UI и Bullet трактуют угол одинаково.

### B2. Фиксированный физический шаг и независимое от FPS сглаживание — P1 (§7–8)

**Теория.** Сила — ньютон, её эффект интегрируется по времени внутри fixed physics tick. Если `applyForce` вызывается один раз за render frame, а Bullet делает разное число substeps, поведение зависит от FPS. `lerp(current,target,0.3)` на каждом кадре также зависит от FPS.

**Пример.** Для сглаживания `alpha = 1 - exp(-k*dt)`; для силы `F` выполняй `body->applyCentralForce(F)` в каждом fixed tick. Если ограничиваешь `dt`, храни остаток в accumulator: `while (accumulator >= fixedDt) { Step(fixedDt); accumulator -= fixedDt; }` с ограничением числа шагов при сильном лаге.

**Шаги.** (1) Сравни падение персонажа, движение NPC, скорость камеры при ПКМ и отдачу за 10 реальных секунд при 30/60/144 FPS. (2) Найди, где `CharacterControllerSystem`, прицел и оружие получают `dt`; выпиши все коэффициенты «на кадр» без времени. (3) Для визуальных переходов используй временную формулу, для Bullet проверь число и размер substeps; силы и импульсы должны иметь один понятный момент применения. (4) Сравни результаты и зафиксируй допустимую погрешность. (5) Для Windows loop проверь §7.3: `SystemClass::Run` сейчас обрабатывает только одно `PeekMessage` за итерацию; при плотной очереди сообщений измерь задержку игры и при необходимости вычитывай очередь циклом `while (PeekMessage(...))`.

**Готово, когда:** одинаковая сцена приходит к близкому состоянию при разных FPS и приложение остаётся отзывчивым при движении мыши/окна.

### B3. Компоненты Bullet и управление персонажем — P1/P2 (§26–27, §37.2)

**Теория.** Поля `RigidBodyComponent` имеют смысл только если настройки дошли до `btRigidBody` (`friction`, damping, CCD, angular factor). Gizmo, который телепортирует mesh, но не обновляет Bullet body, создаёт два разных положения одного объекта. Удерживание Space может снова запустить прыжок при приземлении, если проверять только `Down`.

**Пример.** Прыжок по фронту ввода: `if (input.Pressed(GameAction::Jump) && grounded) Jump();`; авто-прыжок — отдельное явно включаемое поведение. Для gizmo динамического тела либо временно переводи его в authoring/kinematic режим и обновляй motion state, либо перестраивай shape/инерцию при масштабе.

**Шаги.** (1) Сравни компонент и реальное создание body в `PhysicsSystem.cpp`; составь таблицу «поле → Bullet setter». (2) Проверь CCD быстрым маленьким телом у тонкой стены, friction на склоне, damping за 10 секунд. (3) Перемести и масштабируй динамический ящик в редакторе, затем запусти Play. (4) Нажми и держи Space при приземлении; реши нужный контракт и закрепи тестом. (5) Проверь, что collider игрока и NPC совпадает с видимой моделью после поворота и смены анимации.

**Готово, когда:** настройка компонента реально меняет физику, collider следует за gizmo, а прыжок ведёт себя по выбранному правилу.

### B4. Collision shape для стен, укрытий и динамических предметов — P2 (§26.3)

**Теория.** Bullet `btBvhTriangleMeshShape` подходит статической геометрии; динамическому вогнутому объекту нужны GImpact или составной набор выпуклых частей. VHACD раскладывает сложную модель на выпуклые hulls. Флаг в компоненте ещё не означает, что весь путь создания shape и добавления body в world реализован.

**Пример.** В `PhysicsSystem.cpp` у compound element `VHACD` оставлен комментарий о пропущенной обработке. Для простой стены достаточно статического box/triangle mesh collider; для динамического вогнутого укрытия понадобится составной convex shape или GImpact. Не выбирай VHACD по названию, пока его путь не реализован и не измерен.

**Шаги.** (1) Сделай тестовое вогнутое укрытие и положи на него динамический предмет. (2) Сравни `ConvexHull`, `TriangleMesh`, `GImpact`, `VHACD` при static/dynamic body: прохождение сквозь стенку, устойчивость, цена CPU. (3) Для каждого нужного режима выпиши точный код создания shape и владение `btTriangleMesh`/hulls. (4) Если VHACD нужен для текущих игровых предметов, доведи путь декомпозиции, кеширования hulls и cleanup; иначе убери обманчивый выбор из редактора. (5) Проверь, что пуля и NPC сталкиваются с тем же укрытием, которое видно игроку.

**Готово, когда:** выбранный shape соответствует реальной Bullet-конфигурации, укрытие блокирует пули и движение ожидаемо, после выгрузки не остаётся объектов в world.

## Блок C. Рендер: от корректности к качеству

Перед изменением шейдера сделай пять контрольных объектов: белый матовый куб, гладкий металл, чёрный rough материал, стеклянная панель и модель персонажа с оружием. Поставь один свет, затем несколько, и сфотографируй одну камеру до/после. Так будет видно, что исправление не ломает другой проход. Для каждого draw pass записывай render target, depth state, blend state, rasterizer state, shader/SRV и параметры камеры.

### C1. Constant buffer не должен переписывать свою память — P0, баг (§18.2)

**Теория.** D3D11 constant buffer выделяется размером, кратным 16 байтам; CPU-структура и HLSL-layout должны соответствовать. В `SkyShaderClass.cpp` буфер создаётся по `sizeof(SkyConstantBuffer)`, а legacy `SetShaderParameters` пишет в него локальную `SkyCB` с двумя матрицами и солнцем. Если размер меньше записываемого, это выход за границу mapped memory.

**Пример.** `static_assert(sizeof(SkyCB) <= alignedBufferBytes);` полезен только если именно `SkyCB` — контракт созданного буфера; лучше один общий `struct alignas(16) SkyCB` для создания и записи. После `Map` проверь `HRESULT` **до** обращения к `mapped.pData`, затем `Unmap`.

**Шаги.** (1) Выпиши `sizeof` обоих структур и HLSL `cbuffer` по смещениям. (2) Выясни, вызывается ли legacy метод сейчас; неактивный код всё равно опасен при будущем подключении. (3) Удали дублирование структур либо сделай отдельный буфер соответствующего размера. (4) Проверь Create/Map failure paths. (5) Прогоняй инициализацию/выгрузку шейдера много раз и смотри Debug Layer.

**Готово, когда:** созданный размер равен реальной схеме данных, Debug Layer молчит, карта буфера корректна и при ошибке Map нет dereference.

### C2. Полный контракт состояния каждого прохода и COM lifetime — P1 (§18.3–18.4, §19)

**Теория.** D3D11 state «прилипает» к context. Если прозрачный проход оставил blending или выключенную запись глубины, следующий draw может выглядеть ошибочно. Сырые `ID3D11*` требуют `Release` и аккуратного cleanup при частичной инициализации; `ComPtr` передаёт владение явно.

**Пример.** Таблица прохода: `Opaque: blend off, depth write on, back-face cull`; `Transparent: alpha blend, depth test on/write off`; `Sky: depth less-equal/write off`. Перед каждым проходом выставляй весь нужный набор, после — не рассчитывай, что «кто-то вернёт назад».

**Шаги.** (1) Составь таблицу всех pass в `Renderer.cpp`: shadow, reflection/refraction, opaque, transparent, particles, first person, UI. (2) Включи D3D11 Debug Layer и проверь утечки при закрытии. (3) Вынеси состояние в именованные методы/объекты, затем явно устанавливай его на входе каждого pass. (4) У каждого ресурса проверь провал на третьем шаге Initialize: предыдущие ресурсы должны освобождаться. (5) Проверь устойчивость при resize окна и повторном создании сцены.

**Готово, когда:** порядок независимых проходов не меняет их картинку, а shutdown не оставляет D3D11 live objects.

### C3. Прозрачность и отражения игровых материалов — P1, часть аудит (§23)

**Теория.** Обычная alpha transparency требует рисования сзади вперёд при `depth test on`, `depth write off`. Сортировка по **целому объекту** может быть неверной для пересекающихся прозрачных поверхностей; сначала реши типичные сцены, затем усложняй. Если в нынешнем уровне есть зеркальная/стеклянная поверхность, reflection/refraction должны получать релевантные lights и корректную позицию камеры, но при отражении позиция *виртуальной* камеры отличается от основной.

**Пример.** Для двух стёкол на расстоянии 3 м и 7 м очередь при прозрачном blending: 7 м → 3 м. Если сначала нарисовать близкое стекло с depth write on, дальнее вообще может не появиться. Это применимо также к прозрачному забралу, стеклу прицела и частицам дыма.

**Шаги.** (1) Расставь две стеклянные панели и предмет за ними; запиши render queue и depth state. (2) Исправь только действительно неверные pass states/сортировку. (3) Если используешь refraction, проверь `Renderer.cpp`: он уже собирает lights и позицию камеры — сначала подтверди результат тестом. (4) Если используешь reflection, проверь его с камерой в разных положениях: specular не должен ломаться от неверного `cameraPosition`. (5) Проверь дым от выстрела и прозрачное стекло перед оружием от первого лица.

**Готово, когда:** оба слоя стекла видны в любом порядке создания сущностей, дым и стекло не скрывают оружие ошибочно, используемые reflection/refraction pass не зависят от случайного состояния предыдущего pass.

### C4. Нормали и цветовой конвейер — P1/P2 (§14.4, §20–21)

**Теория.** Освещение обычно считают в линейном цветовом пространстве. sRGB-текстура при чтении аппаратно декодируется в linear, далее PBR работает в linear. Тон-маппинг и gamma/sRGB conversion выполняются **один раз** в конце HDR pipeline. Если зашить tone mapping в каждый PBR draw в UNORM target, прозрачность и последующие проходы смешивают уже нелинейные значения.

**Пример.** `linearHDR = shade(...)`; после всех HDR проходов `mapped = linearHDR/(1+linearHDR)` (простейший Reinhard); вывод в sRGB render target или явная gamma-конверсия — один выбранный путь, не оба. Для нормали: `normalWS = normalize(mul(normalOS, inverseTranspose(world3x3)))` с соответствующим HLSL порядком умножения.

**Шаги.** (1) Проверь форматы текстур и render targets, где выполняются tone mapping/gamma; нарисуй схему данных от texture load до swapchain. (2) На неравномерно растянутом кубе сравни normal shading до/после normal matrix. (3) Введи один HDR target и финальный postprocess, если текущая архитектура позволяет; иначе сначала документируй ограничения UNORM и исправь двойную gamma. (4) Сравни белую карту, металл и прозрачность при одинаковом свете. (5) Проверь alpha отдельно от RGB — alpha не должен проходить tone mapping.

**Готово, когда:** яркие источники не срезаются до финального этапа, прозрачность не темнеет от двойной gamma, растянутые объекты освещаются правильно.

### C5. Светильники, окружение и тени — P2 (§20.7, §21.3–21.4, §22)

**Теория.** В шейдер передаётся ограниченное число lights (в учебнике — четыре). «Первые четыре в ECS» нестабильны: порядок создания не равен важности для объекта. IBL для PBR — это отдельные diffuse irradiance, specular prefilter и BRDF LUT; просто HDR-текстура как отражение не даёт энерго-согласованное освещение. Тени должны покрывать видимую область и иметь достаточную плотность texels; привязка shadow projection к origin даёт исчезновение теней на удалении.

**Пример.** Для каждого объекта оцени `score = intensity / (distanceSquared + epsilon)`, отсортируй кандидатов и возьми N ближайших/влиятельных; directional light учитывай отдельно. Для тени подстрой orthographic bounds по видимой области и округли light-space center к размеру texel, чтобы не было «ползания» при движении камеры.

**Шаги.** (1) Создай 5–6 lights, меняй порядок создания; проверь, какие реально освещают объект. (2) Сделай детерминированный выбор релевантных lights. (3) Поставь объект далеко от мирового нуля, проверь shadow caster culling и световую камеру; подстрой покрытие и texel snapping. (4) Проверь skinned mesh, alpha cutout и grass в shadow pass. (5) Для IBL отдельно подготовь irradiance/prefilter/BRDF LUT и согласуй поворот sky HDR с PBR reflection UV; добавляй этапы по одному, сохраняя контрольные снимки.

**Готово, когда:** перестановка создания источников не меняет релевантный свет, тени остаются стабильными при движении камеры, ориентация блика совпадает с небом.

### C6. Частицы и взрывы — P2 (§24)

**Теория.** Равномерный радиус `r=R*u` даёт слишком много точек около центра шара; для равномерного объёма нужно `r=R*cbrt(u)`. Для alpha-blended частиц порядок смешивания важен: сортировка всего массива, а потом grouping по texture, может разрушить глобальный порядок. Взрыв за стеной не должен сообщать полный импульс, если нужна физическая окклюзия.

**Пример.** `radius = maxRadius * std::cbrt(random01);` и случайное равномерное направление. Две перекрывающиеся полупрозрачные частицы разной текстуры должны оставаться в порядке дальняя → ближняя; смена текстуры между ними стоит draw call, но сохраняет результат.

**Шаги.** (1) Проверь текущую реализацию sampling в `ParticleSystem.cpp`, не полагайся только на снимок из учебника. (2) Сгенерируй 10 000 точек, посчитай долю внутри половинного радиуса: ожидаемо около `1/8`, если это равномерный объём. (3) В `ParticleRenderer.cpp` проверь порядок при двух texture IDs; исправь сортировку/батчинг лишь при видимом нарушении. (4) Взрыв по обе стороны стены сравни с raycast/attenuation; решение зависит от желаемого геймплея. (5) Сравни стоимость draw calls до/после.

**Готово, когда:** частицы распределены по объёму ожидаемо, перекрытие выглядит одинаково независимо от texture ID, взрыв ведёт себя по выбранному правилу укрытий.

## Блок D. Навигация, анимация, редактор и измерения

### D1. NavMesh: маршруты врага по игровой локации — P2 (§33–34)

**Теория.** Recast строит walkable mesh, Detour ищет маршрут. Статические стены, динамические ящики и другие NPC требуют разной обработки. Tile cache позволяет локально обновлять NavMesh при изменении препятствий; RVO помогает NPC обходить друг друга. Старый маршрут по корабельным комнатам нынешней игре не обязателен.

**Пример.** NPC идёт к последней увиденной позиции игрока за стеной: путь должен обогнуть стену, а физический контроллер пройти по точкам. Если path query возвращает лишь 64 точки, длинный маршрут надо продолжить по частям, а не считать 64-ю точку конечной целью.

**Шаги.** (1) Проверяй ровный тестовый участок без стен, затем стену с проходом, затем движущееся укрытие. (2) Для неудачи распечатай: start/target projected on NavMesh?, число polygon refs, длину path, причину blocked, фактическую позицию capsule. (3) Сверь лимиты 256 refs/64 точек и поведение при превышении. (4) Раздели статическую геометрию и динамические препятствия; обновление NavMesh добавляй лишь если оно нужно настоящей локации. (5) Двух NPC проверь на взаимную блокировку, затем решай, нужен ли RVO.

**Готово, когда:** неуспех пути имеет конкретную диагностическую причину, видимая стена и физический capsule согласованы, длинный маршрут не обрывается молча.

### D2. Анимация и владельцы Transform — P2 (§25, §27, §41)

**Теория.** Skeleton transform проходит `local bone → parent chain → inverse bind → skinning`. Если root motion анимации и CharacterController одновременно двигают мировую позицию, появляется скольжение/рывок. Если кость левой руки привязана к оружию, это runtime-зависимость: порядок обновления оружия, IK и камеры важен.

**Пример.** Для locomotion выбери один источник мирового движения: controller задаёт позицию, а анимация шагает «на месте». Позиции кисти/цевья вычисляй после обновления позы оружия; IK читает свежую цель этого кадра.

**Шаги.** (1) На тестовом персонаже отключай по очереди root motion, controller, IK и смотри, какой слой меняет Transform. (2) Запиши порядок в `ApplicationClass.cpp` и анимационных системах. (3) Проверь двуручный хват на idle, ходьбе, повороте, выстреле и при reload; визуал и collider оружия должны совпадать. (4) По §25.3 HLSL bone buffer рассчитан на 128 костей: сделай модель с 129 костями, потребуй явную ошибку импортера или осознанный fallback, а не тихий пропуск bone ID. Сравни одного персонажа в основном, shadow, transparent, reflection/refraction pass: все должны получить актуальную матрицу костей. (5) Сравни legacy hierarchy path в `assimpmodelclass.cpp` с основным порядком матриц. (6) На крайних углах вращения проверь нормализацию quaternion и отсутствие NaN. Исправляй только обнаруженный конфликт владельцев, а не всю систему анимации разом.

**Готово, когда:** персонаж не телепортируется от смены клипа, ноги не скользят из-за двух источников движения, кисть не тянется за старой позицией оружия.

### D3. Editor gizmo, debug UI и culling cache — P2 (§17.3, §37)

**Теория.** Редактор меняет authoring data; physics и renderer хранят производные данные. После изменения Transform должны обновиться collider, bounds и кэш кандидатов. Debug UI только показывает/задаёт команды, но не должен быть единственным местом, где живёт игровая логика.

**Пример.** Сдвинь укрытие gizmo за пределы кадра и обратно. Его world AABB обязан измениться сразу, иначе frustum culling может скрыть видимый объект. После загрузки другой сцены async-кэш со старой камерой должен быть отклонён по scene epoch из A5.

**Шаги.** (1) Выбери объект, сдвинь/поверни/масштабируй в Editor; сравни mesh, collider, AABB и picking. (2) Проверь асинхронный cache при резком переносе камеры и смене сцены. (3) Вынеси gameplay-команду из debug UI в обычную функцию/систему, UI оставь вызывающим клиентом. (4) Добавь в инспектор минимум: Entity alive, world transform, collider, bounds, render material, visible/cull reason, active constraints. (5) Проверь работу после Save/Load.

**Готово, когда:** gizmo и Play видят один объект, culling не зависит от старой камеры, UI можно закрыть без изменения игровых правил.

### D4. Измерять производительность и диагностировать симптом — P2 (§40–41)

**Теория.** Оптимизация без профиля может ускорить не тот участок. CPU время дели на input/editor, AI/NavMesh, fixed physics, scene update, culling, draw submission, UI и main-thread uploads; GPU — на shadow, reflection/refraction, opaque, transparent, particles, first person, postprocess. Среднее FPS скрывает редкие долгие кадры: храни медиану и 95/99-й процентиль frame time.

**Пример.** На 60 FPS бюджет кадра ≈16.67 мс. Если shadow pass берёт 8 мс, а AI 0.2 мс, переписывать AI ради FPS бессмысленно. Добавь счётчики jobs queued/active/failed, Bullet bodies, render candidates/culled/draw calls, GPU buffers/textures.

**Шаги.** (1) Выбери фиксированную камеру и тестовую сцену. (2) Измерь 300–1000 кадров без первого прогревочного участка. (3) Добавь scoped CPU timers и GPU timestamp queries с корректной задержкой чтения результатов. (4) Запиши baseline в табличку. (5) Меняй один hotspot и сравни и скорость, и качество изображения/симуляции. Для симптома «объект не виден» проходи последовательность из §41: Active → Transform → mesh buffers → material/SRV → culling → depth/blending → near/far.

**Готово, когда:** у каждой оптимизации есть измеримый baseline, а изменение не ухудшает кадр/картинку по скрытой причине.

## Блок E. Возможности, которых учебник пока не считает готовыми

Эти пункты — **развитие**, не срочные багфиксы. Делай после первой недели и блоков A–C, если они нужны твоей игре.

### E1. Боевой AI: память, осторожность и роли — P3 (§32.4)

**Теория.** Боевой AI выбирает действие по состоянию или score. Память не должна давать врагу «телепатическое» знание текущей позиции игрока: сохраняй `lastSeenPosition` и время наблюдения. Hysteresis предотвращает переключение состояний на границе score.

**Пример.** `switchToAttack` только если `attackScore > currentScore + 0.15f`; выход из атаки — когда `attackScore < 0.25f`. Для двух врагов роли могут различаться: один удерживает игрока огнём из укрытия, другой идёт к последнему замеченному месту; оба не должны менять роль каждый кадр.

**Шаги.** (1) После рабочего одиночного врага из первого файла добавь двух. (2) Покажи score/цель/lastSeenTime в debug UI. (3) Сделай память ограниченной по времени и разные реакции на слышимый выстрел/видимого игрока. (4) Добавь осторожность при низком HP только при наличии понятного эффекта: отход к укрытию или задержка выстрела. (5) Проверь, что ручная команда `NpcCommand`, если она используется в новом AI, сохраняет приоритет.

**Готово, когда:** поведение объяснимо значениями score, враги не знают невидимую цель, два NPC не конфликтуют за одну задачу.

### E2. Продвинутый PBR и тени боевой сцены — P3 (§20–22)

**Теория.** IBL, cascaded shadow maps, weighted blended OIT и SSR — отдельные техники, каждая со своей стоимостью и ограничениями. Выбирай по художественной цели боевой сцены: читаемость силуэта врага, металл винтовки, тени укрытий и дым от выстрела.

**Пример.** Переход от одной shadow map к двум cascades: ближняя каскадная область получает больше texels на метр, дальняя — меньше; на границе каскад нужен blend, иначе виден шов. Если тень врага вблизи «квадратная», сначала измерь texels на метр и shadow bias, а не включай все эффекты сразу.

**Шаги.** (1) Определи один визуальный симптом, который мешает сцене. (2) Сделай до/после кадр и GPU budget. (3) Реализуй одну технику с fallback. (4) Проверь разное освещение, разрешение экрана и угол камеры. (5) Оставь технику только если качество оправдывает её стоимость.

**Готово, когда:** новая графика решает названный симптом и не ломает базовые материалы, отражения и производительность.
