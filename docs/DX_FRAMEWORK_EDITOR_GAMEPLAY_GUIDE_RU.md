## 1. Назначение руководства

Это руководство рассчитано не только на автора движка, но и на нового разработчика уровней, который впервые открыл DX Framework. Основная цель последних улучшений — перенос повседневной настройки gameplay из C++ в редактор:

- создание готовых сущностей через `Quick Create`;
- настройка зон, действий, NPC и экипажа через Inspector;
- визуальная работа с Transform и привязкой к сетке;
- сохранение логических сущностей вместе со сценой;
- проверка результата в Play Mode;
- отображение состояния игрока, корабля, экипажа и инвентаря в HUD.

Движок использует ECS: сущность является идентификатором, а её возможности задаются компонентами. Поэтому редактор не ограничивает объект одним заранее заданным классом — одну сущность можно собрать из нужного набора данных.

## 2. Быстрый старт

### 2.1. Запуск готовой Debug-сборки

После успешной сборки исполняемый файл находится по пути:

```text
x64\Debug\DX_FrameWork.exe
```

Для Release-сборки:

```text
x64\Release\DX_FrameWork.exe
```

Запускайте движок из корня проекта или через Visual Studio, чтобы относительные пути вида `assets/model/Rifle_M4_CC0.glb` разрешались относительно проекта.

Поддерживаемая и проверяемая цель проекта — `x64`. Конфигурации `Debug|x64` и `Release|x64` входят в автоматическую проверку. В основном `.vcxproj` ещё присутствуют записи Win32, но 32-битная цепочка зависимостей, runtime DLL и проект core tests для неё не настроены и не проверяются; Win32 не следует считать поддерживаемой платформой.

### 2.2. Минимальный тест новых возможностей

1. Откройте редактор.
2. В верхнем меню выберите `Create -> Crew NPC (logic)`.
3. Выберите `Create -> Rifle Pickup`.
4. Выберите `Create -> Trigger Zone`.
5. В Inspector у зоны оставьте действие `Show HUD message` и измените текст сообщения.
6. Нажмите `Ctrl+S` и сохраните сцену как JSON.
7. Нажмите `F5`, чтобы войти в Play Mode.
8. Войдите в зону и проверьте уведомление HUD.
9. Наведитесь на винтовку и нажмите `E`.
10. Переключите слоты клавишами `1`, `2`, `3`; нажмите `G`, чтобы выбросить активную винтовку.
11. Нажмите `P`, чтобы остановить симуляцию, затем `[` или `]`, чтобы изменить её скорость.
12. Нажмите `F5`, чтобы вернуться в Editor Mode.

Важно: `F5` переключает режим, но не откатывает сцену. Play-in-Editor работает с тем же ECS Registry, что и редактор, без автоматического snapshot/restore. Подобранные предметы, перемещённые физикой объекты, повреждения и другие runtime-изменения могут остаться в Registry после возврата в Editor. Чтобы вернуть сохранённое авторское состояние, повторно загрузите Scene JSON; не сохраняйте сцену после Play, если не хотите зафиксировать runtime-изменения.

Если у шаблона NPC нет модели, это нормально: `Crew NPC (logic)` создаёт прежде всего gameplay-сущность. Для полноценного персонажа ей потребуется визуальная модель, корректные клипы анимации и физический/character-controller контур.

## 3. Модель редактора: аналогии с UE5

DX Framework не копирует внутреннее устройство Unreal Engine, но для освоения удобно использовать следующие аналогии:

| DX Framework | Ближайшая аналогия в UE5 | Назначение |
|---|---|---|
| Scene JSON | Level / Map | Набор сущностей и их авторских данных |
| Entity | Actor | Уникальный объект сцены |
| ECS Component | Actor Component / набор свойств | Добавляет сущности данные и поведение |
| Scene Hierarchy | World Outliner | Поиск и выбор объектов сцены |
| Inspector | Details Panel | Изменение компонентов выбранной сущности |
| Quick Create | Place Actors / Add Actor | Создание готового шаблона |
| Editor Mode | Level Editing | Изменение авторских данных |
| Play Mode | Play In Editor | Запуск gameplay и runtime-систем в том же Registry; автоматического отката нет |
| `ActiveComponent` | Actor Enabled / active state | Участвует ли сущность в сцене |

Ключевое отличие ECS: тип сущности определяется не наследованием, а составом компонентов. Например, винтовка для подбора состоит как минимум из визуального объекта, `WeaponComponent`, `WeaponPickupComponent`, `InteractionComponent` и, при необходимости, `RigidBodyComponent`.

## 4. Интерфейс редактора

### 4.1. Главное меню

Верхняя строка содержит:

- `File` — сохранение и загрузка сцены;
- `Create` — быстрые шаблоны gameplay-сущностей и зон;
- `Edit` — удаление выделенного объекта;
- `View` — показ неактивных сущностей и Transform Snapping;
- счётчики сущностей, мешей, источников света и спрайтов.

Команда `Save Scene` становится доступной после выбора пути сохранения. Для первого сохранения используйте `Save As...` или `Ctrl+S`, после чего повторный `Ctrl+S` сохраняет в последний путь.

### 4.2. Панель быстрых действий

Плавающая панель редактора содержит:

- `+ Create` — то же меню шаблонов, что и верхнее `Create`;
- `Save` / `Save As`;
- `Delete` — удаление выбранного элемента с подтверждением;
- `Snap` — привязка значений Transform;
- `Settings` — шаг позиции, вращения и масштаба.

Стандартные шаги задаются отдельно:

- `Position step` — шаг позиции;
- `Rotation step` — шаг вращения в градусах;
- `Scale step` — шаг масштаба.

Привязка применяется к изменениям Transform в Inspector. Вращение в Inspector представлено в градусах, хотя внутренний Transform движка хранит ориентацию в своём runtime-формате.

### 4.3. Scene Hierarchy

`Scene Hierarchy` выполняет роль World Outliner. Поле поиска фильтрует элементы без учёта регистра по имени, типу или идентификатору сущности. Кнопка `X` очищает фильтр.

Иерархия показывает не только меши, но и логические gameplay-объекты:

- комнаты и сгруппированные панели корпуса;
- World Areas;
- коллайдеры;
- логические источники света;
- триггеры;
- NPC без меша;
- точки взаимодействия;
- другие сущности с Transform.

Флаг `Show inactive` раскрывает сущности без активного состояния. Неактивные элементы отображаются приглушённым цветом.

### 4.4. Inspector / Details

В начале Inspector показаны:

- `Entity ID`;
- редактируемое имя;
- `Active in scene`;
- краткий список найденных компонентов.

Далее идут секции компонентов. Их состав зависит от выбранной сущности. Для общих объектов доступны Transform, физика, взаимодействие, NPC, оружие, комнаты, зоны и другие системы проекта.

Transform предоставляет:

- Position;
- Rotation в градусах;
- Scale;
- отдельный сброс значений;
- привязку к настроенному шагу.

В нижней части Inspector есть `+ Add Component`. В открывшемся списке можно искать компонент по имени. Уже добавленные компоненты отключены или помечены соответствующим статусом.

### 4.5. Удаление

Удаление из Toolbar, меню `Edit` или клавишей `Delete` открывает подтверждение с именем/ID выбранного элемента. Операция необратима в текущей сессии: встроенной истории Undo/Redo пока нет.

## 5. Горячие клавиши

### 5.1. Editor Mode

| Клавиша | Действие |
|---|---|
| `Ctrl+S` | Сохранить в последний путь или открыть Save As при первом сохранении |
| `Ctrl+O` | Открыть диалог загрузки сцены |
| `Delete` | Запросить удаление выбранной сущности/спрайта |
| `F5` | Перейти в Play Mode |
| `Space`, `K` | Отладочная пауза/шаг `TimeManager` только в Editor |
| `Esc` | Выход из приложения только в Editor |

Горячие клавиши редактора не срабатывают, пока фокус находится в текстовом поле.

### 5.2. Play Mode

| Клавиша | Действие |
|---|---|
| `F5` | Вернуться в Editor Mode без автоматического восстановления сцены |
| `F2` | Освободить/захватить курсор для runtime-интерфейса ImGui |
| `W/A/S/D`, `Shift`, `Space` | Движение, бег, прыжок |
| `ЛКМ` или `H` | Стрельба |
| `L` | Ремонт при удержании |
| `E` | Взаимодействовать; если канал/панель уже открыты — закрыть их независимо от направления взгляда |
| `Esc` | Закрыть открытую NPC/устройственную панель |
| `1`, `2`, `3` | Выбрать соответствующий слот оружия |
| `G` | Выбросить оружие из активного слота |
| `P` | Пауза/продолжение игровой симуляции |
| `[` | Уменьшить Time Scale на `0.25` |
| `]` | Увеличить Time Scale на `0.25` |
| `F3` | Показать/скрыть отладочную телеметрию HUD |
| `Tab` | Показать/скрыть журнал событий корабля |

Привязки этих игровых действий находятся в `src/Gameplay/Player/GameplayInputSystem.cpp`. `ПКМ` и средняя кнопка уже считываются как действия прицеливания, но сама механика прицела пока не подключена. Пошаговый пример расширения ввода есть в разделе 7.4 архитектурного учебника.

`P`, `[` и `]` изменяют только время симуляции. Интерфейс, ввод и HUD продолжают обновляться даже при паузе. При нулевой simulation delta не выполняются стрельба, урон, AI, ремонт, двери, подбор/выброс предметов и события Trigger Zone.

## 6. Quick Create

Меню открывается через `Create` в главном меню или `+ Create` на Toolbar.

### 6.1. Gameplay

#### Empty Entity

Создаёт логическую сущность с именем и Transform без меша. Используйте как точку привязки, цель Trigger Action или основу для собственного набора компонентов.

#### Interaction Point

Создаёт логическую точку с `InteractionComponent`:

- включена по умолчанию;
- дистанция взаимодействия — `3.0`;
- подсказка — `Interact`.

Для взаимодействия луч должен попасть в физический объект сущности. Если точка остаётся полностью логической и не имеет доступного для raycast коллайдера, добавьте подходящую физическую форму или привяжите логику к видимому объекту.

#### Point Light

Создаёт логическую сущность и добавляет `LightComponent`.

#### Crew NPC (logic)

Создаёт заготовку члена экипажа со следующими компонентами:

- `InteractionComponent` с подсказкой `Talk`;
- `NPCComponent`;
- `NpcBrainComponent`;
- `NPCMovementComponent`;
- `CharacterMovement`;
- `CharacterController`;
- `CharacterPhysicsTuningComponent`;
- `AnimationComponent`;
- `CrewMemberComponent`.

Это логическая заготовка, а не законченный визуальный персонаж. Назначьте модель, клипы и физические параметры перед использованием в полноценной сцене.

#### Rifle Pickup

Загружает `assets/model/Rifle_M4_CC0.glb` и создаёт готовую подбираемую винтовку:

- имя `Rifle Pickup`;
- `WeaponComponent`;
- `WeaponPickupComponent`;
- `InteractionComponent` с подсказкой `Pick up rifle` и дальностью `3.0`;
- динамический box rigid body массой `1.5`;
- размер формы по умолчанию `0.35 x 0.18 x 0.90`.

### 6.2. Zones

#### Trigger Zone

Создаёт сущность с Transform, `TriggerZoneComponent` и `TriggerActionComponent`. Начальный box имеет half extents `1.5 x 1.0 x 1.5`, то есть полный размер `3 x 2 x 3`.

#### Spawn Area

Создаёт `WorldAreaComponent` типа Spawn размером `4 x 2 x 4`.

#### Grass Area

Создаёт Grass Area размером `10 x 1 x 10`.

#### No Grass Area

Создаёт исключающую траву область размером `10 x 1 x 10`.

#### Forest Area

Создаёт Forest Area размером `20 x 2 x 20`.

### 6.3. Где появляется новый объект

Редактор выбирает позицию последовательно:

1. Если выделена сущность с Transform — на один метр правее по X.
2. Если выделена World Area — на один метр правее её центра.
3. Иначе — в позиции, заданной в параметрах обычного Spawn Object.

После создания новая сущность автоматически выделяется.

## 7. Сущности и компоненты

### 7.1. Базовое правило ECS

`Entity` — числовой ID. Сам по себе он ничего не делает. Данные находятся в компонентах, а системы проходят по подходящим наборам компонентов.

Примеры:

- Transform + Mesh Renderer — видимый объект;
- Transform + Trigger Zone — невидимый gameplay-объём;
- NPC + Brain + Movement + Character Controller — автономный персонаж;
- Weapon + Weapon Pickup + Interaction — оружие, которое можно подобрать;
- Inventory — три ссылки на сущности-предметы и индекс активного слота.

### 7.2. Имя и активность

`NameComponent` отвечает за человекочитаемое имя в редакторе и HUD.

`ActiveComponent` означает, что сущность активна в сцене. Встроенные Trigger Actions `Set entity active` и `Toggle entity active` добавляют или удаляют именно этот компонент. Рендер, физические тела, character controller, AI, двери, урон и Trigger Zone учитывают это состояние.

Неактивные авторские сущности сохраняются в JSON с полем `active: false` и восстанавливаются при загрузке. Поэтому свет, NPC, физический объект или логическую цель можно подготовить выключенными и затем активировать зоной без C++.

### 7.3. Ссылки между сущностями

Некоторые компоненты хранят `Entity`-ссылки:

- `TriggerZoneComponent.linkedEntity`;
- `TriggerActionComponent.target`;
- слоты `InventoryComponent`;
- владелец оружия и другие существующие связи движка.

При загрузке сцены старые ID заменяются новыми через таблицу remap. Remap применяется только к сущностям, восстановленным из `objects` Scene JSON; уже существующие/заново импортированные GLB-сущности не переписываются случайно при совпадении числового ID. Не редактируйте сохранённые ID вручную без необходимости: отсутствующая JSON-цель превратится в недействительную ссылку.

## 8. Триггерные зоны

### 8.1. Архитектура

Триггер — обычная ECS-сущность с `TransformComponent` и `TriggerZoneComponent`. Bullet rigid body или ghost object ему не нужен. `TriggerZoneSystem` проверяет мировую позицию каждой подходящей сущности как точку внутри объёма.

Преимущества:

- низкая стоимость авторской зоны;
- отсутствие физического контакта с игроком;
- безопасное редактирование размеров и вращения;
- одинаковая работа для Player, NPC и Other;
- детерминированный порядок обработки по Entity ID.

### 8.2. Форма и Transform

Доступны две формы:

- `Box` — ориентированный box, учитывающий позицию, вращение и масштаб Transform;
- `Sphere` — сфера, масштабируемая по наибольшему абсолютному компоненту масштаба Transform.

Поля:

| Поле | Назначение |
|---|---|
| `Enabled` | Включает обработку зоны |
| `Shape` | Box или Sphere |
| `Local center` | Смещение центра относительно Transform |
| `Half extents` | Половина размера Box по каждой оси |
| `Radius` | Локальный радиус Sphere |
| Transform Position | Мировое положение сущности зоны |
| Transform Rotation | Ориентация Box |
| Transform Scale | Масштабирует объём |

Для Box Inspector показывает полный размер и предоставляет пресеты `3 x 2 x 3` и `10 x 3 x 10`.

### 8.3. Фильтр акторов

В `Accepted actors` доступны независимые флаги:

- `Player` — сущность с `PlayerGameTag`;
- `NPC` — сущность с `NPCComponent`;
- `Other` — активная динамическая сущность с `RigidBodyComponent`, не являющаяся Player или NPC.

По умолчанию включены Player и NPC.

Статические меши, логические точки, соседние зоны и неактивные сущности не считаются `Other`. Это защищает one-shot зоны от случайной активации при загрузке уровня. Флаг полезен для ящиков, выброшенного оружия и других динамических props.

### 8.4. События Enter, Stay и Exit

Зона генерирует `TriggerZoneEvent` со следующими данными:

- ID зоны;
- ID вошедшего актора;
- тип актора;
- `Enter`, `Stay` или `Exit`;
- строковый `Event ID`;
- необязательная linked entity;
- время зоны.

`Enter` возникает при пересечении границы снаружи внутрь. `Exit` парно возникает для ранее активированного пересечения при выходе. `Stay` возникает, пока актор остаётся внутри и включён `Emit Stay events`.

`Stay interval = 0` означает одно событие на каждый update симуляции. Положительное значение ограничивает частоту, например `1.0` — примерно одно Stay в секунду игрового времени.

### 8.5. One Shot и Cooldown

`One shot` принимает только первый разрешённый `Enter` после запуска Play. Актор, который активировал зону, всё равно получает последующие `Stay` и `Exit`, чтобы жизненный цикл события оставался парным.

`Cooldown` хранится отдельно для каждого актора. Если повторный вход произошёл слишком рано, `Enter` отклоняется. Актор должен выйти и пересечь границу снова после окончания cooldown.

Runtime-состояние зоны — текущие пересечения, cooldown и признак использованного one-shot — не хранится в компоненте и сбрасывается при новом Play/Reset.

### 8.6. Event ID и Linked Entity

`Event ID` — стабильная строка для будущих квестов, скриптов или специфических систем игры. Встроенный `TriggerAction` может работать без кода, но событие всё равно несёт `Event ID`.

`Linked entity` — необязательная ссылка на объект сцены. Если у Trigger Action не выбрана собственная цель, он использует linked entity зоны.

Рекомендация по именованию Event ID:

```text
Deck02.EngineRoom.PlayerEntered
Airlock.InnerDoor.Exit
Crew.Quarters.AlarmZone
```

### 8.7. Визуализация в редакторе

`Show debug shape` включает отображение объёма в Editor Mode. `Debug color` задаёт его цвет и прозрачность. Box рисуется ориентированным wireframe-объёмом, а Sphere — настоящим сферическим wireframe из трёх взаимно перпендикулярных больших окружностей. Радиус и мировой центр визуализации соответствуют сферической проверке `TriggerZoneSystem`.

## 9. Trigger Action: логика без кода

`TriggerActionComponent` связывает событие зоны с одним встроенным действием. Шаблон `Trigger Zone` добавляет этот компонент автоматически. Если он был удалён, Inspector предлагает `Add Trigger Action`.

### 9.1. Когда выполнять действие

Можно независимо включить:

- `On Enter`;
- `On Stay`;
- `On Exit`.

По умолчанию включён только `On Enter`.

Не включайте `On Stay` для тяжёлых или переключающих действий без `Stay interval`: при нулевом интервале действие будет выполняться каждый кадр симуляции.

### 9.2. Доступные действия

#### Emit event only

Не выполняет встроенную мутацию, но `TriggerZoneEvent` с `Event ID` остаётся в очереди. Используется как точка расширения для будущей квестовой или скриптовой системы.

#### Show HUD message

Показывает уведомление в верхней центральной части HUD.

Поля:

- `HUD message` — текст;
- `Duration` — длительность, минимум `0.1` секунды реального update HUD/action feedback.

Если текст пуст, система использует `Event ID`.

#### Set entity active

Добавляет или удаляет у цели `ActiveComponent` в соответствии с `Target value`. При выключении физическое тело или character capsule перестают участвовать в столкновениях, а AI/дверные и damage-системы пропускают сущность; при включении runtime-ресурсы восстанавливаются.

#### Toggle entity active

Переключает наличие `ActiveComponent` у цели при каждом выполнении.

#### Set door open

Устанавливает `DoorComponent.isOpen` у целевой сущности.

### 9.3. Выбор цели

В `Target entity` можно:

- выбрать конкретную сущность с Transform;
- оставить `Use Trigger linked entity`.

Во втором случае действие берёт цель из `TriggerZoneComponent.linkedEntity`.

Выбирайте устойчивую авторскую сущность, которая сама сериализуется в Scene JSON. Прямая авторская ссылка на временную импортированную сущность с `ShipPartComponent` не поддерживается и блокируется authoring/persistence-путём: сохраняется корень корабля, а части пересоздаются при загрузке. Для цели используйте корень, сериализуемый контроллер или стабильную логическую proxy-сущность.

### 9.4. Invert value on Exit

Если действие запускается на `Exit` и включён `Invert value on Exit`, выход применяет значение, противоположное `Target value`.

Типичный сценарий:

- Action: `Set door open`;
- On Enter: включено;
- On Exit: включено;
- Target value: `true`;
- Invert on Exit: включено.

Результат: вход открывает дверь, выход закрывает её.

### 9.5. Когда всё же нужен C++

Встроенный action выполняет только одно действие. Для цепочек, условий, задержек, квестовых стадий, сохранения сюжетного состояния и сложных реакций создайте систему-потребитель `TriggerZoneEvent`, фильтрующую события по `eventId`.

## 10. Взаимодействие с NPC

### 10.1. Поиск цели

`InteractionSystem` делает raycast из камеры, исключает собственный физический объект игрока и проверяет дальность.

NPC взаимодействует по умолчанию даже без `InteractionComponent`. Для такого NPC используется стандартная дистанция `3.0`. Добавленный `InteractionComponent` позволяет изменить prompt и max distance.

Особое правило:

- NPC без `InteractionComponent` — доступен для взаимодействия;
- NPC с включённым `InteractionComponent` — доступен с авторскими параметрами;
- NPC с выключенным `InteractionComponent` — явно исключён из взаимодействия.

### 10.2. Подсказки

При наведении система формирует:

- `Talk to <name>`, если у NPC есть имя;
- `Talk`, если имя пусто;
- авторский prompt из `InteractionComponent`, если он задан.

При доступной цели прицел меняет цвет, а под ним появляется подсказка с клавишей `E`.

### 10.3. Панель NPC

Нажатие `E` открывает `CREW LINK // LOCAL CHANNEL`. Панель показывает:

- имя;
- роль экипажа;
- текущее состояние AI;
- описание;
- автономное назначение или текущий status;
- подсказку `E CLOSE CHANNEL`.

Если панель уже открыта, `E` или `Esc` закрывают её независимо от направления взгляда; это нажатие `E` не открывает другую цель в тот же кадр. Канал также закрывается при отходе дальше авторской дистанции плюс один метр, при деактивации/уничтожении сущности, выключении взаимодействия и при выходе из Play Mode.

### 10.4. Авторские данные NPC

Для качественного результата заполните в Inspector:

- Name;
- NPC name и description;
- hostility;
- движение и дистанции;
- animation bindings;
- Crew role, on-duty и repair skill.

## 11. Crew Task Coordinator и «живой мир»

### 11.1. Идея системы

Игра строится вокруг космического мира, где игрок не обязан быть главным героем каждого события. Поэтому `CrewTaskCoordinator` делает NPC участниками симуляции, а не декорациями, ожидающими команды игрока.

Если на корабле появилась пробоина или сломалось ремонтируемое оборудование, экипаж сам распределяет работу. Игрок может увидеть последствия, помочь, проигнорировать инцидент или находиться в другой части корабля — мир продолжает жить.

### 11.2. Роли экипажа

`CrewMemberComponent` поддерживает:

| Роль | Базовая склонность к ремонту |
|---|---:|
| Generalist | `0.90` |
| Engineer | `1.25` |
| Operations | `1.05` |
| Security | `0.72` |
| Medic | `0.62` |

Operations получает дополнительный бонус для генераторов энергии и кислорода. `Repair skill` ограничивается диапазоном `0.25–2.0` и влияет сразу на два этапа:

- умножает score при выборе исполнителя задачи;
- изменяет фактическую скорость ремонта в `StateSystem`.

Для автономного NPC прогресс за update рассчитывается как:

```text
progressDelta = requiredProgress * deltaTime * repairSkill / repairDuration
```

Таким образом, `1.0` — нейтральная скорость, `0.5` даёт половину базовой скорости, а `2.0` — двойную. Значение больше `2.0` или меньше `0.25` при выполнении всё равно ограничивается этим диапазоном.

### 11.3. Какие задачи учитываются

Координатор собирает сущности с `RepairableComponent`, если:

- объект ещё не отремонтирован;
- пробоина ещё не герметизирована; или
- здоровье `DamageableComponent` ниже максимума.

Поддерживаются типы задач:

- `Seal hull breach`;
- `Repair equipment`.

### 11.4. Распределение задач

Последовательность каждого update:

1. Удаляются недействительные claims.
2. Собираются и сортируются ремонтные цели.
3. Собираются и сортируются NPC.
4. Пропускаются hostile, off-duty и NPC с активной ручной debug-командой.
5. Сохраняется прежнее допустимое назначение.
6. Для свободного NPC вычисляется score каждой незанятой цели.
7. На выбранную цель добавляется `CrewTaskClaimComponent` с assignee, типом, приоритетом и временем.
8. Brain переводится в движение к ремонту.

Score учитывает серьёзность инцидента на `65%`, близость на `35%`, роль и навык. Цели за пределами `NpcBrainComponent.detectionRange` не рассматриваются.

Claim хранится на самой ремонтируемой сущности. Благодаря этому два NPC не бегут к одной и той же пробоине, а Inspector/debug-система может понять, кто владеет задачей, без скрытой глобальной таблицы.

Когда назначенный член экипажа полностью закрывает пробоину, `RepairSystem` увеличивает его `completedTasks` до уничтожения сущности пробоины и очищает соответствующее назначение. Это важно именно для пробоин: после `DestroyEntity` coordinator уже не смог бы найти claim на следующем update. Счётчик показывается в Inspector, но остаётся runtime-данными текущего Registry и не сериализуется в Scene JSON.

### 11.5. Порядок AI pipeline

Порядок интеграции является частью контракта:

```text
NpcUtilitySystem
    -> CrewTaskCoordinator
    -> StateSystem
    -> CharacterFacingSystem
    -> CharacterControllerSystem
    -> AnimationController
```

Utility сначала оценивает намерения, координатор делит общие инциденты, State строит движение/маршрут, затем физика и анимация применяют результат.

### 11.6. HUD экипажа

Панель `CREW NETWORK` показывает:

- число занятых и доступных членов экипажа;
- количество открытых ремонтных задач;
- паузу симуляции;
- изменённый Time Scale.

Так игрок видит, что корабль функционирует как система, а не как сцена, существующая только вокруг него.

## 12. Игровой HUD

HUD рендерится только в Play Mode и оформлен как интерфейс корабельного/скафандрового терминала.

### 12.1. Основные блоки

- `EVA SUIT // LIFE SUPPORT` — здоровье, выносливость и кислород игрока;
- Environment — давление, кислород и температура текущей комнаты;
- `CREW NETWORK` — доступный/занятый экипаж и открытые задачи;
- три слота оружия;
- центральный прицел;
- interaction prompt;
- корабельное предупреждение;
- уведомления Trigger Action и инвентаря;
- панель взаимодействия с NPC;
- debug telemetry;
- Ship Event Log.

Цвета меняются при опасных значениях. Например, низкое здоровье, кислород или давление используют тревожный оттенок, а доступная интерактивная цель подсвечивает прицел.

### 12.2. Инвентарь в HUD

В нижней части экрана находятся три слота. Активный слот выделен. Для предмета используется `NameComponent`; если имя недоступно, HUD пытается вывести имя модели оружия, иначе показывает `RIFLE`/`ITEM`. Пустой слот отображается как `EMPTY`.

### 12.3. Уведомления

Успешные операции инвентаря показываются зелёным, ошибки — красным. Trigger Action `Show HUD message` использует то же центральное место уведомлений. Если одновременно видимы оба сообщения, интеграция приложения отдаёт приоритет feedback инвентаря.

### 12.4. Debug telemetry

`F3` показывает:

- FPS;
- длительность кадра;
- CPU-время рендера;
- количество mesh-объектов;
- main/shadow rendered objects;
- статистику room culling;
- кислород игрока;
- параметры атмосферы комнаты.

### 12.5. Журнал корабля

`Tab` открывает журнал последних событий: пробоины, ремонт, отказы оборудования, brownout, пожары и тушение. При открытом журнале скрываются прицел, inventory prompt и часть контекстного интерфейса.

## 13. Инвентарь и подбор винтовок

### 13.1. Устройство инвентаря

`InventoryComponent` содержит ровно три слота и индекс активного слота. Каждый слот хранит ссылку на сущность предмета, а не копию данных оружия. Поэтому патроны, cooldown, профиль визуала и будущие уникальные свойства остаются на самой сущности.

В начале Play `InventorySystem::EnsureInventory`:

- создаёт Inventory у игрока при отсутствии;
- очищает недействительные/повторяющиеся ссылки;
- принимает legacy `EquippedWeaponComponent` в первый свободный слот;
- синхронизирует активный слот с экипированным оружием.

### 13.2. Что можно подобрать

В текущем варианте инвентаря принимаются только сущности с `WeaponComponent`. Для взаимодействия в мире оружию нужен включённый `WeaponPickupComponent` и доступная интерактивная цель.

`WeaponPickupComponent` задаёт:

- `Enabled`;
- `Equip on pickup`;
- создание физики при выбрасывании;
- массу после выбрасывания;
- размер box collider;
- prompt.

### 13.3. Подбор

1. Наведите прицел на винтовку.
2. Дождитесь подсказки `E`.
3. Нажмите `E`.

Система сначала пытается использовать выбранный пустой слот, иначе первый свободный. После успеха:

- устанавливается владелец оружия;
- при `Equip on pickup` слот становится активным;
- world interaction и rigid body удаляются;
- сущность становится неактивной в мире, но сохраняется как предмет по ссылке;
- HUD сообщает номер слота.

Если все три слота заняты, появляется `Inventory is full`, а винтовка остаётся в мире.

### 13.4. Переключение

Клавиши `1`, `2`, `3` выбирают слот напрямую. Выбор пустого слота допустим и убирает активное оружие. HUD сообщает, что слот пуст.

`InventorySystem` также имеет API выбора следующего/предыдущего слота и swap, но в текущем пользовательском управлении к ним не привязаны отдельные клавиши или drag-and-drop UI.

### 13.5. Выбрасывание

`G` извлекает предмет из активного слота и помещает ту же сущность перед камерой:

- примерно на `1.25` метра вперёд;
- с вертикальным смещением `0.35`;
- возвращает `ActiveComponent`;
- возвращает `InteractionComponent`;
- при включённой настройке создаёт динамический box rigid body.

Оружие можно снова подобрать. Если активный слот опустел, система выбирает первый занятый слот; при полностью пустом инвентаре оружие снимается.

### 13.6. Владение

Оружие с `WeaponOwnerComponent`, принадлежащее другой сущности, нельзя подобрать. Это уже позволяет расширить систему до личного оружия NPC и экипажа без копирования предметов.

## 14. GameTimer и скорость симуляции

### 14.1. Назначение

`GameTimer` — часы игровой симуляции. Его scaled delta передаётся в gameplay, AI, двери, оружие, ремонт, персонажей, анимацию, урон, частицы, физику, воду и scene update.

UI, ввод, камера редактора и HUD используют реальное frame delta. Поэтому пауза мира не «замораживает» интерфейс.

В Editor Mode world-, physics- и atmosphere-update вызываются с нулевой delta. Это сохраняет синхронизацию редакторных данных, но не продвигает физику, AI, повреждения, давление и остальные gameplay-процессы до входа в Play. Исключение — UV-анимация воды: она остаётся чисто визуальной и может обновляться по реальному времени. Нулевая delta в Editor уменьшает случайные мутации, но не заменяет snapshot: изменения, уже сделанные в общем Registry во время Play, по F5 не откатываются.

### 14.2. Формула

```text
simulationDelta = max(realDelta, 0) * timeScale
```

При паузе `simulationDelta = 0`.

`timeScale` ограничен диапазоном `0.0–16.0`. Отрицательное значение становится нулём.

### 14.3. Управление

- `P` — переключить pause;
- `[` — уменьшить Time Scale на `0.25`;
- `]` — увеличить Time Scale на `0.25`.

HUD показывает `SIM PAUSED` или `TIME xN`, если scale отличается от `1.0`.

### 14.4. Жизненный цикл

При входе в Play:

- Timer сбрасывается к `0`;
- Time Scale становится `1.0`;
- pause снимается;
- журнал событий очищается;
- runtime-состояние триггеров сбрасывается.

Это даёт чистое состояние часов, журнала и trigger cooldown/one-shot, но не означает полный сброс сцены. Editor и Play используют общий ECS Registry: F5 не создаёт snapshot и не восстанавливает Transform, здоровье, Active state, инвентарь или другие изменённые компоненты. Для действительно чистого повторного прогона сначала перезагрузите сохранённую сцену.

### 14.5. WorldEvent и WorldEventLog

`WorldEvent` — не таймер и не команда, а историческая запись о значимом факте мира: открылась/закрылась пробоина, оборудование отказало, было уничтожено или отремонтировано, начался/потушен пожар, возник дефицит питания. Запись содержит тип, время из `GameTimer`, source/subject/room и severity.

`WorldEventLog` хранит до `512` последних записей, удаляя самые старые. Damage и Repair systems добавляют события, а HUD показывает историю по `Tab`. Это основа для будущих корабельных новостей, репутации, статистики, реакции NPC и save-game — системы могут реагировать на то, что произошло без жёсткой связи друг с другом.

Не путайте его с `EventQueue`:

- `EventQueue` — краткоживущая шина команд/сигналов одного кадра (`InteractionEvent`, `TriggerZoneEvent`, `DoorOpenedEvent`);
- `WorldEventLog` — ограниченная хронология уже произошедших фактов для UI и систем высокого уровня.

Обработка `EventQueue` зависит от порядка систем внутри кадра. Очередь очищается в начале каждого `ApplicationClass::Frame`, затем producer должен сгенерировать событие до соответствующего consumer. Это не немедленная глобальная рассылка и не очередь с гарантированной доставкой в следующем кадре: consumer, вызванный раньше producer, не увидит позднее событие, а в начале следующего кадра оно будет очищено. При добавлении новой связи явно располагайте consumer после producer либо проектируйте отдельное устойчивое состояние/журнал.

При новом Play журнал очищается. Для постоянной истории кампании его следует включить в отдельную Save Game, а не в авторский Scene JSON.

## 15. Сохранение сцен: JSON v2

### 15.1. Верхний уровень

Новая сцена сохраняется в формате:

```json
{
  "scene_name": "MyLevel",
  "version": 2,
  "objects": []
}
```

`version = 2` отмечает расширенный набор сериализуемых gameplay-компонентов.

### 15.2. Что добавлено в v2

Сохраняются авторские данные:

- `WorldAreaComponent`;
- `InteractionComponent`;
- `TriggerZoneComponent`;
- `TriggerActionComponent`;
- `CrewMemberComponent` — роль, on-duty, repair skill;
- `InventoryComponent` — активный слот и три ссылки;
- `WeaponPickupComponent`;
- headless/logical NPC и weapon entities;
- остальные ранее поддерживаемые компоненты сцены.

Логические области, точки взаимодействия, зоны и inventory owners теперь перечисляются отдельными save-pass, поэтому объект не обязан иметь меш или rigid body, чтобы попасть в сцену.

Одна сущность может встретиться в нескольких component pools. `savedEntities` гарантирует, что она сериализуется в `objects` только один раз.

### 15.3. Remap ссылок

После загрузки ECS создаёт новые Entity ID. Затем SceneManager заменяет старые ссылки на новые как минимум для:

- inventory slots;
- trigger linked entity;
- trigger action target;
- weapon ownership/equipment и существующих связей сцены.

Область remap ограничена множеством сущностей, действительно восстановленных из Scene JSON. Это защищает внутренние связи заново импортированного GLB: случайное совпадение их числового Entity ID со старым JSON ID больше не приводит к перепривязке уже существующей импортированной сущности.

Если связанный JSON-объект отсутствует, ссылка становится недействительной.

Исправленный scope remap не делает отдельные импортированные части устойчивыми авторскими целями. `ShipPartComponent` по-прежнему пропускается SaveScene, части пересоздаются, а их прежние числовые ID не являются постоянным контрактом. Поэтому прямые `Trigger linked entity`/`Trigger Action target` на regenerated ShipPart не поддерживаются и блокируются; используйте сохраняемую сущность-контроллер, корень корабля, самостоятельно сериализуемое устройство или стабильную логическую proxy-сущность.

### 15.4. Что является runtime-состоянием

Не сохраняются как авторские данные:

- текущие акторы внутри триггера;
- cooldown и consumed one-shot;
- активный crew task и время назначения;
- `CrewTaskClaimComponent`;
- счётчик выполненных задач экипажа;
- состояние паузы и Time Scale;
- открытая HUD/NPC-панель;
- текущие временные уведомления.

Часть этих данных пересоздаётся системами по текущему состоянию Registry при запуске/обновлении Play, а часть существует только до перезагрузки сцены. В частности, crew assignments строятся заново из открытых инцидентов, trigger overlaps сбрасываются, а `completedTasks` не загружается из Scene JSON. Из-за общего Editor/Play Registry выход по F5 сам по себе не очищает все runtime-мутации.

### 15.5. Важные правила сохранения

Текущий save-pass:

- сохраняет как активные, так и неактивные авторские сущности и записывает их состояние;
- пропускает импортированные `ShipPartComponent`, сохраняя корень корабля;
- не реализует полноценную таблицу миграций между версиями;
- читает отсутствующие новые поля через значения по умолчанию компонента.

После загрузки `RigidBodyComponent` восстанавливается из JSON, а Bullet body пересоздаётся отдельным runtime-pass после remap ссылок. Благодаря этому сохранённые rifle pickups и коллайдеры сразу участвуют в физике и raycast.

Перед изменением схемы увеличивайте `version` и добавляйте явную миграцию/валидацию, если старые сцены должны гарантированно поддерживаться.

## 16. Практические рецепты

### 16.1. Сообщение при входе в отсек

1. `Create -> Trigger Zone`.
2. Переименуйте сущность в `Engine Room Entry`.
3. Разместите Box в дверном проёме.
4. Включите только actor `Player`.
5. Укажите Event ID `Deck01.EngineRoom.PlayerEntered`.
6. В Trigger Action выберите `Show HUD message`.
7. Включите `On Enter`, отключите `On Stay` и `On Exit`.
8. Введите `ENGINEERING DECK // AUTHORIZED PERSONNEL`.
9. Установите Duration `3.0`.
10. Сохраните сцену и проверьте в Play.

### 16.2. Автоматическая дверь

1. Создайте/выберите сущность с `DoorComponent`.
2. Создайте Trigger Zone перед дверью.
3. В `Linked entity` выберите дверь.
4. Action: `Set door open`.
5. On Enter: включено.
6. On Exit: включено.
7. Target value: `true`.
8. Invert value on Exit: включено.
9. Actor mask: Player и при необходимости NPC.

Вход открывает дверь, выход закрывает. Если в зоне одновременно находятся несколько акторов, каждый имеет собственный Enter/Exit; для сложной многопользовательской логики «закрыть только когда вышел последний» потребуется отдельный consumer active-occupants.

### 16.3. Одноразовый сюжетный маркер

1. Создайте Trigger Zone.
2. Включите `One shot`.
3. Отключите `Emit Stay events`.
4. Выберите только Player.
5. Укажите стабильный Event ID.
6. Добавьте HUD message или обработайте Event ID в своей системе.

One Shot сбрасывается при новом входе в Play и пока не является сохранённым сюжетным флагом. Для постоянного квестового прогресса нужна отдельная save-game система.

### 16.4. Зона тревоги для NPC и игрока

1. Создайте Trigger Zone типа Sphere.
2. Включите Player и NPC.
3. Установите Radius.
4. Включите Stay с интервалом `1.0`.
5. Задайте Event ID `Ship.Security.RestrictedArea`.
6. Используйте HUD message только на Enter, а Stay обрабатывайте специализированной security-системой.

### 16.5. Тест трёх винтовок

1. Трижды выполните `Create -> Rifle Pickup`.
2. Разнесите сущности по сцене.
3. В Play подберите каждую клавишей `E`.
4. Убедитесь, что HUD заполнил слоты `1–3`.
5. Попробуйте подобрать четвёртую — должен появиться `Inventory is full`.
6. Выберите слот `2`, нажмите `G`, затем снова подберите выброшенную винтовку.

### 16.6. Автономный инженер

1. Создайте `Crew NPC (logic)` или выберите полноценного NPC.
2. Убедитесь, что присутствуют NPC, Brain и Crew Member.
3. Role: `Engineer`.
4. On duty: включено.
5. Repair skill: например `1.4`.
6. Настройте detection range Brain так, чтобы ремонтная цель попадала в область обнаружения.
7. Создайте повреждение/пробоину с корректными repair-компонентами.
8. В Play следите за `CREW NETWORK` и полем Assigned task в runtime Inspector.

## 17. Диагностика проблем

### 17.1. Зона не срабатывает

Проверьте:

- сущность имеет Transform и Trigger Zone;
- `Enabled` включён;
- актор имеет Transform;
- выбран правильный actor mask;
- размеры являются half extents, а не полным размером;
- scale Transform не равен нулю;
- One Shot ещё не был использован;
- Cooldown не блокирует повторный вход;
- актор действительно вышел перед повторным входом;
- Play Mode запущен;
- для наглядности включён debug shape.

### 17.2. Trigger Action не изменяет цель

Проверьте:

- выбран подходящий Action;
- включено нужное событие Enter/Stay/Exit;
- назначен Target или Linked Entity;
- целевая сущность существует;
- для двери есть `DoorComponent`;
- `Target value` и `Invert on Exit` настроены ожидаемо;
- действие `Toggle` не запускается на Stay каждый кадр.

### 17.3. NPC не показывает панель

Проверьте:

- raycast действительно попадает в физическую форму NPC;
- дистанция меньше max distance или стандартных `3.0`;
- Interaction Component не отключён;
- у сущности есть `NPCComponent`;
- курсор/камера направлены на NPC;
- нажата `E`, а не только освобождён курсор через `F2`.

### 17.4. NPC не идёт ремонтировать

Проверьте:

- есть NPC и `NpcBrainComponent`;
- Crew Member включён `On duty`;
- NPC не hostile;
- нет активной ручной debug-команды;
- цель имеет `RepairableComponent`;
- пробоина не sealed или оборудование действительно повреждено;
- цель в detection range;
- другой NPC ещё не держит claim этой цели;
- навигация между комнатами и дверьми достижима.

### 17.5. Винтовка не подбирается

Проверьте:

- есть `WeaponComponent`;
- есть включённый `WeaponPickupComponent`;
- есть включённый `InteractionComponent`;
- raycast попадает в rigid body/коллайдер;
- дистанция не больше `3.0` или авторского значения;
- в инвентаре есть свободный слот;
- оружие не принадлежит другой сущности.

### 17.6. Выброшенная винтовка проваливается или имеет неверный коллайдер

В Weapon Pickup настройте:

- `Create physics on drop`;
- положительную mass;
- collision size под фактическую модель;
- Transform scale и положение поверхности.

Box collider является авторским приближением и не строится автоматически по сложной геометрии GLB.

### 17.7. Объект исчез после сохранения

Проверьте, что сущность является авторским объектом: имеет имя либо один из сериализуемых scene/gameplay-компонентов. Неактивное состояние сохраняется. Импортированные Ship Parts не сохраняются по отдельности: должен сохраняться корень импортированного корабля.

### 17.8. Ссылки Trigger/Inventory потерялись после загрузки

Проверьте, что связанная сущность сама попала в JSON. Remap может восстановить только объект, присутствующий в сохранённой сцене. Неактивные авторские цели поддерживаются; удалённая или несериализуемая цель превратится в `INVALID_ENTITY`.

### 17.9. Симуляция стоит, а HUD работает

Проверьте `CREW NETWORK`: возможно, отображается `SIM PAUSED` или `TIME x0.0`. Нажмите `P` либо увеличьте scale клавишей `]`.

## 18. Текущие ограничения

Следующие пункты являются осознанными границами текущей версии, а не скрытыми обещаниями функциональности:

- нет Undo/Redo редакторных операций;
- удаление подтверждается, но не восстанавливается;
- Play-in-Editor использует тот же ECS Registry, что и Editor Mode: автоматического snapshot/restore при F5 нет, поэтому runtime-мутации могут остаться в авторской сцене до явной загрузки JSON;
- Quick Create NPC создаёт логическую, а не полностью визуально настроенную сущность;
- Trigger Zone использует позиции сущностей как точки, а не объёмы их коллайдеров;
- `Other` проверяет точку Transform динамического rigid body, а не полный объём его коллайдера;
- у Trigger Action только одно встроенное действие на компонент;
- нет редакторной системы цепочек действий, условий и задержек;
- общая `EventQueue` очищается каждый кадр и зависит от порядка producer/consumer; событие не переживает кадр автоматически;
- One Shot и cooldown не являются постоянными save-game флагами;
- Scene JSON имеет version tag, но пока без формальной migration table и строгой проверки версии;
- remap защищает импортированные GLB internal links от коллизий ID, но regenerated `ShipPartComponent` всё равно не является сохраняемой прямой целью Trigger linked/target; такая авторская ссылка не поддерживается и блокируется;
- инвентарь ограничен тремя weapon slots;
- нет UI drag-and-drop, stackable items, количества, веса и категорий предметов;
- selection next/previous и swap доступны в API, но не привязаны к игровому UI;
- pickup использует один базовый box collider при выбрасывании;
- Crew Coordinator координирует ремонт, но пока не планирует медицину, безопасность, питание, смены и социальные задачи;
- Crew Task Claim является runtime-состоянием;
- журнал WorldEvent не сохраняется между Play-сессиями;
- поддерживаемая и проверяемая платформа — x64; полноценная Win32-конфигурация зависимостей и тестов отсутствует;
- полноценная save-game система прогресса игрока и живого мира отделена от scene authoring и ещё требуется.

Рекомендуемый следующий архитектурный шаг — разделить `Scene Save` (авторское состояние уровня) и `Save Game` (сюжет, инвентарь, повреждения, one-shot флаги, отношения и текущие задачи мира).

## 19. Сборка и тестирование

### 19.1. Полная проверка Debug и Release

Из PowerShell в корне проекта:

```powershell
.\scripts\verify_engine.ps1 -Configuration All
```

Скрипт последовательно:

1. проверяет шейдеры;
2. собирает `DX_FrameWork.vcxproj`;
3. проверяет наличие EXE и Assimp DLL;
4. собирает `tests/DXFrameworkCoreTests.vcxproj`;
5. запускает core contract tests.

`-Configuration All` покрывает две поддерживаемые конфигурации: `Debug|x64` и `Release|x64`. По итогам последней интеграционной проверки текущего среза обе конфигурации прошли проверку шейдеров, сборку движка и запуск core contract tests. Win32 в этот результат не входит и не считается настроенной целью.

### 19.2. Только Debug

```powershell
.\scripts\verify_engine.ps1 -Configuration Debug
```

### 19.3. Чистая пересборка

```powershell
.\scripts\verify_engine.ps1 -Configuration Debug -Rebuild
```

### 19.4. Выборочная проверка

```powershell
# Без сборки движка
.\scripts\verify_engine.ps1 -Configuration Debug -SkipEngine

# Без core tests
.\scripts\verify_engine.ps1 -Configuration Debug -SkipTests

# Без проверки шейдеров
.\scripts\verify_engine.ps1 -Configuration Debug -SkipShaders
```

### 19.5. Что уже проверяют core contracts

Для `GameTimer` тестируются:

- обычное продвижение времени;
- применение Time Scale к delta и total time;
- пауза;
- Reset с чистым состоянием;
- запрет отрицательного Time Scale;
- защита от `NaN` и бесконечной delta/time scale/reset time.

Для `InventorySystem` тестируются создание трёх слотов, последовательное заполнение, отказ от четвёртого оружия, синхронизация `EquippedWeaponComponent` и корректное освобождение ownership при выбрасывании.

После изменения Trigger, Inventory или Crew рекомендуется добавить отдельные контрактные тесты ECS без запуска рендера: Enter/Stay/Exit, cooldown, remap ссылок, заполнение трёх слотов, claim нескольких NPC и освобождение задачи.

### 19.6. Ручной smoke test

После автоматической проверки обязательно выполните короткий Play-тест:

1. Загрузить сцену.
2. Войти/выйти из Trigger Zone.
3. Проверить action на Enter и Exit.
4. Открыть NPC через `E`.
5. Подобрать три винтовки, переключить слоты и выбросить одну.
6. Проверить `P`, `[` и `]`.
7. Открыть F3 telemetry и Tab event log.
8. Вернуться по F5 и убедиться, что это лишь смена режима, а не восстановление snapshot.
9. Не сохраняя нежелательные runtime-мутации, повторно загрузить JSON, сохранённый до Play.
10. Отдельно выполнить авторское сохранение/загрузку и проверить, что trigger targets и inventory references сохранили смысл после Entity remap.

## Заключение

Обновлённый DX Framework уже позволяет собирать небольшой системный игровой фрагмент без написания C++ для каждого уровня: разместить NPC, винтовки и зоны, связать зоны с сообщениями, дверьми или активностью объектов, сохранить сцену и наблюдать результат в Play Mode.

Главная авторская идея новых систем — мир не должен ждать игрока. Экипаж самостоятельно замечает повреждения, делит задачи и ремонтирует корабль, а HUD показывает эту работу как часть общей симуляции. Игрок остаётся важным участником событий, но не единственным центром вселенной.
